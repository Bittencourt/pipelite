## 1. `crmBus` spine — mutations vs. direct-emit API routes

**Verdict: HOLDS**

- Bus + payload types: `src/lib/events/bus.ts`, `src/lib/events/types.ts`. Singleton is bridged
  through `globalThis.crmBus` — correct for surviving Turbopack's per-module-graph duplication.
- Four subscribers, all registered in `src/instrumentation.ts` (webhook, workflow-trigger,
  stage-history, audit — `src/lib/events/subscribers/{webhook,workflow-trigger,stage-history,audit}.ts`).
- Checked the "does every write path emit" question two ways:
  - **Mutation layer** (`src/lib/mutations/{organizations,people,deals,activities,dedup}.ts`):
    every create/update/delete/owner-transfer mutation I read (`createOrganizationMutation`,
    `updateOrganizationMutation`, `deleteOrganizationMutation`, `updateOrganizationOwnerMutation`,
    and their deal/person/activity counterparts) ends with a `crmBus.emit(...)` call. The one
    documented exception, `restoreOrganizationMutation`, deliberately emits nothing (no
    `organization.restored` event type exists) and instead writes the audit row directly inline —
    stated explicitly in a comment at `src/lib/mutations/organizations.ts:466-468` and verified by
    reading the function (it calls `db.insert(auditLog)` itself at line ~517).
  - **API routes**: confirmed the split the prompt described is real and consistent, not partial.
    `src/app/api/v1/organizations/{route.ts,[id]/route.ts,batch/route.ts}` do NOT import `crmBus`
    at all — they delegate entirely to `createOrganizationMutation` / `updateOrganizationMutation`
    / `deleteOrganizationMutation`, which already emit. `src/app/api/v1/{deals,people,activities}/[id]/route.ts`
    and `.../batch/route.ts` DO import `crmBus` directly and emit `*.created` / `*.updated` /
    `*.deleted` / `deal.stage_changed` at every mutating branch I checked (deals `[id]/route.ts:362,366,413`;
    people `[id]/route.ts:261,310`; activities `[id]/route.ts:251,286`; deals `batch/route.ts:232`;
    people `batch/route.ts:172`, which also runs `recalculateFormulas` per row before emitting,
    sharing one `FORMULA_EVALUATION_BUDGET` across the batch — same pattern as the mutation layer).
  - No mutating route found that silently emits nothing.

## 3. Bulk operations (38) vs. audit log (36)

**Verdict: HOLDS.**

Traced `bulkDeleteOrganizations` (`src/app/organizations/actions.ts:262-336`): loops over
deduplicated, capped ids, and for each one calls `deleteRecordByType("organization", id, userId)`
(`src/lib/bulk/dispatch.ts:126-132`), which routes to the single-record `deleteOrganizationMutation`
— the same function the single-record delete path uses. That mutation emits `organization.deleted`
once per call, so a bulk delete of N records produces **N** audit rows, not one and not zero. Same
shape confirmed for deals/people/activities bulk delete (`src/app/{deals,people,activities}/actions.ts`
all import `deleteRecordByType` from the same dispatch module). `src/lib/bulk/dispatch.ts`'s own
header states this is deliberate ("NO PERMISSION CHECK LIVES HERE EITHER... this also matches...
a mutation checks entity existence and nothing more").

Bulk owner reassignment: same shape via `updateRecordOwnerByType` → `updateOrganizationOwnerMutation`
(`src/lib/mutations/organizations.ts:372-416`), which emits `organization.updated` with
`changedFields: ["ownerId"]` per record whenever the owner actually changes (no-op emits nothing,
by design — comment at line 385-390).

## 4. Merge (39) vs. audit (36) vs. trash (37)

**Verdict: HOLDS for audit/trash sequencing. BROKEN for formula reactivity — see §5.**

Read `mergeRecordsMutation` end-to-end (`src/lib/mutations/dedup.ts:234-705`):
- Inside one transaction: survivor gets the chosen field values; the loser is soft-deleted
  (`deletedAt` set, `src/lib/mutations/dedup.ts:483-488`) — never hard-deleted; two `merged`-action
  audit rows are written directly via `tx.insert(auditLog)` (survivor's per-field diff + merge
  markers at line ~505-521, loser's "mergedInto" marker at line ~531-541); reparented deals/people
  each get an `updated` audit row recording the ownership change (line ~544-563); the pair table is
  updated and every other open pair referencing the loser is superseded.
- After commit (deliberately outside the transaction, since `crmBus`'s subscribers use the
  module-level `db` and would otherwise act on data a later statement could still roll back):
  `crmBus.emit(\`${entityType}.deleted\`, ...)` fires for the loser, which the audit subscriber
  picks up as a `deleted` tombstone — and the code explicitly avoids a duplicate "deleted" audit row
  for the loser by NOT writing one inline (comment at line ~519-533 walks through why, citing that
  `organization.deleted`/`person.deleted` are audited events).
- So: a merge is audited on both sides, and the loser genuinely lands in Trash (not hard-deleted) —
  restorable and reachable by the retention pruner like any other trashed record.

## 5. Formula reactivity (34) vs. merge (39) — the survivor's own fields

**Verdict: BROKEN (latent). New finding, not previously tracked in STATE.md.**

Every ordinary single-record edit recalculates the entity's own formula fields before emitting:
`updateOrganizationMutation` calls `recalcCustomFieldsForEmit(...)` (which wraps
`recalculateFormulas`) and only then emits (`src/lib/mutations/organizations.ts:322-337`, comment
"Emit CRM event — after the recalculation, never before (D-17)").

Merge does not do this for the **survivor**. After commit, the only recalculation call is
`recalcReparentedChildren(...)` (`src/lib/mutations/dedup.ts:640-651`, definition at 735-806), which
recomputes the *reparented children's* formula fields (one hop, budget-capped — a documented
limitation). I searched the entire merge path for any `recalculateFormulas({ ..., entityId:
survivorId, ... })` call and found none — the two occurrences of `survivorId` near the recalc
imports are both `.update(table)...where(eq(table.id, survivorId))` writes, not recalculation
calls. `39-RESEARCH.md:619` explicitly reasons about *not* relying on a survivor-rooted cascade
because it "recomputes nothing" when the survivor wins every field — but that research addresses
reaching the *children*, and never revisits whether the survivor's *own* formula fields (which can
depend on other native/custom fields that DID change via the merge, e.g. a field the user chose to
take from the loser) get recalculated. They do not.

Currently unreachable in production data: queried the live database —
`select entity_type, type, count(*) from custom_field_definitions group by 1,2` returns zero rows
of `type = 'formula'` for any entity (organization has only `multi_select`/`text`, person only
`text`, deal has `date/multi_select/number/single_select/text`). `39-10-SUMMARY.md:379-381`
independently confirms the dev database has "169 definitions, zero of type formula" and states the
db-backed merge test suite therefore "runs and finds nothing to do" for this exact case. So the gap
is real, code-verified, and untested, but currently dormant for lack of any formula field on a
mergeable entity type (organization/person).

**Exposing scenario:** an admin defines a formula field on Organizations, e.g.
`{{Industry}} - {{Name}}`. Two duplicate orgs differ in `Industry`; the operator merges them and
chooses the loser's `Industry` value for the survivor. The survivor's stored formula value is
whatever it was before the merge (or whatever raw value the merge picker offered, since
`MERGE_EXCLUDED_COLUMNS` does not exclude formula-type custom fields — checked
`src/lib/dedup/field-groups.ts:34-75` for any formula-type exclusion; none exists) — it does not
reflect the newly-merged `Industry`, and nothing subsequently recalculates it. This is the same
class of defect §32-45's "formula silently stale after a bulk write" concern names, just at a
different seam than bulk-reassign (which is provably fine, see §6).

## 6. Formula reactivity (34) vs. bulk ops / import

**Verdict: HOLDS.**

- Bulk owner reassignment: does not need recalculation because `ownerId` is not a member of
  `ENTITY_NATIVE_ATTRIBUTES` for any entity — verified by the mutation's own comment
  (`src/lib/mutations/organizations.ts:399-400`: "ownerId is absent from
  ENTITY_NATIVE_ATTRIBUTES.organization, so a recalculation would scope to zero evaluations"). Not
  a gap; a correct scoping decision.
- Bulk delete: soft-delete mutations explicitly skip recalculation on the record being deleted
  (`organizations.ts:437-438`, "No recalculation here: a soft delete is not a save"); this leaves
  the deleted record's own children with a known, STATE.md-tracked stale-value gap (WR-02,
  `.planning/STATE.md:357`) — pre-existing, not a v1.3 wiring break, and honestly labeled in both
  places.
- CSV/API import: `src/lib/import/formula-recalc-batch.ts` (`recalculateImportedRows`) is imported
  and used by `src/lib/import/pipedrive-api-import-actions.ts:59`. The people batch-create REST
  endpoint (`src/app/api/v1/people/batch/route.ts:146-183`) also runs `recalculateFormulas` per
  inserted row against one shared budget before emitting. Both paths recalculate; neither silently
  skips it.

## 8. Trash pruner (37) vs. uploads volume (43)

**Verdict: BROKEN — confirmed, and self-documented in source and in STATE.md (not a new finding,
but a real and currently-live one worth restating for this milestone).**

`src/lib/trash/prune.ts:63-73` states outright: "NOT COVERED — UPLOADED FILE BLOBS ARE NOT REMOVED.
A file custom field stores its bytes under `${UPLOAD_DIR}/${entityId}/${fieldName}/${storedName}`
and is referenced only from that JSONB column, so purging the row destroys the REFERENCE and leaves
the BYTES on disk (or in S3)." Verified the only file-deletion code path in the app is the
user-triggered single-file DELETE handler at
`src/app/api/files/[entityId]/[fieldName]/[filename]/route.ts:126` (`unlink(filePath)`) — the purge
mutations (`purgeOrganizationMutation`, `purgePersonMutation`, etc.) never call it, never import
`fs`, and never touch `UPLOAD_DIR`. `.planning/STATE.md:357` independently tracks this as CR-01,
deliberately scoped out of Phase 37's fix pass, and additionally notes the orphaned file's URL
survives in the audit-log tombstone the purge preserves, so the "leak" is discoverable, not just
inert disk usage.

Net effect: the daily trash pruner (`startTrashPruner`, confirmed alive via `/api/health` above)
runs unattended and will grow `UPLOAD_DIR` (or the S3 bucket) monotonically wherever a purged record
had a file-type custom field, forever, with no operator-visible signal (the pruner's own log line
reports rows purged, not bytes orphaned).

**Exposing scenario:** attach a file to a custom field on any deal, soft-delete the deal, wait past
retention (or manipulate `trash.retention.windowHelp`'s underlying setting for a same-day test) —
the file's bytes remain under `${UPLOAD_DIR}/<dealId>/<fieldName>/...` after the deal row and its
`audit_log` purge-adjacent rows exist, downloadable via the old signed/direct URL if anyone retains
it (confirmed the file API's auth check is `session?.user` only, not per-record — same STATE.md
note).

## 9. Trashed record ↔ timeline/audit visibility

**Verdict: HOLDS AS DESIGNED — deliberately out of scope, not a wiring break.**

`src/app/organizations/[id]/page.tsx:41,94` filters `isNull(organizations.deletedAt)` then calls

trashed — but this is a documented product boundary, not a broken cross-phase connection. Flagging
it here only because the prompt asked the question directly.

## 10. The sixth vacuous gate — `formatters-live.test.ts`

**Verdict: CONFIRMED, with direct evidence (this audit ran it both ways).**

```
$ npx vitest run src/lib/export/formatters-live.test.ts        # no DATABASE_URL, i.e. exactly CI's env
 ↓ src/lib/export/formatters-live.test.ts (24 tests | 24 skipped)
 Test Files  1 skipped (1)
      Tests  24 skipped (24)
```

`.github/workflows/ci.yml` runs `npm test`, which is `vitest run && vitest run --config
vitest.rsc.config.ts` — no `DATABASE_URL` is set anywhere in that job. `HAS_DB =
!!process.env.DATABASE_URL` (`formatters-live.test.ts:31`) is therefore always false in CI, and
`describe.skipIf(!HAS_DB)` skips all 24 assertions unconditionally, every run, forever. The file
is NOT excluded by `vitest.config.ts` (only `*.rsc.test.*` and `*.db.test.*` are excluded; this file
is neither), so it silently contributes 24 "skipped" entries to the green run rather than 24
failures or 24 passes — indistinguishable in a CI summary from "not applicable."

Ran it the other way, against the live stack, to check whether the code it guards currently works:

```
$ DATABASE_URL="postgresql://pipelite:pipelite@localhost:5433/pipelite" \
    npx vitest run src/lib/export/formatters-live.test.ts
 ✓ src/lib/export/formatters-live.test.ts (24 tests) 11644ms
 Test Files  1 passed (1)
      Tests  24 passed (24)
```

So: the export-filter path this file exists to catch (a malformed drizzle `= ANY(...)` fragment
that a fully-mocked suite cannot detect, per the file's own header, citing the exact Phase 37
regression it originally caught) is currently correct — but nothing in CI, and nothing in the
"4605 passed" figure, proves that, and a future regression identical in shape to the one this file
was written for would ship green.

## Summary

**Holds (verified):**
- crmBus emission is complete and consistent across the mutation-layer / direct-API-route split.
- Bulk delete and bulk owner-reassign correctly produce one audit row per record, not one for the
  whole batch and not zero.
- Merge audits both sides and correctly trashes (not hard-deletes) the loser.
- CSV/API import paths trigger formula recalculation; bulk owner-reassign correctly does not need
  to (ownerId isn't formula-referenceable).
- Saved views' shared prop contract and the three `TableMeta`-narrowed tables phase 43 touched are
  still fully wired to each other.
- The observability roster is complete and accurate — checked live against a running container, not
  just against source.

**Broken:**
- **Merge (39) never recalculates the survivor's own formula fields** — only reparented children
  get a one-hop refresh. New finding, not in STATE.md's existing known-limitations list. Currently
  dormant (zero formula-type fields exist in the live database today) but will silently produce
  stale formula values the moment an admin adds one to Organizations or People and someone merges
  two records that disagree on an underlying field.
- **The trash pruner never deletes uploaded file blobs on purge** — confirmed live in source and
  cross-referenced against STATE.md's own tracked CR-01. Storage leaks monotonically; already known,
  restated here because it is a genuine, currently-active cross-phase break between Phase 37 and 43.
- **`formatters-live.test.ts`'s 24 assertions never run in CI** — confirmed by running vitest with
  and without `DATABASE_URL`. The export path they guard is currently correct (also confirmed by
  running it live), but nothing automated would catch a regression there.

**Could not fully establish:**
- Whether `ownerId`/audit `diff.ts` renders every field type identically for every entity's owner
  transfer (spot-checked organizations only, did not exhaustively check deals/people/activities'
  diff-rendering for every native column).
- Whether every one of the "four list surfaces" (deals/people/organizations/activities) wires
  `SavedViewsBar` with fully identical fidelity — verified organizations in depth; people and
  pipelines only at the type-declaration level, not the full render path.

**Single most important finding:** the merge-vs-formula-reactivity gap (§5) is the one no phase's
own verification could have caught by construction — Phase 34 verified formula recalculation on
ordinary writes, Phase 39 verified merge's transactional correctness and its (documented) one-hop
child recalculation, and neither phase's test suite exercises the other's concern at their shared
seam. It is dormant only because the current dataset happens to define zero formula fields on
Organizations or People; it is a real, code-level gap that a future admin action makes live with no
further code changes needed to trigger it.
