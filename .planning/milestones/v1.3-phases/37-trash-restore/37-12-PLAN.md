  <action>
Create `src/app/api/v1/trash/route.ts` exporting `GET`, wrapped in `withApiAuth`.

Order of operations, copied from `src/app/api/v1/audit/route.ts`:

  1. Resolve the caller's role. `ApiAuthContext` is `{ userId, keyId }` and carries NO role, so the role
     must be re-read from storage on every request via `resolveActorRole(context.userId)`. An
     unresolvable actor — including a soft-deleted user — is DENIED with `Problems.forbidden()`, matching
     how `/api/v1/audit` treats the same case. This is NOT an admin gate: the trash listing is
     owner-or-admin, so the resolved role is used to build the scope, not to refuse the request.
  2. Validate the query string with a Zod schema whose `type` is `z.enum(TRASH_TABS).optional()`, built
     with the `as const satisfies` posture at `audit/route.ts:44-49`. An invalid `type` returns
     `Problems.validation(...)` with the issue list mapped the way the audit route maps it — the REST
     surface reports the error rather than silently falling back to deals, because an API caller who
     typo'd a type deserves to know.
  3. `const { offset, limit } = parsePagination(req)`.
  4. Call `listTrashed(tab, page, { userId: context.userId, role })` and `countTrashed({ userId, role })`
     for the total. The owner scope is applied inside those queries; do NOT re-filter the rows here and
     do NOT pass a role the caller supplied.
  5. Return `paginatedResponse(rows.map(serializeTrashRow), total, offset, limit)`.

Add a module-private `serializeTrashRow` that emits snake_case fields consistent with the other v1
serializers: `id`, `entity_type`, `name`, `secondary`, `deleted_at` (ISO string), `linked_parents`, and
`deleted_by` as a small object carrying the presentation `kind` plus whatever that kind resolves
(`name`/`email` for a user, `workflow_name` for a workflow run, nothing for the rest). Never emit a key
name for an `api_key` actor — there is none to emit.

Wrap the body in try/catch returning `Problems.internalError()` and logging
`GET /api/v1/trash failed:` with the error, matching every sibling route.

`parsePagination`'s `offset`/`limit` must be reconciled with `listTrashed`'s page-based signature —
convert the offset into a page using `TRASH_PAGE_SIZE`, or add an offset-based overload; pick one and
state which in the summary. Do not let a caller-supplied offset reach a query unbounded: `parsePagination`
already clamps `limit`, and the page conversion must clamp too.

`restore/route.ts` exporting `POST`, inside `withApiAuth`:

  1. `const { type, id } = await params`. Narrow `type` with `isTrashEntityType` after mapping the plural
     path segment through `TRASH_TAB_TO_ENTITY[parseTrashTab(type)]` — but return
     `Problems.validation(...)` for an unrecognised segment rather than silently defaulting to deals. A
     REST path segment is not a UI search param; a caller who asked for the wrong entity type must be
     told.
  2. Resolve the role with `resolveActorRole(context.userId)`; a `null` actor is denied with
     `Problems.forbidden()`.
  3. `const record = await findTrashedRecord(entityType, id)`; null returns `Problems.notFound("Record")`.
  4. Owner-or-admin: `record.ownerId !== context.userId && role !== "admin"` returns
     `Problems.forbidden()`. This must be the SAME decision the server action makes, so the two surfaces
     cannot diverge — reference `src/app/trash/actions.ts` in a comment.
  5. `runWithActor({ kind: "api_key", userId: context.userId }, () => restoreRecordByType(entityType, id))`.
     `api_key` is the honest actor kind for a REST call; the subscriber convention is to store the key's
     OWNER in `actor_user_id` for that kind, which is exactly what this passes.
  6. A `NOT_IN_TRASH` failure returns `Problems.notFound("Record")` — from the caller's point of view a
     record that is not in trash is simply not there. Any other failure returns
     `Problems.internalError()`.
  7. Success returns `noContentResponse()`.

`route.ts` exporting `DELETE` (the purge), inside `withApiAuth`:

  Same steps 1-3, with one change at step 4: this endpoint is ADMIN-ONLY. Resolve the role and return
  `Problems.forbidden()` unless it is `"admin"`, and do that BEFORE the record lookup so a non-admin
  cannot use the endpoint to probe whether an id exists. Then
  `runWithActor({ kind: "api_key", userId: context.userId }, () => purgeRecordByType(entityType, id))`
  and return `noContentResponse()` on success.

Both routes DELEGATE to the mutation layer rather than inlining the write, following
`DELETE /api/v1/organizations/[id]`, so there is exactly one restore implementation and one purge
implementation per entity and the ordered teardown lives in one place.

Both wrap their bodies in try/catch returning `Problems.internalError()` with a
`<METHOD> /api/v1/trash/[type]/[id]...  failed:` log line.

Neither route emits a CRM bus event — CONTEXT.md locks that no restore or purge event type is
introduced.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API key → REST route | An unauthenticated-by-session caller with no role in its context |
| path segment `[type]` → entity selection | An attacker-controlled string that selects a table |
| REST route → mutation layer | Where an id becomes an irreversible write with no UI in between |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-01 | Elevation of Privilege | `DELETE /api/v1/trash/[type]/[id]` | mitigate | `ApiAuthContext` carries no role, so the role is re-read from storage via `resolveActorRole(context.userId)` on every request and the admin check runs BEFORE the record lookup, so a non-admin cannot probe for existence. An unresolvable actor — including a soft-deleted user — is denied |
| T-37-02 | Information Disclosure | `GET /api/v1/trash` and the restore route | mitigate | The listing's owner scope is applied inside `listTrashed`/`countTrashed` from a role re-read from storage, never from a caller-supplied value; the restore route re-checks owner-or-admin against the record's own `ownerId`, matching the server action's decision exactly |
| T-37-03 | Tampering | the `[type]` path segment | mitigate | Narrowed through the closed `TRASH_TABS` vocabulary; an unrecognised value returns a validation problem rather than silently defaulting, because a REST caller must be told |
| T-37-08 | Repudiation | actor attribution for REST writes | mitigate | Every write is wrapped in `runWithActor({ kind: "api_key", userId: context.userId })`, matching the repo convention of storing the key's owner in `actor_user_id` for that kind. The trash view then renders the api-key badge without ever printing a key name it cannot resolve |
| T-37-31 | Information Disclosure | the serialized `deleted_by` | mitigate | The serializer emits no api-key name field at all — `audit_log` has no such reference and resolving one through the owner would print an arbitrary key as fact |
| T-37-32 | Tampering | duplicated write logic | mitigate | Both routes delegate to `src/lib/trash/dispatch.ts` rather than inlining, so the ordered teardown and the `isNotNull(deletedAt)` guard exist in exactly one place per entity. A grep assertion keeps a direct `db.update`/`db.delete` out of the route files |
