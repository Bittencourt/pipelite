<interfaces>
This plan builds the exact same two contracts plan 37-04 builds for deals and activities. The
signatures are:

  restorePersonMutation(id: string): Promise<{ success: true } | { success: false; error: string }>
  purgePersonMutation(id: string): Promise<{ success: true; detached: number } | { success: false; error: string }>
  restoreOrganizationMutation(id: string): Promise<{ success: true } | { success: false; error: string }>
  purgeOrganizationMutation(id: string): Promise<{ success: true; detached: number } | { success: false; error: string }>

`"NOT_IN_TRASH"` is the discriminated error code for "already purged or already restored".

The foreign keys blocking a bare DELETE (all `ON DELETE NO ACTION`, catalog-verified):
  purging a PERSON:        deals.person_id           → nullable → DETACH
  purging an ORGANIZATION: deals.organization_id     → nullable → DETACH
                           people.organization_id    → nullable → DETACH
`notes` is polymorphic with NO foreign key → its rows must be deleted explicitly.
Neither entity has a pure join-row child equivalent to `deal_assignees` / `deal_stage_history`.

The formula cascade, `CASCADE_CHILD_RELATIONS` at src/lib/formula-recalc.ts:225, walks
organization→deal, organization→person, person→deal, deal→activity. Restoring an organization is the
case where this matters most: it is the direction that repairs dot-reference formulas on the children.
`cascadeToChildren` (line 886) filters `isNull(relation.deletedAt)`, which is why the recalculation
must run AFTER the update.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server action / pruner → mutation layer | An id crosses into an irreversible multi-table write |
| purge transaction → live child rows | Purging an organization mutates deals and people the caller never selected |
| mutation → `audit_log` | The only durable record that a purge or restore happened |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-07 | Repudiation | `purgePersonMutation` / `purgeOrganizationMutation` | mitigate | The purge audit row is inserted inside the transaction so a rollback cannot record a purge that did not happen; `audit_log.entity_id` has no foreign key so the record's prior rows survive |
| T-37-10 | Repudiation | detach of `deals.person_id`, `deals.organization_id`, `people.organization_id` | mitigate | One `audit_log` row per detached child in the same transaction, so an unlinked deal or person traces back to the record purged out from under it. Organization is the widest case: two child tables |
| T-37-15 | Tampering | the final deletes | mitigate | `isNotNull(table.deletedAt)` is carried on the delete predicate itself, so a live record cannot be purged even by a guessed id |
| T-37-16 | Denial of Service | bare `DELETE` on a parent with children | mitigate | The teardown exists because both parents were empirically proven to raise SQLSTATE 23503; in the pruner an unhandled 23503 kills the tick |
| T-37-08 | Repudiation | actor attribution | mitigate | `getCurrentActor()` captured synchronously at entry, never taken from a payload; absence recorded honestly as `system` |
| T-37-SC | Tampering | npm/pip/cargo installs | accept | This phase installs nothing (`37-RESEARCH.md § Package Legitimacy Audit`) |
</threat_model>
