## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server action / pruner → mutation layer | An id crosses into an irreversible multi-table write |
| purge transaction → live child rows | A purge mutates rows the caller never selected |
| mutation → `audit_log` | The only durable record that a purge or restore happened |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-07 | Repudiation | `purgeDealMutation` / `purgeActivityMutation` | mitigate | The purge audit row is inserted INSIDE the transaction, so a rollback cannot record a purge that did not happen; `audit_log.entity_id` has no foreign key, so the record's prior rows survive the hard delete. Asserted by an order test |
| T-37-10 | Repudiation | detach of `activities.deal_id` | mitigate | One `audit_log` row per detached child, `action: 'updated'`, `changes: { dealId: { from: id, to: null } }`, written in the same transaction. Without it a live activity loses its deal with no trace |
| T-37-15 | Tampering | the final `delete(deals)` predicate | mitigate | `isNotNull(deals.deletedAt)` is carried on the delete itself, so a guessed id for a LIVE record cannot be purged even if every upstream check were bypassed |
| T-37-16 | Denial of Service | bare `DELETE` on a parent with children | mitigate | The ordered teardown exists precisely because a bare delete raises SQLSTATE 23503 — proven by rolled-back probes — which in the pruner would kill the tick.
