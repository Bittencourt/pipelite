column, thread the two new server props, and mount the bar, its spacer and the failure report.

Purpose: this surface is the reference implementation for People (`people/data-table.tsx` is
byte-identical modulo the rename) and it is where the phase's two subtlest wiring rules land.
`getRowId` is load-bearing rather than hygiene: TanStack's default row id is the row INDEX, and the
rows array is CUMULATIVE across Load More (`page.tsx` takes `limit = PAGE_SIZE * pageNum + 1` and
slices to `PAGE_SIZE * pageNum`), so with index keys any reorder or removal silently retargets the
selection onto different records — and the next action would be a bulk delete of records the user never
picked. And the clear-on-filter effect must key on the SEARCH STRING, never on the `data` array,
because Phase 35 measured that `revalidatePath` re-renders the current client tree regardless of the
path argument, so a `[data]`-keyed effect would fire mid-action and wipe the failed-id selection SC-3
requires to survive.
Output: two edited files; `organizations/columns.tsx` is deliberately NOT touched.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server page -> client table | Only plain serializable values cross (`retentionDays: number \| null`, `bulkOwners: {id,name}[]`); a React element crossing into a Radix `asChild` slot renders nothing at all |
| selection state -> destructive action | The id set the bar submits is derived here; a phantom or mis-keyed id is a delete of a record the user never picked |
| owners list -> ownership transfer | An unapproved or soft-deleted user in that list becomes the owner of up to 100 records, and the write succeeds so no per-record failure reports it |
