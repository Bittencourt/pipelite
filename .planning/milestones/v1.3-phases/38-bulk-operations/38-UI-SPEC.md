# Phase 38 — UI Design Contract

> Visual and interaction contract for multi-record selection on the four CRM list surfaces, the
> floating bulk action bar, bulk soft-delete, bulk owner reassignment, selection-scoped CSV export,
> and the per-record failure report.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Sources:** `38-CONTEXT.md` (all decisions LOCKED — none re-asked, none re-litigated),
`.planning/REQUIREMENTS.md` (BULK-01..04), `.planning/ROADMAP.md` (Phase 38 SC-1..SC-5), and —
above all — **`37-UI-SPEC.md`**, whose spacing scale, type roles, colour reserve, copy rules,
accessibility contract and registry posture this phase inherits wholesale.

**Autonomous mode.** Every grey area `38-CONTEXT.md` left to Claude's discretion is resolved below
and annotated **(auto-accepted recommended, autonomous mode)**. No question was put to the user.

**Inheritance is the governing rule.** Phase 35 declared the scale, Phases 36 and 37 restated it.
This phase restates it for a fourth set of surfaces. Where a section repeats an inherited value it
is to make the executor's job single-file; where it *adds* something, the addition is called out and
justified. Nothing here contradicts `37-UI-SPEC.md`.

**No new dependencies. No new shadcn component. No registry fetch.** `checkbox.tsx`,
`alert-dialog.tsx`, `alert.tsx`, `dialog.tsx`, `select.tsx`, `table.tsx`, `button.tsx`, `card.tsx`

`checkbox.tsx` is required and is specified in § Surface 1 — it is the only primitive this phase
touches.

## Spacing Scale

Identical to `37-UI-SPEC.md`, `36-UI-SPEC.md` and `35-UI-SPEC.md`. All multiples of 4.

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | `gap-1` between a failed record's name and its reason; `mr-1` from the stage-header checkbox to the stage colour dot |
| sm | 8px | `gap-2` between the bar's controls; `p-2` on every checkbox hit-area wrapper; `px-2 py-2` bar padding on the inner row; `space-y-2` inside the reassign dialog's field block; `gap-2` between icon and label in every bar button |
| md | 16px | `space-y-4` on each list's root stack (existing); `gap-4` between the reassign dialog's description and its field; `mb-4` above a table when the failure report is present |
| lg | 24px | `space-y-6` page shell (existing); `px-6` / `py-6` `Card` padding (from the `Card` primitive); `p-6` dialog padding (from `dialog.tsx` / `alert-dialog.tsx`) |
| xl | 32px | `h-8` on every bar button (`size="sm"`); the 32×32 checkbox pointer target (16px control + `p-2`) |
| 2xl | 48px | Not used |
| 3xl | 64px | Not used |

**Exceptions: three, all declared, none novel in kind.**

1. **32px bar controls.** Every control in the bulk action bar renders at `size="sm"` (32px tall),
   below the 44px touch guidance. Accepted for exactly the reason Phases 35, 36 and 37 accepted it:
   desktop-first CRM, and the controls are **always visible**, never a hover-only reveal.
2. **32px checkbox pointer target.** The `Checkbox` primitive is `size-4` (16px). Every instance in
   this phase is wrapped in `<div className="flex items-center justify-center p-2">`, giving a
   32×32px pointer target inside a ~40px-tall table row. Still under 44px; the same desktop-first
   exception, and the row's own height gives comfortable vertical aim. **The bare 16px control with
   no wrapper is a contract violation** — the wrapper is not optional.
3. **`bottom-4` / `inset-x-4` on the fixed bar, and an `h-20` (80px) in-flow spacer.** 16px, 16px and
   80px are all multiples of 4. The spacer exists so the bar never covers the last row or the
   `Load More` button; see § Surface 3.

No other exception. Every value on all seven surfaces is one of the declared tokens.

Inherited verbatim from `37-UI-SPEC.md`. Five roles, four sizes, two declared weights, two declared

**Weight exception 1 (inherited, unchanged).** 500 (`font-medium`) is hardcoded in shared primitives
this phase declines to patch: `button.tsx`'s base class and `alert.tsx`'s `AlertTitle`. Every bar
button label and the failure report's title therefore render at 500. Phases 35, 36 and 37 all took
this posture; **it is the same exception, not a new one** — no new weight value enters the product.

> `AlertTitle` is `font-medium leading-none`. The Label role above asks for 600. **Do not patch
> `alert.tsx`** — accept 500 there under exception 1, exactly as Phase 37 accepted 500 on `TableHead`
> and `TabsTrigger`. Adding `font-semibold` in the consumer's `className` is also acceptable and is
> the preferred resolution, because it is local. Either is in contract; patching the primitive is not.

**Weight exception 2 (inherited).** `text-3xl font-bold` on page `<h1>`s. Not reached by this phase.

**The selection count is Label (14/600), not Body, and it is the bar's first element.** A user about
to press *Delete* must read a number before they read a verb. Rendering "12 selected" at Body weight
next to four 500-weight button labels would make the count the *weakest* text in the most consequential
control cluster in the product.

## Color

| Role | Token | Value (light) | Usage |
|------|-------|---------------|-------|
| Dominant (60%) | `--background` / `--card` | `oklch(1 0 0)` | Page background; the `Card` wrapping each list table; **the floating bar's own surface (`bg-card`)**; both dialog surfaces |
| Secondary (30%) | `--muted` / `--border` | `oklch(0.97 0 0)` / `oklch(0.922 0 0)` | The bar's border and `shadow-lg`; **selected row background (`data-[state=selected]:bg-muted`, already in `table.tsx:60` — free, no new class)**; keyboard-cursor row (`bg-muted/50`, existing); every failure reason and every helper line (`text-muted-foreground`) |
| Accent (10%) | `--primary` | `oklch(0.205 0 0)` | See reserved list |
| Destructive | `--destructive` | `oklch(0.577 0.245 27.325)` | See reserved list |

**Accent (`--primary`) reserved for exactly four things in this phase — nothing else:**

1. **The checked checkbox.** `checkbox.tsx` already ships
   `data-[state=checked]:bg-primary data-[state=checked]:text-primary-foreground`. A 16×16 solid
   primary square with a white check, repeated down the leading column, **is** this phase's selection
   indicator — and 50 of them stacked form exactly the vertical accent rail a hand-drawn one would.
   Total accent area at a full page of 50: ~12,800px², well inside 10%.
2. **The `Reassign N records` confirm button** in the reassign dialog — `Button variant="default"`,
   the only `--primary`-filled *button* this phase adds, on either surface.
3. **The selected deal card's tint** — `bg-primary/5` on the card root. See the collision note below.
4. The keyboard focus outline, already global (`globals.css:151-157`).

**The bulk action bar itself has ZERO accent-filled controls, and that is deliberate.** It floats
above the rows with `bg-card shadow-lg`, so it already has the strongest visual weight on the page;
a filled primary or filled destructive button inside it would read as the page's dominant element
and would sit permanently over the user's data. `Reassign owner` and `Export CSV` are
`variant="outline"`; `Delete` is `variant="ghost"` with `text-destructive`; `Clear selection` is
`variant="ghost"`. This is the identical argument `37-UI-SPEC.md` makes for `/trash`'s row actions,
and it is the correct one here for a stronger reason: the bar is *superimposed on* the content.

**Destructive (`--destructive`) reserved for exactly four things:**

1. The **`Delete`** control in the bar — `Button variant="ghost" size="sm"` with
   `className="text-destructive hover:text-destructive"`. Text and icon only, no fill. Matches the
   existing `text-destructive` ghost row actions in `organizations/columns.tsx:121` and
   `activity-list.tsx` (the per-row delete).
2. The `AlertDialogAction` confirm button in the **bulk delete** dialog (filled,
   `bg-destructive text-destructive-foreground hover:bg-destructive/90`) — the same class string the
   six existing delete dialogs already use.
3. The **failure report** — `Alert variant="destructive"`, which is
   `border-destructive/50 text-destructive` with **no fill**. A partial failure is an error the user
   must read; this is the one place in the phase where destructive is a *region*, not a control, and
   it is admissible because `alert.tsx` gives it no background.
4. Sonner `toast.error(...)` / `toast.warning(...)`, owned by the `sonner.tsx` primitive.

**Never destructive:** the checkbox in any state, the selected row or card, the bar's surface or
border, the count text, `Clear selection`, or the reassign dialog. **A selected record must not be
rendered in red.** Selecting twelve records is not an error, and colouring the selection as danger
would make the one genuinely dangerous control in the bar invisible.

### The selection-indicator collision (read this before writing any class)

Three primary-coloured "selected" affordances already exist in this codebase and **this phase must
not add a fourth in the same visual language**:

| Existing affordance | Where | Rendered as |
|---|---|---|
| Keyboard cursor row | `useDataTableKeyboard` → `rowProps(i)` | `data-selected="true"` → `box-shadow: 0 0 0 2px var(--primary)` (`globals.css:172-174`) **plus** `className="bg-muted/50"` (`data-table-keyboard.tsx:147`) |
| Keyboard cursor card | `useKanbanKeyboard` → `DealCard isSelected` | `ring-2 ring-primary ring-offset-2` (`deal-card.tsx:132`) |
| Expanded deal card | `deal-card.tsx` local state | `ring-2 ring-primary` (`deal-card.tsx:131`) |

**Therefore, hard rules:**

- **Bulk selection on a table row is `data-state="selected"`, never `data-selected`.**
  `data-selected` is the keyboard cursor and is already wired on all four tables
  (`organizations/data-table.tsx:181`, `people/data-table.tsx:181`, `activities/activity-list.tsx:481`,
  `admin/pipelines`, `admin/users`). `data-state={row.getIsSelected() && "selected"}` is **already
  present and inert** on those same lines — it starts working the moment `rowSelection` is enabled,
  and `table.tsx:60` already styles it `bg-muted`. Zero new CSS.
- **`bg-muted` (selected) vs `bg-muted/50` (keyboard cursor) is a near-invisible difference, and the
  spec does not pretend otherwise.** The row tint is *reinforcement*. The three carriers that do the
  actual work are: the checked checkbox (primary fill), the bar's live count (Label 14/600), and the
  checkbox's own `aria-checked`. A checker must not read the weak tint as the affordance.
- **A bulk-selected row or card must never get a primary ring or a primary border.** Both ring
  treatments are taken, and a card can legitimately be keyboard-focused *and* expanded *and*
  bulk-selected at once.
- **A bulk-selected deal card gets `bg-primary/5`** (replacing `bg-card`), because a card sits on a
  `bg-muted/50` column track where `bg-muted` would vanish entirely. `bg-primary/5` is a 5% tint of
  an existing token and composes cleanly under both existing rings — the same family as the
  `bg-primary/10` header icon tiles the app already uses.

**Forbidden:** any hardcoded hex, `bg-white`, `text-black`, `text-red-*`, `text-green-*`, `bg-red-*`,
`bg-green-*`, or any colour outside the token set anywhere in the seven surfaces. (Note:
`activity-list.tsx:402-404` already contains `border-red-200 bg-red-50 text-red-600 text-red-700` in
its overdue banner. That is pre-existing debt in a block this phase does not touch. **Do not copy it,
and do not "fix" it here** — it is unrelated scope.)

## Surface 1 — Row selection on Organizations, People, Activities

### Where the state lives

Per `38-CONTEXT.md` (locked): TanStack Table's own `rowSelection`, per list, with
`getRowId: (row) => row.id`. No URL param, no global store, no context.

```ts
const [rowSelection, setRowSelection] = useState<RowSelectionState>({})

const table = useReactTable({
  data,
  columns: columnsWithSelect,
  getRowId: (row) => row.id,          // REQUIRED — without it the key is the row index
  state: { rowSelection },
  onRowSelectionChange: setRowSelection,
  enableRowSelection: true,
  getCoreRowModel: getCoreRowModel(),
  // ...existing meta unchanged
})
```

**`getRowId` is load-bearing, not hygiene.** TanStack's default row id is the row *index*. `Load More`
re-renders the server tree with `PAGE_SIZE * pageNum` rows (verified: `organizations/page.tsx:19-20`
takes `limit = PAGE_SIZE * pageNum + 1` and slices to `PAGE_SIZE * pageNum` — the array is
**cumulative**, which is what makes `38-CONTEXT.md`'s "selection persists across Load More" true).
With index keys, any reorder or removal silently retargets the selection onto different records —
and the next action would be a bulk delete of records the user never picked.

### The derived id list (defensive, and required)

```ts
const loadedIds = useMemo(() => new Set(data.map((r) => r.id)), [data])
const selectedIds = useMemo(
  () => Object.keys(rowSelection).filter((id) => rowSelection[id] && loadedIds.has(id)),
  [rowSelection, loadedIds]
)
```

**`selectedIds` is derived from `rowSelection`'s keys, intersected with the loaded rows — never from
`table.getSelectedRowModel()`.** Two reasons, both real:

1. TanStack does **not** prune `rowSelection` when a row leaves `data`. After a successful bulk
   delete the server tree re-renders without those rows, and any un-pruned key would linger as a
   phantom inflating the count. The `loadedIds` intersection makes a phantom impossible *by
   construction*, on top of the explicit clearing in § Interaction Contract.
2. `activity-list.tsx` uses `getFilteredRowModel()` (client-side filtering, line ~395). A row hidden
   by that filter is still in `rowSelection`, so a model-derived list could act on records the user
   cannot see.

### The header select-all

**`getToggleAllPageRowsSelectedHandler()` / `getIsAllPageRowsSelected()`, never the `AllRows`
variants.** The `Page` variants operate on `getRowModel().rows` — the final row model. On Activities
that is the *filtered* set, which is what the user can see and what the count must match. The
`AllRows` variants would select filter-hidden rows and make the bar's count exceed the visible row
count, which is the exact defect `38-CONTEXT.md` rejects filter-wide select-all to avoid.

Select-all is **page-scoped** (locked): it selects the rows currently loaded — 50 after first paint,
100 after one `Load More`, and so on. The bar always states the exact count. There is no
"select all N matching" affordance and no copy implying one.

### The indeterminate state — a real defect to prevent, and its fix

`checkbox.tsx` renders **only** `<CheckIcon />` inside `CheckboxPrimitive.Indicator`. Radix renders
the Indicator for `checked === "indeterminate"` as well as for `true`, so a partially-selected header
checkbox would render **a check mark, visually identical to all-selected**. Shipping the header
checkbox without fixing this means "3 of 50 selected" and "50 of 50 selected" look the same.

**Fix — additive, two lines, in `src/components/ui/checkbox.tsx`:**

```tsx
import { CheckIcon, MinusIcon } from "lucide-react"   // MinusIcon is the alias of `minus`
// ...
<CheckboxPrimitive.Indicator
  data-slot="checkbox-indicator"
  className="grid place-content-center text-current transition-none"
>
  <CheckIcon className="size-3.5 group-data-[state=indeterminate]/checkbox:hidden" />
  <MinusIcon className="hidden size-3.5 group-data-[state=indeterminate]/checkbox:block" />
</CheckboxPrimitive.Indicator>
```

…with `group/checkbox` added to the Root's `className`. **This is behaviour-neutral for every
existing consumer** — verified 2026-08-17: the **10** modules importing `Checkbox`
(`import-preview.tsx`, `boolean-field.tsx`, `notification-form.tsx`, `admin/export/export-form.tsx`,
`select-entities-step.tsx`, `webhook-dialog.tsx`, `all-users-client.tsx`, `login/page.tsx`,
`admin/fields/[entityType]/field-dialog.tsx`, `admin/fields/[entityType]/fields-list.tsx`) pass
**no** `indeterminate` value, so the new branch is unreachable for all of them.

> **CORRECTED during execution of plan 38-05.** This census originally said 8 and omitted the two
> `admin/fields/[entityType]/` modules, which arrived in `a108448 feat(44-08)` and import with
> **single quotes** — a double-quote-only grep does not see them, which is how the count went stale.
> The conclusion is unchanged and now stronger: `grep -rn "indeterminate" src/` returns **0**
> repo-wide, so all ten are provably unable to reach the new branch. Any gate asserting this count
> must assert 10.
(auto-accepted recommended, autonomous mode — the alternative, dropping indeterminate and relying on
the count alone, ships a header control that lies about its own state.)

### The select column — where it lives, and why NOT in `columns.tsx`

**New shared module `src/components/bulk/select-column.tsx`, consumed inside each table's
`'use client'` component. `organizations/columns.tsx` and `people/columns.tsx` are NOT edited.**
(auto-accepted recommended, autonomous mode)

`38-CONTEXT.md` § Integration Points names `{organizations,people}/columns.tsx` as the edit site and
notes the resulting collision with Phase 43's POLISH-01 retype. That is an *observation*, not a
locked decision, and component decomposition is explicitly Claude's discretion. Prepending the column
inside `data-table.tsx` is strictly better on four counts:

1. **It removes the Phase 43 collision entirely.** Neither `columns.tsx` file is touched, so
   POLISH-01's retype has no merge surface with this phase.
2. **It gets translated `aria-label`s.** Both `page.tsx` files import the *static* `columns` array
   (verified: `organizations/page.tsx:4`, `people/page.tsx:5`) — the translated `useColumns()` hook
   exported alongside it is dead code on both surfaces. A checkbox column added to the static array
   could not call `useTranslations`, so its accessible name would be untranslated English.
3. **One definition, three tables.** Activities defines its columns inline inside `activity-list.tsx`
   and has no `columns.tsx` at all, so a `columns.tsx`-based approach needs two implementations
   regardless.
4. It keeps the checkbox column's `onClick` guard adjacent to the `useDataTableKeyboard` wiring it
   must coexist with.

```ts
// src/components/bulk/select-column.tsx  — 'use client'
export function useSelectColumn<T>(getLabel: (row: T) => string): ColumnDef<T, unknown>
```

```ts
// in each data-table.tsx
const selectColumn = useSelectColumn<Organization>((o) => o.name)
const columnsWithSelect = useMemo(() => [selectColumn, ...columns], [selectColumn, columns])
```

Column def contract:

| Property | Value |
|----------|-------|
| `id` | `"select"` |
| `size` | `44` — picked up automatically by `activity-list.tsx`, which renders `style={{ width: header.getSize() }}`. Organizations/People do not read `getSize()`; there the column auto-sizes to its 32px target plus `p-2` cell padding (~48px), which is correct and needs no change to their header rendering |
| `enableSorting` | `false` |
| `enableHiding` | `false` |
| `header` | The select-all checkbox, in the same `p-2` wrapper |
| `cell` | The row checkbox, in the same `p-2` wrapper |
| Position | **First column**, before the existing leading column |

### The checkbox cell

```tsx
<div
  className="flex items-center justify-center p-2"
  onClick={(e) => e.stopPropagation()}
>
  <Checkbox
    checked={row.getIsSelected()}
    onCheckedChange={(v) => row.toggleSelected(!!v)}
    disabled={!row.getCanSelect()}
    aria-label={t("selectRow", { name: getLabel(row.original) })}
  />
</div>
```

- **`aria-label` names the record, not the row.** Fifty checkboxes all announcing "Select row" is
  useless; "Select Acme Ltda" is navigable. This is the same rule `37-UI-SPEC.md` states for
  icon-only controls: the accessible name must identify the object.
- **`stopPropagation` on the wrapper's `onClick`.** Correcting a claim in the phase brief: the row
  `onClick` on these tables is `rowProps(index).onClick`, which is
  `() => setSelectedIndex(index)` — it moves the **keyboard cursor** and does **not** open the
  record. `onOpen` is bound to the `enter` hotkey (`data-table-keyboard.tsx:90-97`), not to a click.
  So the stop is defence in depth, not a bug fix: toggling a checkbox must have exactly one effect,
  and the guard survives any future change to what the row click does.
- **No `<label>` element, and no `htmlFor`.** The `aria-label` is the accessible name; adding a
  visible label would put text in a 48px column.

### The header checkbox

```tsx
<div className="flex items-center justify-center p-2">
  <Checkbox
    checked={
      table.getIsAllPageRowsSelected() ||
      (table.getIsSomePageRowsSelected() && "indeterminate")
    }
    onCheckedChange={(v) => table.toggleAllPageRowsSelected(!!v)}
    disabled={table.getRowModel().rows.length === 0}
    aria-label={t("selectAllLoaded", { count: table.getRowModel().rows.length })}
  />
</div>
```

**Disabled, not hidden, on an empty table.** A header cell that appears and disappears makes the
column widths jump between an empty and a non-empty result, and Radix keeps the disabled control in
the tab order-free state that `disabled:opacity-50` already communicates.

### Always visible, never hover-revealed

The checkbox column renders unconditionally on all three tables — not on row hover, not only once a
selection exists. Inherited posture: `37-UI-SPEC.md` § Spacing accepted its 32px row controls
*specifically because* they are "always visible (never a hover-only reveal)". A hover-reveal is
invisible on touch, invisible to a keyboard user scanning the table, and undiscoverable — and SC-1 is
a discoverability criterion. Cost: one ~48px column. Accepted.
(auto-accepted recommended, autonomous mode)

## Surface 2 — Card selection on the Deals kanban

`/deals` is a kanban, not a table (locked, and verified: `kanban-board.tsx`, `kanban-column.tsx`,
`deal-card.tsx`). There is no `useReactTable`, so **this is the one declared exception to
"selection lives in TanStack `rowSelection`"**: `kanban-board.tsx` owns
`useState<Set<string>>` for selected deal ids, and derives the same `selectedIds` array. A full

### Per-card checkbox

Placed as the **first child of the card's existing `flex items-start justify-between gap-2` row**
(`deal-card.tsx:135`), before the `flex-1 min-w-0` text block — not floated, not absolutely
positioned, so it never overlaps the title.

```tsx
<div
  className="flex items-center justify-center p-2 -m-2"
  onClick={(e) => e.stopPropagation()}
  onPointerDown={(e) => e.stopPropagation()}
  onKeyDown={(e) => e.stopPropagation()}
>
  <Checkbox
    checked={isBulkSelected}
    onCheckedChange={(v) => onBulkSelectChange(deal.id, !!v)}
    aria-label={t("selectRow", { name: deal.title })}
  />
</div>
```

**All three stops are required, and each prevents a different concrete failure:**

| Handler | What it prevents |
|---------|------------------|
| `onClick` | The card root's `onClick={() => setIsExpanded(!isExpanded)}` (`deal-card.tsx:138`). Without this, checking a box also expands the card |
| `onPointerDown` | dnd-kit's `listeners` are spread on the card root (`deal-card.tsx:140`). `PointerSensor` has `activationConstraint: { distance: 5 }` so a clean click will not start a drag, but a 6px pointer wobble on the checkbox would drag the deal into another stage |
| `onKeyDown` | The root also carries `{...attributes}` from `useSortable` — `role="button"`, `tabIndex=0`, and the `KeyboardSensor` binding. Space on a focused card starts a keyboard drag; Space is also how a keyboard user toggles a checkbox. Without the stop, keyboard selection is impossible |

The `-m-2` cancels the wrapper's own padding so the 32px target does not add 16px to every card's
height — the padding buys the pointer target, the negative margin returns the layout.

**Nesting note, declared rather than discovered later.** The card root carries `role="button"` and
`tabIndex=0` from `useSortable`'s `attributes`, so the checkbox is an interactive control inside a
`role="button"`. This is a **pre-existing structural property of the card**, not something this phase
introduces: the expanded card already nests two `Button`s and a `Link` inside the same root
(`deal-card.tsx:181-210`). The checkbox is reachable and operable, and re-architecting the card's
drag handle is out of scope. Do not "fix" it by moving the checkbox outside the draggable node — that
breaks the card's layout and the drag target.

## Surface 3 — The bulk action bar

### Placement: a fixed bottom bar. This is the load-bearing layout decision of the phase.

(auto-accepted recommended, autonomous mode)

```tsx
{selectedIds.length > 0 && (
  <>
    <div
      role="region"
      aria-label={t("actionBarLabel", { count: selectedIds.length })}
      className="fixed inset-x-4 bottom-4 z-30 mx-auto w-fit max-w-[calc(100%-2rem)]

    >

        <span className="text-sm leading-tight font-semibold px-1">

        </span>
        {/* Reassign owner | Export CSV | Delete | Clear selection */}
      </div>
    </div>
    <div aria-hidden className="h-20" />
  </>
)}
```

**Three placements were considered; this one is chosen for reasons the other two fail:**

| Candidate | Why rejected |
|-----------|--------------|
| A row inserted **above the table**, below the search input | Checking the first row would push every row down ~48px *while the user is mid-selection*, so the second checkbox they aim at is under a different record. On a 50-row (up to 150 after `Load More`) list it also scrolls out of view long before the user finishes selecting |
| Swapping the header row's `Add Organization` button for the bulk cluster | Zero layout shift, but it hides the page's primary CTA, has no equivalent on `activity-list.tsx` (whose search lives in a different component), and still scrolls away |
| **Fixed bottom bar (chosen)** | Zero layout shift above the fold — nothing the user is pointing at moves. Reachable at any scroll depth, which matters precisely because `Load More` accumulates 150+ rows. Identical on the kanban, which has no search row and whose board scrolls horizontally. It is also the pattern every mature bulk-selection UI converges on, so it costs the user no learning |

**The `h-20` spacer is not optional.** A `fixed` bar would otherwise cover the last table row and the
`Load More` button. The spacer is the *last* element in the list's stack, so it changes only what is
below everything — no row the user is aiming at moves.

**`max-w-[calc(100%-2rem)]` + `flex-wrap` is a hard requirement, and it is the direct answer to
Phase 37's lesson.** A `fixed` element that exceeds the viewport **does** contribute to
`document.scrollWidth`. At 320px the bar must **wrap to two or three lines and never scroll
horizontally**. Verified per § States Checklist through a 320px same-origin iframe — `resize_window`
cannot change `window.innerWidth` in this environment (Phase 37). Note that the global app `<header>`
already overflows at 320px on every route (37-UAT G5, `scrollWidth 416` vs `clientWidth 301`) — that
pre-existing overflow **must not be misattributed to this bar**. Measure the bar's own
`scrollWidth`/`clientWidth`, not the document's.

- `BULK_MAX_IDS = 100` lives in **one shared constant**, `src/lib/bulk/limits.ts`, imported by the

  a per-mutation copy is four numbers that can drift out of agreement with the one string that
  states the number to the user. auto-accepted recommended, autonomous mode)

## Surface 4 — Bulk delete confirmation

`AlertDialog`, **controlled**, rendered from inside a `'use client'` module with no trigger component
of its own. This is the non-definer shape `trash-table.tsx` and `retention-form.tsx` use, and it is a
hard boundary: **CFUI-01** (Phase 44) means a React element crossing the RSC boundary into a Radix
`asChild` slot renders nothing at all, silently, and a repo-wide gate
(`src/app/admin/fields/[entityType]/__tests__/rsc-boundary.test.tsx`) fails the build if a non-client
module hands children to one.

| Field | Copy / treatment |
|-------|------------------|
| Title | `bulk.deleteDialog.title` — **"Delete 12 records?"** (ICU plural) |
| Description | `bulk.deleteDialog.description` — **"12 records move to Trash. You can restore them for 30 days."** — or `descriptionNoRetention` when the retention window is unset |
| Cancel | `bulk.deleteDialog.cancel` — **"Keep records"**, not "Cancel" |
| Confirm | `bulk.deleteDialog.confirm` — **"Delete 12 records"**, `bg-destructive text-destructive-foreground hover:bg-destructive/90`, with `Loader2 animate-spin` while in flight and `event.preventDefault()` on the click so Radix does not close the dialog mid-request |

**The dialog names both the count and the retention window** (locked in `38-CONTEXT.md`: count-aware,
with the *live* window read from trash settings, not a copy of the singular `DeleteDialog` string).
`retentionDays: number | null` must therefore reach each list's client component as a prop from its
server page — a new prop on all four surfaces; see § Assumptions.

**`descriptionNoRetention` is a separate string, not a `{days}` default.** `readRetentionDays` fails
closed (Phase 37): when `trash.retention_days` is unset or unparseable, nothing is purged
automatically. A dialog promising "30 days" on a deployment with no configured window would be the UI
lying about its own configuration — the exact reason `trash.empty.bodyNoRetention` exists.

**No type-the-count confirmation, no "type DELETE".** No precedent in this repo, and the action is
*reversible* — every record lands in Trash and SC-2 requires it. A friction gate proportionate to an
irreversible purge would be theatre here, and it would train users to click through the one dialog
(Phase 37's purge) where the friction is warranted.

**The dialog closes on confirm.** Progress, results and failures are reported by the toast and by
Surface 7, both of which outlive the dialog. Keeping it open to host a failure list would trap focus
in a modal the user must dismiss before retrying.

### The owner picker — a flagged deviation from `38-CONTEXT.md`

`38-CONTEXT.md` states the picker "reuses `src/components/ui/entity-combobox.tsx` over active users
rather than introducing a new member-picker component."

**`EntityCombobox` cannot address users, and widening it would be a schema change.** Verified
2026-08-17: it takes `entityType: EntityType` and calls `searchEntities(entityType, query)`
(`src/lib/fetch-entities.ts`), whose `switch` has exactly four arms — `organization`, `person`,
`deal`, `activity`. `EntityType` is declared once in `src/db/schema/custom-fields.ts:19` and is
imported by `audit-log.ts` (which widens it by one literal for a **persisted** column),
`notes.ts` (a persisted column) and `src/lib/timeline/assemble.ts`'s `assertEntityType`. Adding
`"user"` to it would push a non-CRM literal into two persisted contracts and one runtime validator.

**Resolution — the vendored `Select`, which honours the decision's actual intent (no new
member-picker component) at zero cost:** (auto-accepted recommended, autonomous mode)

- It is the **established owner-picking idiom of this product**, on three of the four surfaces
  already: `deals/deal-dialog.tsx:412-424` (Owner), `activities/activity-dialog.tsx:456-468`
  (Assignee), and `deals/deal-filters.tsx` (the owner filter). Reusing it means a user sets `ownerId`
  the same way in bulk as they do singly.
- **Zero new components, zero new dependencies** — the letter of the decision's purpose.
- **Measured, not assumed:** the live database has **1** user with `deleted_at IS NULL AND
  status = 'approved'` (`docker compose exec postgres psql`, 2026-08-17). A search-and-filter
  combobox over one option would be absurd.
- If a deployment ever exceeds ~30 active users, switch to the `Popover` + `Command` shape already
  vendored as `src/components/assignee-picker.tsx`, in single-select mode. That is also zero new
  components. Do **not** reach for `EntityCombobox`.

**Nothing behavioural changes:** still single-select, still scoped to active users, still `ownerId`,
still no new picker component. Only the primitive differs, and the primitive named in CONTEXT is
unimplementable.

### Population: "active users" means `deleted_at IS NULL` **and** `status = 'approved'`

`deals/page.tsx:159-163` currently filters on `deletedAt` alone, so it can offer a
`pending_verification` or `rejected` user as a deal owner. **This phase's picker must filter on both**
— assigning 100 records to a user who has not verified their email, or who was rejected, is a data
defect that no per-record failure would report because the write succeeds. Do not "fix"
`deals/page.tsx` here; that is unrelated scope. Just do not copy its predicate.

`organizations/page.tsx` and `people/page.tsx` do **not** currently fetch users at all, so both need
a new `owners: { id: string; name: string }[]` prop; see § Assumptions.

### The no-email notice is required copy, not a nicety

`38-CONTEXT.md` locks: **no email is sent on bulk reassign** (a per-record notification would emit up
to 100 emails from one click; a digest is deferred). The single reassign path *does* email a new
assignee. So a user who has been trained by the product to expect a notification would reasonably
assume one here. `bulk.reassignDialog.noEmailNotice` — *"The new owner isn't emailed about this
change."* — is the honest statement, in Meta 12/400 muted directly under the field. This is
`37-UI-SPEC.md`'s "copy never promises what the system will not do" rule, applied to a promise the
rest of the product does keep.

**Confirm is disabled until an owner is chosen.** There is no "unassign" option: `ownerId` is how
every list scopes visibility, and a bulk unassign would make 100 records unreachable from the surface
the user is standing on.

## Surface 6 — Scoped CSV export

**No dialog. No format picker. No options.** One button, one round trip, one file.
(auto-accepted recommended, autonomous mode — a dialog to confirm a non-destructive, no-side-effect
read is friction with nothing to prevent, and CSV-only is locked)

| Step | Behaviour |
|------|-----------|
| Click `Export CSV` | Bar controls disable; the button shows `Loader2 animate-spin` + `bulk.exporting` ("Preparing CSV…") |
| Server action | Receives `selectedIds`, reuses `fetchFilteredData` + the `formatters.ts` flatteners + `deriveCsvColumns`, returns the existing `ExportResult` shape: `{ success: true, data, filename, count }` |
| Download | `new Blob([data], { type: "text/csv" })` → `URL.createObjectURL` → a synthetic `<a download>` → `revokeObjectURL`. **Reuse the existing `downloadFile` helper pattern in `src/app/admin/export/export-form.tsx:31-38`** — do not write a third copy |
| Success | `toast.success(t('exported', { count }))`. **A toast is required here**: the file leaves the browser and nothing in the page changes, so there is no visible result for Phase 35's "no toast where the result is visible" rule to apply to |
| Failure | `toast.error(t('error.exportFailed'))`. Selection is **preserved** — the user's next act is to retry |
| Selection after success | **Cleared**, like every other successful bulk action (locked). An export is complete; leaving 12 rows checked invites a second identical download |

**Filename: `{entity}-selected-{count}-{YYYY-MM-DD}.csv`** (locked). Two hard rules:

- **The filename is never translated.** `{entity}` is the English slug (`organizations`, `people`,
  `deals`, `activities`), not `nav.*`. A locale-dependent filename on disk is unsupportable, and
  es-ES / pt-BR names carry diacritics that survive round trips poorly.
- **It is generated server-side**, inside the `ExportResult` the action already returns, so the name
  and the row count cannot disagree.

**Custom-field columns survive** because `deriveCsvColumns` unions keys across every row
(`src/lib/export/csv-columns.ts`, closed by 34-13 and verified live on a 38,345-row export). The
STATE.md note about dropped `custom_*` columns describes pre-34-13 behaviour; do not re-derive
headers from row 1.

**The Pipedrive variant (`src/lib/export/pipedrive.ts`) is not offered** (locked). No format `Select`
appears in the bar, and no copy implies one exists.

## Surface 7 — The per-record failure report

SC-3: *"any per-record failure is named rather than silently swallowed."* Deletion and reassignment
are **per-record and sequential, best-effort — not one all-or-nothing transaction** (locked, precisely
because an aborting transaction structurally cannot name a per-record failure).

Partial failure surfaces **twice** (locked):

### 1. The toast summary

`toast.warning(t('partial', { succeeded, total, failed }))` — *"9 of 12 succeeded. 3 failed."*
`warning`, not `error`: nine records really did change, and calling that an error misdescribes the
outcome. Sonner 2.0.7 supports `toast.warning` and owns its own icon and live region.

### 2. The inline report

An `Alert variant="destructive"` inserted **directly above the table or board, below the search /
filter row** — at the top, because this is a report to read, not a control to press, and it can run to
several lines. It is emphatically **not** put inside the fixed bar, which must stay a single compact
control cluster at every viewport.
(placement + layout: auto-accepted recommended, autonomous mode — this was Claude's discretion)

```
<Alert variant="destructive" class="mb-4">          ← role="alert" comes from the primitive
  <AlertCircle class="h-4 w-4" aria-hidden />
  <AlertTitle class="font-semibold">               {t('failures.deleteTitle', {count})}
  <AlertDescription>
    <ul class="mt-2 max-h-48 space-y-1 overflow-y-auto text-sm">
      <li class="flex flex-wrap items-baseline gap-1">
        <span>{record.name}</span>
        <span class="text-muted-foreground text-xs">— {t(`reason.${record.reason}`)}</span>
      </li>
      …
    </ul>
    <p class="text-muted-foreground mt-2 text-xs">{t('failures.retryHint')}</p>
  </AlertDescription>
  <Button variant="ghost" size="sm" class="absolute right-2 top-2">   {t('failures.dismiss')}
</Alert>
```

- **Every failure is named. There is no "and 3 more".** SC-3 says *named*, and a cap is exactly the
  swallowing it forbids. Height is bounded by `max-h-48 overflow-y-auto` (192px ≈ 8 rows) instead —
  the list scrolls, the page does not grow, and nothing is hidden from a screen reader, which reads
  the whole `<ul>` regardless of the scroll box.
- **Each failure carries a reason from a closed set**, so the report never renders a raw server
  string: `bulk.reason.notFound`, `.notPermitted`, `.alreadyDeleted`, `.unknown`. The server actions
  must return a discriminated reason code per failed id, not a message.
- **Failed records stay selected; succeeded records are deselected** (locked). So after a partial
  failure the bar reads "3 selected" and the retry is the same button — no re-picking. The
  `loadedIds` intersection in Surface 1 is what guarantees the count is 3 and not 12 after the server
  tree re-renders without the nine deleted rows.
- **Dismissed by the `Dismiss` button, or replaced by the next bulk action's result, or cleared when
  the selection is cleared.** It does not auto-dismiss on a timer: a list of records that failed is
  the one thing on this surface a user may need to copy down.
- **Total failure is a toast, not this panel.** When *zero* records succeeded (an over-cap rejection,
  an auth failure, a dead connection) the cause is one thing, not N things:
  `toast.error(t('error.deleteFailed'))` and no inline report. A twelve-item list all reading
  "Couldn't be saved" is noise.

### Destructive confirmations

| Action | Trigger | Confirm label |
|--------|---------|---------------|
| Bulk soft-delete N records | `Delete` in the bar | **Delete {N} records** |

That is the phase's only destructive action. **Bulk reassign gets no `AlertDialog`** — it is fully

(SC-5), and gating a reversible write behind a second modal after the user already opened a dialog and
picked an owner is friction with nothing to prevent. **Bulk export destroys nothing** and gets no
confirmation either.

### Copy rules for this phase (inherited from Phases 35-37, restated because they bind here)

- **No generic CTA labels.** Every button names its object *and its count* where a count exists:
  "Delete 12 records", "Reassign 12 records", "Keep records", "Keep current owners", "Clear
  selection", "Export CSV". A bare "Save", "Cancel", "Confirm", "OK", "Yes", "Apply" or "Delete" is
  forbidden in these surfaces, **including inside both dialogs**. (The bar's `Delete` is the single
  exception, and it is admissible only because it *opens* the dialog where the count is stated — the
  irreversible-looking word never appears next to a number the user has not read.)
- **Every count is an ICU plural, never `{count} record(s)` and never string concatenation.** es-ES
  and pt-BR both inflect, and this phase's copy is almost entirely counts.
- No exclamation marks. No "Oops". No standalone "Something went wrong" — every error names the
  failed action and the next step.
- **Copy is factual, never editorial.** "3 records weren't deleted", not "Uh oh, some records had
  problems". "No longer exists", not "mysteriously vanished".
- **Copy never promises what the system will not do.** Hence `descriptionNoRetention`, hence
  `noEmailNotice`, hence the absence of any "select all matching" wording.
- **No success toast where the result is visible** — with three declared exceptions, each argued
  above: bulk delete (rows vanishing is ambiguous between deleted / filtered / failed, and SC-2
  needs Trash named), bulk reassign (the owner column is not even rendered on Activities or the
  kanban, so the result is invisible on 2 of 4 surfaces), and export (the result leaves the browser).

## Interaction Contract

**Selection**

| Trigger | Behaviour |
|---------|-----------|
| Click a row checkbox | Toggles that row only. Does not open the record, does not expand a card, does not start a drag, does not sort |
| Click the header checkbox | Selects / deselects every **loaded** row (Activities: every **filtered** row). Indeterminate when some but not all are selected |
| Click a stage-header checkbox | Selects / deselects every deal rendered in that stage column |
| `Load More` | Selection **persists** — the rows array is cumulative and `getRowId` is the record id |
| Search / filter change | Selection **cleared**. See the effect contract below |
| Pipeline change on `/deals` | Selection **cleared** — the previously selected deals are no longer on screen |
| Any successful bulk action | Succeeded ids deselected; failed ids **stay** selected |
| `Clear selection` | Selection emptied; the bar and the failure report unmount |
| `Escape` while the bar is visible and no dialog is open | Clears the selection |
| Nothing selected | The bar is **absent** from the DOM, along with its `h-20` spacer. No reserved strip, no ghost bar |

**The clear-on-filter-change reset must be keyed on the filter STRING, never on the `data` array.**

> **CORRECTED during execution of plan 38-15.** This spec originally wrote the reset as
> `useEffect(() => { setRowSelection({}) }, [search])`, and that exact code is a **lint ERROR** in this
> repo — `react-hooks/set-state-in-effect`, "Avoid calling setState() directly within an effect",
> proven with a throwaway probe rather than assumed. Following it literally would have failed the
> plan's own "lint 0 errors" gate, and the three existing suppressions of that rule in this codebase
> are all logged as deferrals, so a fourth was not acceptable. Plan 38-08 hit the same rule
> independently on the dialog's owner reset.
>
> Use React's documented adjust-state-on-prop-change pattern instead — there is **no effect at all**:
>
> ```ts
> const [prevSearch, setPrevSearch] = useState(search)
> if (prevSearch !== search) {
>   setPrevSearch(search)
>   setRowSelection({})
> }
> ```
>
> This is also marginally stronger than the effect: the reset lands in the same render that first sees
> the new search, rather than one render later. **Consequence for any gate:** do NOT assert that a
> `useEffect` exists in these files — it cannot. Assert the contract instead (`data` absent from any
> clear-on-filter position).

Phase 35 measured that `revalidatePath` **re-renders the current client tree regardless of the path
argument** (Next 16.1.6), and every bulk server action calls it. An effect keyed on `data` would
therefore fire in the middle of a bulk action's own revalidation and wipe the failed-record selection
this contract requires to survive. Succeeded ids are removed **explicitly in the action handler**, not
by an effect.

**Existing keyboard shortcuts are untouched, and no bulk shortcut is added.**
`useDataTableKeyboard` binds bare `j`/`k`/`Enter`/`e`/`d`/`n`. `d` opens the **single-record** delete
dialog for the keyboard-cursor row and continues to do so while a bulk selection exists — a
deliberate non-change: silently repurposing `d` to mean "delete 12 records" would be the most
dangerous thing this phase could ship. **Do not bind `d`, `x`, `Delete`, `Backspace` or any letter to
a bulk action.** `Escape` to clear is the only new binding, and `useDataTableKeyboard` does not bind
`Escape`, so there is no collision. When a dialog is open, Radix owns `Escape`.

**Bulk delete**

| Trigger | Behaviour |
|---------|-----------|
| `Delete` in the bar | Opens the `AlertDialog`. Nothing is sent |
| Confirm | `event.preventDefault()` keeps the dialog open while in flight; the confirm button shows `Loader2` + "Deleting…"; `Keep records` is disabled during the request |
| All succeeded | Dialog closes; rows leave (the action's `revalidatePath` re-renders the tree); selection emptied; `toast.success(bulk.deleted)` with an **Open Trash** action |
| Partial | Dialog closes; succeeded rows leave; failed rows stay selected; `toast.warning(bulk.partial)`; the inline report renders |
| None succeeded | Dialog closes; `toast.error(bulk.error.deleteFailed)`; selection intact; **no** inline report |
| Over the cap | The `Delete` button was already disabled. If the server still rejects, `toast.error(bulk.error.tooMany)` |
| `Escape` / `Keep records` / overlay click | Closes; nothing sent; nothing deleted |
| Focus after close | Returns to the bar's `Delete` button via Radix's own focus restoration — **unless the bar unmounted** (all succeeded), in which case focus moves to the table wrapper `<div tabIndex={-1}>` that `containerProps` already provides. Focus must never be dropped to `<body>`; same rule `37-UI-SPEC.md` sets after a row is removed |

**Bulk reassign**

| Trigger | Behaviour |
|---------|-----------|
| `Reassign owner` | Opens the `Dialog`. The `Select` is empty; Confirm is disabled |
| Choose an owner | Confirm enables, labelled with the count |
| Confirm | Dialog stays open with `Loader2` + "Reassigning…"; `Keep current owners` disabled |
| All succeeded | Dialog closes; selection emptied; `toast.success(bulk.reassigned)` naming the new owner |
| Partial | Dialog closes; failed ids stay selected; `toast.warning`; inline report with `failures.reassignTitle` |
| None succeeded | Dialog closes; `toast.error(bulk.error.reassignFailed)`; selection intact |
| `Escape` / `Keep current owners` / overlay | Closes; nothing sent; the chosen owner is discarded |

**Bulk export** — see § Surface 6. No dialog; disable → spinner → download → toast → clear.

**First paint** is server-rendered, exactly as today. This phase adds no skeleton, no spinner on
initial load, and no client-side fetch on mount. The bar cannot exist at first paint because
`rowSelection` starts empty.

## Accessibility Contract

- **Every checkbox is a real Radix `Checkbox`**, so `role="checkbox"`, `aria-checked`
  (`true` / `false` / `mixed`) and keyboard Space all come for free. The header and stage-header
  checkboxes announce `mixed` when partially selected — which is *why* the visual indeterminate fix
  in § Surface 1 matters: sighted users must get the same information the accessibility tree already
  carries.
- **Every checkbox's accessible name identifies its record**, via `aria-label` — "Select Acme Ltda",
  not "Select row". The select-all names its scope and count — "Select all 50 loaded records",
  "Select all 7 deals in Negotiation".
- **The bar is a landmark:** `role="region"` with an `aria-label` that states the count, so a screen
  reader user can jump to it and knows what it acts on before reading a single button.
- **Every bar control has a visible text label.** No icon-only buttons anywhere in this phase. No
  tooltip primitive is vendored, so a label is the only reachable accessible name — and this is also
  the rule `37-UI-SPEC.md` sets for its row actions.
- **The failure report is `role="alert"`**, from the `alert.tsx` primitive, so a partial failure is
  announced without a bespoke live region. The reason text is real text, never a colour and never an
  icon alone.
- **Result announcements ride Sonner's live region.** No new `aria-live` region is added on any
  surface.
- **Colour is never the sole carrier.** Selection is carried by `aria-checked` + a filled checkbox +
  a stated count. The destructive action is red *and* says "Delete", and its dialog says
  "Delete 12 records". A user who cannot distinguish the colours reads different words and a number.
- **Both dialogs are Radix** — focus trap, `Escape`, and focus restoration come from the primitives.
  The reassign `Select`'s trigger has a visible `<Label htmlFor="bulk-owner">`; a placeholder is never
  a label.
- **Focus is moved deliberately whenever the bar unmounts.** A full-success delete destroys the
  focused button; focus moves to the table's existing `containerProps` wrapper (`tabIndex={-1}`),
  never dropped to `<body>`. Same rule Phase 37 sets for a removed row.
- **The deal card's checkbox stops `keydown` propagation**, which is what makes it operable at all —
  without it, Space is consumed by dnd-kit's `KeyboardSensor` and a keyboard user cannot select a
  deal. This is an accessibility requirement, not an optimisation.
- Focus rings are inherited from `globals.css` `:focus-visible`. Do not add per-component focus
  styling and do not set `outline: none` anywhere in this phase.
- Contrast: everything uses `foreground` / `muted-foreground` / `destructive` on `card` /
  `background` / `muted` — already-audited pairs. The one new surface tint, `bg-primary/5`, carries no
  text of its own (the card's existing `text-foreground` and `text-muted-foreground` sit on it, and
  a 5% tint of `oklch(0.205 0 0)` moves the background from `oklch(1 0 0)` to ≈`oklch(0.96 0 0)` —
  inside the range `bg-muted` already ships against the same foregrounds). No new hue enters the
  product, so no new contrast risk.

   filtered `deleted_at IS NULL AND status = 'approved'`). Neither fetches users today. Deals and
   Activities already pass a users array and only need the `status` predicate added for **this
   phase's** list — do not change theirs.
3. **`ExportFilters` needs an `ids?: string[]`.** `src/lib/export/types.ts` currently exposes only
   `stage` / `owner` / `dateFrom` / `dateTo`, and every `fetch*` in `formatters.ts` must honour the
   new field. `ExportResult` already returns `{ success, data, filename, count }`, so no return-shape
   change is needed. If `ids` cannot be threaded, the scoped export must **fail with
   `bulk.error.exportFailed`** rather than silently export the whole table — SC-4 is "not the whole
   table".
4. **The bulk server actions return a per-id discriminated failure reason**, mapping onto exactly
   `notFound` / `notPermitted` / `alreadyDeleted` / `unknown`, plus the record's display name for the
   report. A raw server message string cannot be rendered — it is untranslatable and may leak
   internals. If the mutation layer cannot distinguish the cases, collapse to `unknown` **in the
   plan, in writing** — do not map a permission failure onto "try again".
5. **The additive `checkbox.tsx` patch is behaviour-neutral.** Verified by reading all **10** importing
   modules on 2026-08-17: none passes `indeterminate`, and `grep -rn "indeterminate" src/` is 0
   repo-wide. If an eleventh consumer appears before this phase lands, re-check it rather than
   assuming. (Count corrected from 8 during plan 38-05 — two single-quote imports under
   `admin/fields/[entityType]/` were missing from the original census; see § Surface 1.)
6. **`toast.warning` is available** on the installed `sonner@2.0.7` and the app's `Toaster` does not
   suppress it. If the wrapper turns out to restrict variants, use `toast.error` for the partial case
   and keep `bulk.partial`'s wording unchanged — the wording, not the severity, is the contract.
7. **`Load More` keeps the rows array cumulative.** Verified in `organizations/page.tsx:19-51`
   (`limit = PAGE_SIZE * pageNum + 1`, sliced to `PAGE_SIZE * pageNum`). If any surface ever switches
   to true per-page fetching, "selection persists across Load More" becomes false and the header
   select-all's scope changes with it — that would need a new decision, not a silent behaviour change.
