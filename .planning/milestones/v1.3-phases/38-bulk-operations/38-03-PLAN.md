<objective>
Add `updateDealOwnerMutation` and `updateActivityOwnerMutation`, and gate the deal one against the
latent `deal_assignees` data-loss bug.

Purpose: `updateDealMutation(id, { ownerId }, userId)` unconditionally destroys every
`deal_assignees` row for that deal. `updateDealSchema = dealSchema.partial()` and `.partial()` does
NOT remove `assigneeIds`' `.default([])` (verified by executable Zod 4.3.6 probe in 38-RESEARCH
Pitfall 2), so `safeParse({ ownerId })` yields `{ assigneeIds: [], ownerId }` and `deals.ts:406`
runs `db.delete(dealAssignees)` before deciding what to re-insert. The loss is unaudited because
assignees live in a join table and never appear in the diffed deal row. Blast radius today is zero
(`deal_assignees` has 0 rows, verified live) but the bug is real and the fix is free.
Activities has the same Zod-strip problem as organizations and people: `activitySchema` does not
declare `ownerId`.
Output: two narrow mutations, their unit coverage, and a `db.delete`-never-called regression gate.
</objective>

| deal row → deal_assignees join table | A partial write to the deal can silently destroy join rows that never appear in the audited diff |
