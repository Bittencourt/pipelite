| Role | Size | Weight | Line Height | Class | Where in this phase |
|------|------|--------|-------------|-------|---------------------|
| Display | 24px | 700 | 1.2 | `text-2xl font-bold` | run-detail `<h1>` — **existing, unchanged** (`page.tsx:141`) |
| Heading | 18px | 600 | 1.25 | `text-lg font-semibold leading-tight` | the two new `DialogTitle`s — **`leading-tight` is mandatory**, see below |
| Body | 14px | 400 | 1.43 | `text-sm` | `DialogDescription`; the prefilled/empty hints; the lineage line; the notification row `Label`; the invalid-JSON error |
| Label | 12px | 400 | 1.33 | `text-xs` | the dry-run `Badge` text (baked into `badgeVariants`); the toolbar's disabled-reason hint |
| JSON (family, not a size) | inherits `text-base md:text-sm` | 400 | 1.43 | `font-mono` | the dry-run `Textarea`. **Do not add a size class.** `textarea.tsx:12` keeps 16px below `md` deliberately so iOS does not zoom the whole editor on focus; `text-xs` here would reintroduce that. `json-viewer.tsx:33` may use `text-xs` because a `<pre>` is never focused. |

**`leading-none` override — mandatory, and this is a measurement not a preference.** `DialogTitle`
ships `leading-none` (`dialog.tsx:149`). At 320px a `DialogContent` gives 240px of content. In
`text-lg` (18px), *"¿Repetir esta ejecución?"* (es-ES) and *"Executar este fluxo como teste"*
(pt-BR) both wrap to two lines at that width, and `leading-none` collides the descenders of line 1
with the ascenders of line 2. Both new titles therefore carry `className="leading-tight"`. This is
the same rule Phase 45 wrote for `SheetTitle` (`45-UI-SPEC.md` § Typography, "Forbidden").

**Weight exceptions (pre-existing, documented, not introduced here):**

- `font-medium` (500) is baked into `buttonVariants`' base class (`button.tsx:9`) and into `Label`
  (`label.tsx:17`). Every new button and every new label inherits 500.
- `font-bold` (700) on the existing run-detail `<h1>`. Untouched.

This phase adds no new 500- or 700-weight text of its own and changes no existing weight.

**Forbidden in this phase:** any font size outside {12, 14, 18, 24}; `leading-none` on any text
that can wrap; any `font-semibold` on body-size copy (the notification `Label` already carries
`font-medium` from the primitive plus the row's own `font-medium` — copy the existing row byte for
byte rather than restyling it).

### Zero new palette colours — C-41-1

**Rule: the six files this phase touches must contain zero new hardcoded Tailwind palette
utilities.** Every colour above is a semantic token, so every one works in both themes without a
`dark:` pair.

This is not a general repo claim — `run-status-badge.tsx:12,22,26` already ships
`bg-emerald-100 … dark:bg-emerald-950`-style pairs, and Phase 45 declared the repo-wide token sweep
out of scope. The rule is narrow and enforceable: **the new code adds none.**

### The dry-run badge is `border-dashed`, not a colour — C-41-2 **[researcher decision]**

```tsx
<Badge variant="outline" className="border-dashed">{t("dryRun.badge")}</Badge>
```

CONTEXT requires a persisted dry run to be visually distinguishable — without it, a dry run looks
like a real run whose changed-records panel is inexplicably empty, which turns criterion 2's proof
into an apparent bug report. Three options were considered:

- A new colour pair (e.g. violet) — would violate C-41-1 and add the seventh palette pair to a file
  that already has six.
- `variant="secondary"` — already taken by `pending` in `run-status-badge.tsx:29`.
- **`variant="outline"` + `border-dashed`** — chosen. A dashed border is the app's *existing* idiom
  for "provisional / not real content": `runs-table.tsx:36` renders its empty state in
  `rounded-lg border border-dashed`. It is token-only, so it is theme-correct for free, and it is
  distinguishable from `skipped` (also `outline`) by border style rather than by hue — which also
  means it survives a monochrome or high-contrast display.

The badge is an **orthogonal dimension** to run status, so it lives in its own component and renders
*beside* `RunStatusBadge`, never instead of it. `run-status-badge.tsx` is not modified; its
`Record<Status, …>` map is exhaustive-by-type on purpose (see its own comment) and `dryRun` is not a
status.

### Consequential, not destructive — the two confirm dialogs

Both new actions get a confirmation, and neither gets destructive styling. The distinction is
deliberate and the checker should enforce both halves:

- **Confirmation is required for Replay** because a replay is a fresh run from node 1, not a resume.
  Every step that already *succeeded* before the failure runs again — so its emails send again, its
  HTTP calls fire again, and its CRM writes repeat. An operator clicking a button labelled "Replay"
  on a failed run does not necessarily expect to duplicate the successful half of it. The
  confirmation body says exactly that; it is the most important string in this phase.
  The existing `admin.webhooks.replay` control has no confirmation, correctly: one delivery *is*
  one attempt, so replaying it duplicates nothing.
- **Confirmation is required for Dry run** implicitly — the dialog *is* the confirmation, because it
  is also the JSON editor. No second step.
- **Neither uses `AlertDialog` and neither uses `variant="destructive"`.** Follow
  `delete-workflow-dialog.tsx`'s shape (plain `Dialog` + `DialogFooter` + outline Cancel) but **omit
  its `AlertTriangle` in a `bg-destructive/10` tile** — that tile is what marks the delete dialog as
  destructive, and copying it would tell the operator that replaying a run is dangerous. Replay's
  dialog carries **no icon**.

### Forbidden copy — F-41-1

**Do not add any string that asserts the dry run mutated nothing.** No *"No records were changed."*,
no *"Nothing happened."*, no reassuring banner, no green tick panel.

`41-CONTEXT.md` § Specific Ideas, verbatim: *"The dry run's proof of non-mutation should be the
existing changed-records panel reading empty, not a new 'nothing happened' message. An empty list
that is normally populated is evidence; a reassuring sentence is not."*

The proof is `run-changed-records.tsx` rendering its **existing** `audit.run.empty` state — the same
state that would appear for a real run that happened to change nothing. That equivalence is the
point: the panel is not a dry-run feature, it is a general instrument, and an instrument reading zero
is evidence in a way a special-case sentence is not.

Note for the checker: `audit.run.empty` *is* a sentence, and it is **not** a violation of this rule —
it is the pre-existing general string, unchanged, not a new dry-run-specific reassurance. The
distinction the rule draws is authorship, not grammar.

Also forbidden: any copy in the dry-run dialog promising that the run *will* prove non-mutation.
`workflows.dryRun.description` states what is *simulated* (a factual property of the execution), not
what the operator will conclude.

### ICU and placeholder rules — L-41-1

- **Exactly one interpolation in this phase:** `{runId}` in `workflows.replay.lineage`. It is a
  plain placeholder, covered by the existing placeholder gate
  (`locale-parity.test.ts:1138`, regex `/\{[a-zA-Z0-9_]+\}/g`). All three locales must keep it.
- **No ICU plurals.** Nothing is added to `ICU_PLURAL_KEYS` (`locale-parity.test.ts:929-938`).

  `dryRun.notAnObject` says *"a JSON object with named fields"* rather than showing `{…}` syntax.
  The `{}` fallback the textarea prefills with is **code**, not copy.

## i18n Scope — the declared seam

**New strings in the `/workflows` tree are translated; existing English literals there are left
alone.** This is not an inconsistency introduced here — it is the seam
`run-changed-records.tsx:15-22` already declared and documented:

> *"The `/workflows` tree has zero `next-intl` call sites today and its strings are English
> literals. This section is translated anyway: three locales ship, `locale-parity.test.ts` makes
> translated keys the enforced default, and writing new untranslated English would propagate the
> debt. […] That seam is the trade; it is NOT to be 'fixed' by translating the rest of the run page,
> which is unrelated scope."*

Consequences the checker must accept rather than flag:

- The run-detail page will show a translated Replay button and lineage line next to an English
  *"Back to Runs"*, *"Started"*, *"Duration:"* and *"Failed at:"*.
- The editor toolbar will show a translated *Test run* next to English *Export JSON*, *Import JSON*
  and *Save*.
- The runs list will show a translated *Show test runs* next to an English *All statuses* Select.
- `RunStatusBadge`'s labels stay English. `DryRunBadge`'s label is translated. Yes, they sit side by
  side.

**Do not translate the rest of the tree in this phase**, and do not add an English literal either.
The rule is: every string *this phase authors* goes through `useTranslations` / `getTranslations`.

## Interaction Contract

### 1. Replay (WFOPS-01)

**Visibility.** The Replay button renders **only** when `run.status === "failed"`. CONTEXT:
*"Cancelled and completed runs get no replay control."* Not disabled — absent. A disabled button on
every completed run is noise on a page that has no other action.

**Placement.** In the run-detail header, in a right-hand cluster opposite the title/badge cluster.
See R-1.

**Trigger.** `<Button size="sm" variant="outline">` + `<RotateCcw className="h-3 w-3 mr-1" />` +
`t("replay.action")` — byte-identical shape to `delivery-table.tsx:108-116`.

**Flow.**

| Step | State |
|------|-------|
| Click | opens the confirm `Dialog` |
| Dialog | `DialogTitle` `replay.confirmTitle` (with `leading-tight`), `DialogDescription` `replay.confirmBody`, **no icon**, `DialogFooter`: outline `common.cancel` + default `replay.confirmAction` |
| Confirm pending | both footer buttons `disabled`; the confirm button shows `<Loader2 className="mr-2 h-4 w-4 animate-spin" />` + `replay.pending` (the `delete-workflow-dialog.tsx:56` pattern) |
| Success | dialog closes, `toast.success(t("replay.success"))`, navigate to the **new** run's detail page |
| Failure | dialog stays open, buttons re-enable, `toast.error(t("replay.error"))` |

Navigating to the new run rather than staying put is what makes criterion 1 observable — the criterion
is *"gets a new run with its own step history"*, and the operator has to be able to see it. The new
run is `pending` with no steps at that instant; that is honest and the status badge says so.

**Lineage line.** When `run.replayedFromRunId` is set, the run-detail metadata row gains a third
item: `t("replay.lineage", { runId })` where `runId` is the origin's first 8 characters, rendered as
a `Link` to `/workflows/{id}/runs/{replayedFromRunId}`. Same `text-sm text-muted-foreground` as its
two siblings. **[researcher decision]** — CONTEXT adds the column so *"a replay-of-a-replay loop"*
is diagnosable; without a rendered link it is diagnosable only by SQL, and `depth` is reset to 0 so
the recursion guard cannot see the chain either. One direction only: **no** *"replayed as …"*
back-link on the origin run, which would need a reverse query and a list (a chain can fan out) for
no criterion.

### 2. Dry run (WFOPS-02)

**Placement: a `Dialog` opened from the toolbar. Not the side panel. [researcher decision —
discretion item 3.]** CONTEXT explicitly left this open ("toolbar vs side panel"). The toolbar wins
on three measured grounds:

1. `side-panel.tsx:100` is `w-[400px]` — a hard fixed width that already overflows a 320px viewport.
   Putting the JSON editor there inherits that defect. `DialogContent` is
   `max-w-[calc(100%-2rem)] sm:max-w-lg` and is 320-safe by construction.
2. The side panel is single-slot and owned by node selection (`selectedNodeId` + `panelMode`,
   `side-panel.tsx:73-75`). A third `panelMode` would couple "test the whole workflow" to "a node is
   selected", and opening the dry run would deselect the node the user was configuring.
3. The interaction shape is *edit-then-confirm-then-wait*, which is a modal. The side panel has no
   confirm affordance; its only footer button is Delete Node.

**Trigger.** In the toolbar's right cluster, immediately **left of** Save:
`<Button size="sm" variant="outline">` + `<FlaskConical className="mr-1 h-4 w-4" />` +
`t("dryRun.action")`. `FlaskConical` over `Play` deliberately — `Play` reads as "run for real", which
is the one thing this button does not do.

**Disabled while dirty. [researcher decision]** A dry run executes the **persisted** workflow (the
engine loads by `workflowId`), so with unsaved edits on screen the test would silently exercise the
old definition and report on something the operator is not looking at. The button is therefore
`disabled={dirty}` and carries `title={t("dryRun.dirtyHint")}` plus an `aria-describedby` pointing at
a `text-xs text-muted-foreground` node rendering the same string — a `title` alone is invisible to
touch and to screen readers that do not announce it. The toolbar already renders an *"Unsaved
changes"* marker in this cluster, so the state is not a surprise.

**Dialog contents, top to bottom.**

| Element | Spec |
|---------|------|
| `DialogTitle` | `dryRun.title`, `className="leading-tight"` |
| `DialogDescription` | `dryRun.description` |
| `Label` | `dryRun.triggerDataLabel`, `htmlFor="dry-run-trigger-data"` |
| `Textarea` | `id="dry-run-trigger-data"`, `className="font-mono min-h-[160px] max-h-[320px] overflow-y-auto"`, `spellCheck={false}`, `autoComplete="off"`. **No font-size class.** Prefilled with `JSON.stringify(latestTriggerData, null, 2)`, or the two characters `{}` when the workflow has no prior run (CONTEXT: *"A workflow with no prior runs falls back to an empty object"*). |
| Hint | `text-sm text-muted-foreground` — `dryRun.prefilledHint` when prefilled, `dryRun.emptyHint` when not. Exactly one of the two, never both. |
| Error | `text-sm text-destructive` with `role="alert"`, rendered only while invalid. The `Textarea` gains `aria-invalid="true"` and `aria-describedby` pointing at it. Text-only — **no fill, no `Alert` component, no border colour change**, matching how `step-detail.tsx` expresses errors in this tree. |
| `DialogFooter` | outline `common.cancel` + default `dryRun.submit` |

**Validation.** On submit (not on every keystroke — per-keystroke red text while someone is halfway
through typing an object is hostile). Two distinct failures, two distinct strings:
`JSON.parse` throws → `dryRun.invalidJson`; parses to a non-object (array, string, number, `null`)
→ `dryRun.notAnObject`. Submit stays enabled so the operator can retry after editing.

**The dialog owns the wait. [researcher decision]** A dry run is persisted as a `pending`
`workflow_runs` row that the execution processor claims asynchronously (CONTEXT). The run-detail page
is a server component with no polling, so navigating immediately would land the operator on an empty
pending run they must reload by hand — and criterion 2 requires them to *see per-node output* and
*confirm no CRM record changed*, both of which need a finished run.

| State | Spec |
|-------|------|
| Submitting / running | footer buttons `disabled`; confirm shows `<Loader2 className="mr-2 h-4 w-4 animate-spin" />` + `dryRun.running`; the `Textarea` becomes `readOnly` (not `disabled` — `disabled` drops it to `opacity-50` and the operator loses sight of what they submitted) |
| Run reaches `completed` or `failed` | dialog closes, navigate to `/workflows/{id}/runs/{newRunId}` |
| 30s elapsed with no terminal status | dialog closes, `toast.info(t("dryRun.timeout"))`, stay in the editor |
| Creation failed | dialog stays open, buttons re-enable, `toast.error(t("dryRun.error"))` |

This confines the async wait to one new client component and leaves `page.tsx`, `run-step-list.tsx`,
`step-detail.tsx` and `json-viewer.tsx` behaviourally untouched — which is what CONTEXT's
*"reuses … unchanged"* requires.

**Landing state.** The dry run's detail page is the existing page, plus the dashed `Test run` badge
beside the status badge, and `run-changed-records.tsx` rendering `audit.run.empty`. Nothing else
changes. That empty panel is the whole proof; see F-41-1.

**Reveal in the runs list.** Dry runs are *"filtered out of the runs list by default"* (CONTEXT) —
`by default` implies a way to see them, and without one a dry run is unreachable once its tab is
closed. A `Checkbox` labelled `dryRun.showInList` sits beside the existing status `Select`, driving a
`?dryRun=1` search param through the same `router.push` mechanism `status-filter.tsx:31-40` already
uses (and, like it, deleting `page`). **[researcher decision]** A `Checkbox` rather than a fifth
`SelectItem`: dry-run-ness is orthogonal to status, and folding it into the status Select would make
"failed" and "test" mutually exclusive when a failed test run is the most interesting row on the
page.

### 3. Failure-alert preference (WFOPS-03)

One additional row in `notification-form.tsx`, **structurally identical** to the three that exist —
same `flex items-start space-x-3`, same `Checkbox` + `div.space-y-1` + `Label.font-medium` +
`p.text-sm.text-muted-foreground`, same `handleToggle` call. `id="workflow-failed"`. No new
component, no new section heading, no divider.

**Position: third of four, before Weekly digest. [researcher decision]** The first two rows are
event alerts ("a deal was assigned", "an activity is due"); a workflow failure is the same kind of
thing. Weekly digest is the only periodic-summary row and reads naturally last. Appending after it
would split the event alerts around the digest.

Nothing else on this surface changes — not the Save button, not the page title, not the subtitle
(*"Choose which email notifications you receive"* already covers a fourth email).

## Responsive Contract — 320px

`e2e/viewport-320.spec.ts` measures 7 routes and **none of them is under `/workflows`**
(`viewport-320.spec.ts:81-89`). The gate does not currently protect these surfaces, which is exactly
why the container changes below are **required rather than advisory** — the defect class Phase 45
found by measurement (non-wrapping toolbars, rows with no scroll container) is live in this tree and
this phase adds a control to two of the offending rows.

**Budget: 241px** of content on `container` pages (305px client width − 64px of
`padding-inline: 2rem`). **240px** inside a `DialogContent`.

| ID | File:line | Current | Required |
|----|-----------|---------|----------|
| **R-1** | `runs/[runId]/page.tsx:145` | `<div className="flex items-center gap-3">` holding `<h1>` + `RunStatusBadge` | Becomes two clusters inside `flex flex-wrap items-center justify-between gap-3`: cluster A = `<h1>` + `RunStatusBadge` + `DryRunBadge`, cluster B = the Replay button. Adding a third and fourth item to a non-wrapping row at 241px overflows with certainty. `justify-between` + `flex-wrap` is the pattern `run-changed-records.tsx:119` already uses for its rows. |
| **R-2** | `runs/[runId]/page.tsx:152` | `<div className="flex items-center gap-4 text-sm text-muted-foreground">` — two items, no wrap | **Add `flex-wrap`.** It gains a third item (the lineage line). This is the exact defect fixed in commit `c082430` — *"wrap the activities stats row — three stats overflow 320px"*. Two items already measure close to 241px in es-ES. |
| **R-3** | `edit/components/toolbar.tsx:146` | `<div className="flex items-center gap-4 border-b px-4 py-2">` — no wrap, holding a `max-w-[300px]` Input, a Switch+Label, and a 4-control right cluster | **Add `flex-wrap`.** Also add **`min-w-0`** to the name `Input` — `max-w-[300px]` caps the maximum but sets no minimum, so the Input refuses to shrink below its intrinsic size and forces the row wide before the wrap can help. The inner right cluster keeps `ml-auto flex items-center gap-2` and gains **`flex-wrap`** too: five `size="sm"` buttons cannot share 241px. |
| **R-4** | `runs/page.tsx:78-82` | `<div className="mb-4">` with one child | Becomes `<div className="mb-4 flex flex-wrap items-center gap-2">` holding the `Select` (`w-[180px]`, fits in 241px) plus the new checkbox+label, which wraps to a second line at 320px. |
| **R-5** | new `dry-run-dialog.tsx` | — | The `Textarea` is already `w-full` and soft-wraps, so long JSON lines cannot widen the dialog. `max-h-[320px] overflow-y-auto` keeps a long envelope from pushing the footer off a `translate-y-[-50%]` dialog. **No horizontal scroll container is needed or permitted here** — a `<textarea>` with `wrap="off"` would create one, so do not set it. |

**Explicitly out of scope, stated so the checker does not flag it:**

- `side-panel.tsx:100` `w-[400px]` — a pre-existing 320px overflow, and the reason the dry-run
  editor is not there. Fixing the side panel is not this phase.
- The runs table's four columns. It already sits inside `Table`'s own
  `overflow-x-auto` (`table.tsx:9-13`), which is the correct treatment: wide content in its own
  scroll container, page body never scrolling. Adding the `DryRunBadge` to the Status cell stacks
  inside the existing `flex flex-col gap-1` (`runs-table.tsx:66`) and adds no width.
- Extending `viewport-320.spec.ts` to `/workflows` routes. The workflow editor is a ReactFlow canvas
  and is not a 320px surface in any meaningful sense; adding it to the matrix would demand a canvas
  redesign this phase has no mandate for. **R-1 through R-5 are asserted by source-scan gates on the
  class strings, not by a new Playwright row.**
