<objective>
Wire the failure alert into the three places a run reaches a terminal failed state, and apply CONTEXT
amendment A3's fix to `processWaitingRuns` so two instances cannot both resume the same delayed run.

Purpose: WFOPS-03's premise is that there is a failure path to hook, and there is not. `executeRun`
never throws when a run fails — it calls `failRun()` internally and returns normally, so the existing
`catch` only fires for *unexpected* exceptions. The alert must therefore **detect** by re-reading the
run's terminal status. And A3: `processWaitingRuns`' `SELECT … FOR UPDATE SKIP LOCKED` runs via
`db.execute` on a transaction-free postgres-js client, so the row locks drop at statement end and the
follow-up step `UPDATE` carries no status guard — two replicas can both resume the same delayed run and
duplicate every side effect after the delay.
Output: three call sites and a ~3-line claim fix, both gated.
</objective>

**A3 beats RESEARCH Open Question 5.** RESEARCH recommended documenting `processWaitingRuns` as unsafe
without fixing it. CONTEXT amendment A3 is USER-APPROVED and overrides: *"this phase applies the ~3-line
fix (transaction wrapper plus a `WHERE status = 'waiting'` guard) so delay resume becomes genuinely
safe. Publishing a doc that tells an operator two replicas are fine when delay resume double-fires was
rejected outright."* REQUIREMENTS.md's out-of-scope fence covers *horizontal scaling of
webhook-response* specifically and does not cover this. Plan 41-04's doc already writes the
`waiting resume` row as history-plus-fix, so the two plans agree.

**A4 / the alert DETECTS, it does not hook.** `executeRun` signals failure by writing a row
(`engine.ts:551-562`), not by throwing. The `catch` at `execution-processor.ts:144` only sees a DB
outage or a bug. So the alert call goes AFTER the try/catch, unconditionally, and
`maybeAlertOnRunFailure` re-reads the status itself.

**Three call sites, including `reclaimStaleRuns`.** A run killed by the five-minute execution lease is
precisely the "fails silently forever" case WFOPS-03 names, and it never passes through `executeRun` at
all — so the ids that `reclaimStaleRuns`' `RETURNING id` already yields must be alerted over. That costs
a loop over an already-returned list and covers a failure class nothing else can see.

**Two coverage gaps stay OPEN and documented, not closed.** Recursion-limit failures are inserted
already-`failed` by `createWorkflowRun` so the processor never claims them; synchronous
webhook-response runs are claimed and executed inline by the inbound webhook route so the processor
never sees them. Do NOT add the alert to `create-run.ts` or to the webhook route: both would put email
latency inside a live HTTP request, which is the exact reason CONTEXT placed the hook in the processor.
Plan 41-04 records both gaps in the deployment docs.

**The A3 target — `processWaitingRuns`' unguarded claim, verbatim:**
```ts
const readySteps = await db.execute(sql`
  SELECT wrs.id, wrs.run_id
  FROM workflow_run_steps wrs
  WHERE wrs.status = 'waiting' AND wrs.resume_at <= NOW()
  FOR UPDATE SKIP LOCKED          -- lock drops at statement end: NO transaction wrapper
`)
// …
await db
  .update(workflowRunSteps)
  .set({ status: "completed" as const, completedAt: new Date() })
  .where(eq(workflowRunSteps.id, stepId))          // <-- NO `AND status = 'waiting'` guard
```

**The guard shape to copy — `src/lib/triggers/create-run.ts:65-73`**, whose header states the protocol
this fix must join (*"flip 'pending' -> 'running' atomically. Whichever side wins the UPDATE owns the
run; the other side sees zero affected rows and backs off."*):
```ts
const claimed = await db
  .update(workflowRuns)
  .set({ status: "running", startedAt: new Date() })
  .where(and(eq(workflowRuns.id, runId), eq(workflowRuns.status, "pending")))
  .returning({ id: workflowRuns.id })
return claimed.length > 0
```

`src/db/index.ts:1-13` — the postgres-js client with **no transaction wrapper**, which is the basis of
the A3 finding. Drizzle's `db.transaction(async (tx) => { … })` is the available wrapper if a
transaction is used; the alternative and simpler fix is to drop the ineffective `FOR UPDATE SKIP LOCKED`
and rely on the guarded per-step `UPDATE … RETURNING` alone. **Both are acceptable; pick one and say
which in the SUMMARY.** The guarded UPDATE is the load-bearing half — the transaction only matters if
the SELECT's locks are being relied on, and once every step is claimed by a guarded write they are not.

`src/lib/execution/execution-processor.test.ts:1-33` — the mock header, which already mocks `db.execute`,
`executeRun`, the schema tables and the `sql` template. Adding an alert mock is one more `vi.mock`:

Its drain-loop idiom: `mockResolvedValueOnce([{…}])` then `mockResolvedValueOnce([])`.
