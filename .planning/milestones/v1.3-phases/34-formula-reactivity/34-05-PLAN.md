<objective>
Fix the two readers that a correct stored value alone does not fix.

Purpose: RESEARCH's reader audit found two of four readers sufficient and two not. The REST API serialisers pass the JSONB through verbatim, so SC-1 needs no change. The webhook payload needs no code change either — only the D-17 ordering guarantee. But `Papa.unparse` stringifies objects, and it was reproduced against the installed papaparse 5.5.3 that a wrapper-shaped value renders as the literal `[object Object]` in every CSV cell. SC-2 says the export must "carry the recalculated values"; `[object Object]` does not. And `resolveFieldPath` walks dot paths over the trigger envelope, so a condition reaching a formula field gets the wrapper object, `Number({...})` yields `NaN`, and `greater_than` silently returns `false` forever — a workflow that never fires and reports no error, which fails SC-3.

Storing a bare scalar instead of the wrapper is not an alternative: D-05 mandates the wrapper for errors so `[object Object]` would still leak on every errored formula, and `formula-field.tsx:50` uses `'formula' in value` to decide whether to trust the cached value — a bare scalar makes the client re-evaluate on every render, discarding the point of the stored value. Keep the wrapper; fix the readers.

Output: CSV and Pipedrive exports emit scalars, the workflow trigger envelope carries scalars, and the first test files for the export module exist.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored JSONB error string → exported CSV cell | `#ERROR: <message>` text produced server-side is written into a file a user downloads and may open in a spreadsheet |
| stored JSONB → workflow trigger envelope → condition evaluation → action execution | A formula-derived value now influences which workflow branch runs and therefore which side effects fire |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-06 | Information Disclosure | `#ERROR: ` text in CSV | mitigate | The error string was already sanitised at write time by `sanitizeFormulaError` (plan 34-03): first line only, capped at 200 characters, never a stack trace or Drizzle error. The export reader adds no new content |
| T-34-14 | Tampering | CSV formula injection | accept | A formula value beginning with `=`, `+`, `-` or `@` can be interpreted as a spreadsheet formula on open. This risk is pre-existing and identical for every text custom field in the export (any user can already type `=cmd|...` into a text field), and papaparse's quoting is unchanged. Not introduced by this phase; record as a backlog candidate for a dedicated CSV-injection pass across all export columns |
| T-34-15 | Tampering | condition branching on a derived value | mitigate | The envelope carries the scalar produced by the server-side recalc, not a client-supplied value — plans 34-07 through 34-10 strip formula keys from all client input (`stripFormulaKeys`). A caller therefore cannot steer a workflow branch by posting a chosen formula value |
| T-34-16 | Tampering | shared payload mutation | mitigate | The normaliser returns a copy; the `crmBus` payload object shared with the webhook subscriber is never mutated. Asserted by a source check and by Test 5's full-envelope deep-equal |
| T-34-SC | Tampering | npm installs | accept | Zero new packages; papaparse 5.5.3 is already a direct dependency |
</threat_model>
