    - No backfill. The database held 0 formula definitions and 0 stored formula values when this phase was built. CONTEXT.md explicitly defers backfill; a blank formula column on old rows is expected, not a defect.
    - `multi_select` arithmetic (D-15). Values are stored as arrays, and `{{Origem}} + 1` where `Origem` is `["Outbound Manual"]` yields the string `"Outbound Manual1"` — JavaScript array-to-primitive coercion inside the sandbox. Engine semantics are out of scope for this phase; use `TEXT.concat` or index access instead. This behaviour is pinned by a test.
    - Time-dependent formulas (Pitfall 10). `DATE.diffDays(DATE.today(), {{Start Date}})` is correct at save time and stale the next day. No save-triggered recalculation can fix that; recalculating on a schedule or on read is deferred.
    - Expressions are unvalidated at authoring time. `validateFormula` and `FormulaEditor` are dead code; the live authoring UI writes `{ expression }` with no checks. Every failure mode therefore surfaces as a stored error rather than as an authoring-time rejection.

Pre-existing and affecting all custom fields, not just formulas.
    - `POST /api/custom-fields/save` emits no CRM event, so a UI custom-field edit fires no webhook and no workflow even though the stored value is now correct (plan 34-08's deliberate decision).
    - Imports emit no CRM events and run with the cascade disabled (plan 34-10's deliberate decision).
    - Soft deletes do not recalculate. A child of a deleted parent retains its last computed value.
    - The cascade ignores ownership (D-09). A save may write formula keys on rows the acting user could not otherwise edit. Phase 36's audit log should attribute these writes to the system, not the user.
    - Recalculation is a second `UPDATE` outside any transaction. A crash between the entity write and the recalculation write leaves the formula value stale until the next save.
