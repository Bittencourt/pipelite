<objective>
Wire the six v1 deal and people routes that bypass the mutation layer to `recalculateFormulas`, before their emits.

Purpose: D-02 exists because Phase 32 established that the v1 routes diverge from the mutation layer — they emit `crmBus` events directly, carry their own auth patterns, and in these six cases perform their own `db.insert`/`db.update` rather than delegating. Wiring only the mutations would leave the entire REST write surface stale, which SC-1 explicitly forbids. These are also the only routes that already accept `custom_fields`, so they are the paths most likely to be exercised by a real integration.

There is one CRM v1 route test file in the repository today (`v1/workflows/__tests__/runs-routes.test.ts`) and no test for any of these six. This plan creates the first two.

Output: `POST /api/v1/deals`, `PUT /api/v1/deals/[id]`, `POST /api/v1/deals/batch`, `POST /api/v1/people`, `PUT /api/v1/people/[id]` and `POST /api/v1/people/batch` all recalculate before emitting.
</objective>

Key-casing divergence to preserve (RESEARCH § "The workflow condition fragility", final paragraph):
  v1/deals/route.ts:249 and v1/people/route.ts:153 emit `serializeDeal(deal)` / `serializePerson(person)`
  — snake_case `custom_fields` — while the mutation layer emits the raw camelCase row. Both spellings
  are normalised by the trigger envelope (plan 34-05). Do NOT "harmonise" the casing here; that would
  be a breaking change to existing webhook consumers.

The coarse sentinel vs the precise scope:
  These routes push the literal string "customFields" into their event `changedFields` array.
  Keep emitting that unchanged (webhook consumers may depend on it), but pass
  `[...changedFields, ...Object.keys(custom_fields ?? {})]` to `recalculateFormulas` so SC-4 holds
  tightly. The helper accepts the sentinel as a safety net, but precise names are strictly better.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API key holder → v1 route → `custom_fields` merge → stored JSONB | An external integration writes arbitrary custom-field keys, including potentially a formula-typed key |
| one batch request → up to 100 row inserts → up to 100 recalc invocations | The batch routes are the highest-amplification entry points in the REST surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-04 | Tampering | `custom_fields` on v1 deal/people routes | mitigate | `stripFormulaKeys` applied to the caller's `custom_fields` before the merge on POST and PUT for both entities. This closes the "any API key can set any value on a formula field" hole named in RESEARCH § "Anti-Patterns to Avoid" |
| T-34-03 | Denial of Service | batch route amplification | mitigate | One `FORMULA_EVALUATION_BUDGET` shared across the whole batch loop and decremented per row, plus `cascade: false`. Without the shared budget, 100 rows × 500 evaluations = 50,000 evaluations ≈ 60 s per request. Asserted by a test that the second call's budget is strictly less than the first's |
| T-34-22 | Denial of Service | batch size | accept | The batch item-count limit is whatever the routes already enforce in their Zod schemas; this plan does not change it. The shared evaluation budget bounds the formula cost independently of the row count |
| T-34-15 | Tampering | branching on an attacker-chosen value | mitigate | Since formula keys are stripped from input and written only by the server, an API caller cannot post a value that steers a workflow condition on a formula field |
| T-34-17 | Repudiation | recalc failure visibility | mitigate | Rejections logged with a `[formula-recalc]` prefix; the route still returns its normal status per D-05 |
| T-34-23 | Information Disclosure | emitted key casing | accept | These routes emit snake_case `custom_fields` via `serialize*` while the mutation layer emits camelCase `customFields`. Pre-existing divergence; harmonising it would break existing webhook consumers. Plan 34-05's trigger-envelope normaliser handles both spellings |
| T-34-SC | Tampering | npm installs | accept | Zero new packages |
</threat_model>
