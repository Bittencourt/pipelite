<objective>
Fix the silent `customFields` drop in the mutation layer. This is a prerequisite for the whole phase (D-12), not an incidental edit.

Purpose: all four mutation modules declare `customFields: z.record(z.string(), z.unknown()).optional()` in their Zod schemas (`deals.ts:19`, `people.ts:17`, `organizations.ts:15`, `activities.ts:17`) and accept it in their `Create*Input` interfaces (`deals.ts:87`, `people.ts:68`, `organizations.ts:27`, `activities.ts:68`) — and then never write it. None of the four `db.insert(...).values({...})` calls (`deals.ts:149`, `people.ts:90`, `organizations.ts:70`, `activities.ts:98`) includes the column, and none of the four update mutations builds it into `updateData`. RESEARCH Pitfall 5 confirms this by reading all four files. Consequences today: `POST /api/v1/organizations` and `POST /api/v1/activities` return 201 with `custom_fields: {}` no matter what the caller sent, and the workflow `crm_action` node's `interpolatedFields` cannot carry custom fields. Consequence for this phase: `recalculateFormulas` would merge a recomputed formula value into a JSONB column the entity write never populated.

Output: `customFields` round-trips through all eight mutation entry points, with a regression test per entity proving the drop cannot return.
</objective>
