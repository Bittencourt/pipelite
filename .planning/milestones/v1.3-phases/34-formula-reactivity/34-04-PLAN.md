<objective>
Add the bounded, depth-1, index-backed cross-entity cascade to `recalculateFormulas`, so a parent save refreshes the dependent child rows whose formulas reference it.

Purpose: D-03 rejects same-entity-only as leaving a known correctness hole the phase goal covers. But the live dataset makes an unbounded cascade a request-amplification primitive: 46,055 organizations, and the worst single organization has 114 deals plus 10 people. RESEARCH measured the reverse lookup at 0.909 ms (Phase 33's `deals_organization_id_idx`, Bitmap Index Scan) and QuickJS at ~1.2 ms per evaluation — the database is not the bottleneck, the sandbox is. Two hops (organization → deals → activities) reaches ~626 evaluations and ~750 ms, which is why D-13 fixes depth at 1 and the bound at 500 total evaluations (~598 ms measured). Also: `relatedEntities` is currently passed by ZERO callers, so `{{Organization.Revenue}}` always errors today. This plan makes cross-entity formulas functional for the first time.

Output: a cascade that fires only when a dotted ref matches a changed parent field, walks exactly one hop, caps at 500 evaluations, and warns loudly with enough detail to diagnose from logs alone.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| one authenticated write request → N child row writes | A single cheap `PUT /api/v1/organizations/{id}` can now trigger reads and writes across up to 124 other rows |
| acting user's ownership scope → child rows owned by others | D-09 deliberately writes rows the actor could not otherwise edit |
| parent row data → child evaluation sandbox | Parent `customFields` values, which are caller-controlled, are injected into a different entity's evaluation context via `relatedEntities` |
