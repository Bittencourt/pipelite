`INSERT INTO "notes" ("id","entity_type","entity_id","content","author_id","source","created_at","updated_at")
SELECT gen_random_uuid()::text, '<entity_type>', x."id", x."notes", x."owner_id", 'migration', x."created_at", x."created_at" FROM "<table>" x WHERE x."notes" IS NOT NULL AND btrim(x."notes") <> '' ON CONFLICT DO NOTHING;`
with each statement preceded by `--> statement-breakpoint`.

Non-negotiable details:
- `ON CONFLICT DO NOTHING` carries NO conflict target. That is deliberate: it resolves against
  `notes_migration_uniq` without naming it, so a future index rename cannot silently turn the
  statement into a duplicate-inserter (D-11).
- The `WHERE` clause does NOT filter `deleted_at`. Notes on soft-deleted parent records ARE
  migrated (D-18, ~15 rows on the live DB). SC-4 is an exact equality with no soft-delete carve-out
  on either side, and Phase 37's Trash & Restore will find note history intact.
- `created_at` and `updated_at` are both the record's `created_at`, which is what guarantees SC-3's
  "first timeline entry" ordering without special-casing the sort (D-10).
- `author_id` is the record's `owner_id` (D-09).
- `btrim(x."notes") <> ''` skips whitespace-only notes. Zero such rows exist today, but a blank
  first timeline entry would be worse than none.
- `gen_random_uuid()` is built into PostgreSQL 13+; no `pgcrypto` extension is required on 16.13.
- deals and people have ZERO non-empty notes in this dataset. Their statements are included anyway
  so the migration is correct on any other deployment.
- One `--> statement-breakpoint` per statement. The migrator runs `tx.execute(sql.raw(stmt))` per
  split chunk; multiple statements in one chunk is not the shape the 0009 precedent used.
- Do NOT hand-write any `CREATE INDEX` (D-06).

Above the data-migration block, add a `--` comment header recording: that this is NOTE-03, that
idempotency comes from `notes_migration_uniq`, and the measured live-data timings
(organizations 29,037 rows / 3,279 ms; activities 46,198 rows / 6,849 ms; re-run 0 rows / 1,451 ms;
resulting notes table 46 MB) with the measurement date.

Do NOT apply the migration in this task.

The file contains two queries:

Part 1 — count reconciliation. For each of the four entity types, compare
`count(*) FROM <table> WHERE notes IS NOT NULL AND btrim(notes) <> ''` against
`count(*) FROM notes WHERE entity_type = '<type>' AND source = 'migration'`, emitting columns
`entity_type`, `legacy_nonempty`, `migrated`, `delta`. Every row must show `delta = 0`.
The four legacy counts are produced by a `UNION ALL` subquery aliased `e`. The predicates MUST be
character-for-character the same as the migration's `WHERE` clauses — including the absence of any
`deleted_at` filter (D-18).

Part 2 — byte-level reconciliation. For each entity type, join the parent table to
`notes` on `entity_type`/`entity_id` with `source = 'migration'` and emit
`count(*) FILTER (WHERE n.content IS DISTINCT FROM <parent>.notes) AS mismatched`. Every row must
show `mismatched = 0`. A count match alone does not prove absence of truncation or encoding damage;
this does.

File header comment block must record all of:
1. What this file proves (SC-4 / NOTE-03) and that both parts must return zeros.
2. The run command: `docker compose exec -T postgres psql -U pipelite -d pipelite -f - < scripts/reconcile-notes.sql`
3. That `scripts/` is a new directory in this repo and this is the first checked-in `.sql` artifact.
4. **The permanent-detector note (Pitfall 6):** `src/lib/import/validators.ts`,
   `src/lib/import/pipedrive-mapping.ts`, `src/lib/import/pipedrive-api-transformers.ts`,
   `src/app/import/actions.ts`, and the `/api/v1` create/update routes still write the legacy
   `notes` column. The migration runs once. Therefore a NON-ZERO `delta` when this file is re-run
   after Phase 35 means something wrote to the legacy column after the migration — most likely an
   import. That is the sanctioned detection mechanism; fixing the importers is explicitly out of
   scope for this phase.
5. That `{{Notes}}` formula fields still read the now-dormant legacy column and therefore freeze at
   their migration-time value (Pitfall 7). This is a known inherited state for the phase that drops
   the column, not a bug to fix here.

The file must be pure SQL with `--` comments so it can be piped to psql unmodified.
