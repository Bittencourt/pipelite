<objective>
Build `GET /api/health` — the endpoint whose entire job is to answer a question no log line can:
is THIS process's `register()` actually alive right now.

Purpose: OBS-03, and the reason the phase exists. `instrumentation.ts` carries an in-source comment
recording that a silent `Dockerfile:24` copy failure killed all four processors in production on
2026-08-08 while every test passed, and the check meant to catch it — grepping the logs for
`[execution-processor] Starting` — is vacuous, because every build including a months-old one emits
that line. This endpoint replaces it.

The central design constraint is amendment A1. If the response is built by iterating the heartbeat
registry, a completely dead `register()` serializes as `processors: {}`, and
`Object.values({}).every(...)` is **`true`** — the endpoint returns 200 ok on precisely the failure it
exists to detect. The response is therefore built from `EXPECTED_WORKERS` (plan 02 already enforces
this inside `snapshot()`), and **the test "empty registry ⇒ 503 with all ten workers present and
`alive:false`" is this phase's most important assertion.** Without it the endpoint is decoration that
passes its own tests.

Output: `src/app/api/health/route.ts` and `src/app/api/health/__tests__/route.test.ts`.
</objective>

```typescript
// src/lib/observability/heartbeat.ts
export const EXPECTED_WORKERS: readonly string[]   // exactly 10 names
export interface WorkerReport { alive: boolean; lastTickAt: string | null }
export function snapshot(now?: number): Record<string, WorkerReport>
export function registerProcessor(name: string, expectedIntervalMs: number, initialDelayMs: number): void
export function registerSubscriber(name: string): void
export function recordTick(name: string): void
export function _resetForTesting(): void
```

Response shape — locked by CONTEXT, and deliberately minimal:

```json
{"status":"ok","db":{"ok":true,"latencyMs":1},"processors":{"webhook-processor":{"alive":true,"lastTickAt":"2026-08-23T12:00:00.000Z"}, "…nine more…":{}}}
```

HTTP 200 when healthy, 503 when degraded, so a load balancer or uptime check can act on the status
code without parsing the body.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated internet → `/api/health` | Any caller can reach this handler. `src/middleware.ts`'s matcher excludes `/api/*`, so next-auth never sees the request. |
| route handler → postgres.js pool | Every request takes one connection from a pool whose default size is 10 |
| in-process registry → public JSON | `snapshot()`'s output is serialized to an anonymous caller |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-01 | Information disclosure | the `GET` response body | mitigate | Fixed minimal payload: `status`, `db.ok`, `db.latencyMs`, and ten `{alive,lastTickAt}` pairs. No version string, no connection detail, no hostname, no row counts. `SELECT 1` is chosen over a "more representative" query precisely because a count is business data on an open endpoint. Enforced by a test asserting the exact top-level and `db` key sets, so a future field cannot be added silently. |
| T-42-21 | Information disclosure | the DB-failure path | mitigate | The rejection is swallowed by a bare `catch {}` and converted to `{ok:false, latencyMs:null}`. No driver message, SQLSTATE, stack or connection string reaches the body. Asserted by test. |
| T-42-02 | Denial of service | unauthenticated DB-touching endpoint | mitigate + accept residual | The 2-second bound caps how long any single request can hold one of the pool's 10 connections, and `clearTimeout` in a `finally` prevents timer accumulation under load. Residual risk accepted and documented: a flood still costs one `SELECT 1` per request. CONTEXT requires the endpoint open for load balancers; the operator's own reverse proxy is the rate-limiting layer. A 1-second memoisation of the probe result is the named cheap mitigation if it ever matters — deliberately not shipped, because the complexity is not yet earned. |
| T-42-03 | Information disclosure | worker liveness as a reconnaissance oracle | accept | An anonymous caller learns that ten named background jobs exist and which are dead. Weighed against load balancers and uptime checks needing the endpoint open, which CONTEXT locks. The job names are already visible in the repository. |
| T-42-10 | Repudiation | `healthy` computation | mitigate | The report comes from `snapshot()`, which iterates the fixed ten-name roster, so the endpoint cannot report healthy on an empty registry. Proven twice: by the empty-registry test, and by RED #2 demonstrating that a registry-iterating implementation returns 200 with `processors: {}`. |
| T-42-22 | Tampering | unauthenticated write verbs | mitigate | Only `GET` is exported and the sibling test asserts `POST`/`PUT`/`PATCH`/`DELETE` are `undefined`. `GET.length === 0` proves the handler reads no input — no query params, no body, no headers — which is the strongest ASVS V5 posture available. |
| T-42-23 | Tampering | a cached health response | mitigate | No `Cache-Control` and no `export const dynamic`. Route Handlers are uncached by default in Next 15+; a cached health response would report a stale liveness claim, which is worse than no endpoint. `docs`'s `max-age=3600` header is explicitly not copied. |
</threat_model>
