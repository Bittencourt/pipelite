<objective>
Build `src/lib/observability/sentry.ts` — opt-in server-side error tracking whose disabled state is a
provable absence rather than an assumed one.

Purpose: OBS-02. Criterion 2's first half is a claim about absence ("with the env var unset nothing
leaves the deployment"), and an absence of observed traffic is not evidence. So the disabled path is
asserted three independent ways: `init` is never called; the SDK module is never even evaluated; and
no outbound `fetch` happens. The second layer is the strong one — the `await import()` sits inside the
DSN guard, so with no DSN the SDK is not loaded at all.

The second constraint is a bundling one (amendment A6). `instrumentation.ts` is compiled for the edge
runtime as well as Node — verified: its edge copy is `async function t(){}`, empty *only* because
every dependency sits behind `await import()` inside the `NEXT_RUNTIME` guard. That rules out Sentry's
own documented one-liner `export const onRequestError = Sentry.captureRequestError`, which needs a
top-level import. This module is the wrapper that makes the guarded form possible, and plan 17 keeps
`instrumentation.ts` a thin delegator over it.

Output: `src/lib/observability/sentry.ts` and `src/lib/observability/sentry.test.ts`.
</objective>

<expectation_setting>
`onRequestError` sees only genuinely UNHANDLED errors. 231 of this repo's 273 log call sites are
`console.error` inside deliberate swallow-and-log catches, and its server actions return
`{ success: false, error }` rather than throwing. None of that reaches Sentry, and that is the design:
the logger is the channel for handled errors, Sentry catches the residue that escapes every handler.

Do NOT wire `log.error` into `Sentry.captureException`. CONTEXT locks "unhandled server errors only",
and coupling them would put this CRM's entire swallowed-error volume on the wire.
</expectation_setting>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| deployment → sentry.io | With a DSN set, error payloads leave the operator's infrastructure entirely. This is the phase's only outbound egress. |
| operator env → SDK config | `SENTRY_DSN` is a credential read from the process environment and handed to the SDK |
| Next.js error seam → this module | Arbitrary unhandled errors, plus the request that produced them, arrive here |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-06 | Information disclosure | Sentry egress from `initSentry()` | mitigate | Two independent filters. Sentry's own `dataCollection` (userInfo off, empty `httpBodies`, header and cookie deny lists) and our `beforeSend`, which runs last and deletes `event.user`, `request.data`, `request.cookies`, `request.headers`. Asserted on `beforeSend`'s return value so a mutate-but-forget-to-return implementation fails. Relying on Sentry-side scrubbing alone would put CRM data on the wire before it was filtered. |
| T-42-17 | Information disclosure | egress when the operator has not opted in | mitigate | Three independent negative assertions: `init` not called, the SDK module never evaluated (throwing mock factory), and no outbound `fetch`. The absence is proven, not inferred from the absence of observed traffic. |
| T-42-07 | Information disclosure | `SENTRY_DSN` value | mitigate | The DSN is read by name and passed straight to `init`. It is never logged, never echoed, and never placed in a `ctx` object. The disabled-path log line names the variable, not any value — asserted by test. |
| T-42-18 | Information disclosure | `reportRequestError`'s `ctx` | mitigate | Only `err`, `path`, `method`, `routePath` and `routeType` are logged. The raw `request` object and its `headers` map are never put into `ctx`, so a bearer token or cookie header cannot be swept into the log stream by this seam. |
| T-42-19 | Information disclosure | coupling handled errors to Sentry | mitigate by omission | `log.error` is deliberately NOT wired into `captureException`. CONTEXT locks "unhandled server errors only"; coupling them would ship this CRM's entire swallowed-error volume — hundreds of catch blocks — to a third party. |
| T-42-20 | Denial of service | edge-runtime double compile | mitigate | Every value import of the SDK is dynamic and inside a guard, so the edge copy of `instrumentation.ts` stays empty. A top-level import would drag the SDK into the edge bundle, where `node:` builtins do not exist, and could fail the build outright. |
</threat_model>
