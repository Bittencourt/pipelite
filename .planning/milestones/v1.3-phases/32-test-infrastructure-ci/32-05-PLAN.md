<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| fork contributor → GitHub Actions runner | A pull request from any fork causes this workflow to execute repository code on GitHub's infrastructure with a token |
| third-party action → runner filesystem and token | `actions/checkout` and `actions/setup-node` run with full access to the workspace and `GITHUB_TOKEN` |
| npm registry → runner | `npm ci` executes install scripts from 1003 packages (notably `argon2`, which builds a native binding) |
| CI job → repository write surface | The default `GITHUB_TOKEN` permission set is often broader than a read-only job needs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-18 | Elevation of Privilege | `GITHUB_TOKEN` scope | mitigate | Declare workflow-level `permissions: contents: read` and nothing else. The default token scope is frequently write-capable; this job only clones and runs three commands, so anything beyond read is unnecessary reach. Asserted by the `grep -A2 '^permissions:'` acceptance criterion. |
| T-32-19 | Elevation of Privilege | trigger event choice | mitigate | Use `pull_request`, never `pull_request_target`. `pull_request_target` executes the **base** workflow definition against **fork-supplied code** with repository secrets and a write token — the canonical Actions privilege-escalation vector. Fork PRs under `pull_request` get a read-only token and no secrets. Asserted by `grep -c 'pull_request_target'` returning 0. |
| T-32-20 | Information Disclosure | secret leakage into logs | mitigate | The job is designed to need zero secrets: no `DATABASE_URL`, no service container, no publish step, no npm token. Asserted by `grep -c 'secrets\.'` and `grep -c 'DATABASE_URL'` both returning 0. Nothing can leak into a log that was never placed in the environment. |
| T-32-21 | Tampering | third-party actions | mitigate | Only two actions, both first-party GitHub (`actions/checkout`, `actions/setup-node`), pinned to major-version tags whose current releases were confirmed live via the GitHub REST API during research (v7.0.1 / v7.0.0). The repo reports `sha_pinning_required: false`, so tags are policy-acceptable; full-SHA pinning remains the hardened upgrade and is noted, not required. |
| T-32-22 | Tampering | dependency resolution in CI | mitigate | `npm ci` (lockfile-exact, fails on lockfile/manifest mismatch) rather than `npm install`, which would re-resolve and could pull a different tree than the one reviewed. Verified to exit 0 without `--legacy-peer-deps`. Asserted by `grep -c 'legacy-peer-deps'` returning 0. |
| T-32-23 | Tampering | npm cache | accept | `actions/setup-node`'s `cache: npm` caches the **global npm cache**, not `node_modules`, so it cannot produce a corrupt half-installed tree. The action's own docs recommend disabling automatic caching only when a workflow **publishes** packages (npm-token exposure); this workflow publishes nothing and holds no token, so `cache: npm` is safe here. `actions/cache/restore` is the read-only hardening option if the job ever gains a token. |
| T-32-24 | Denial of Service | required check that never reports | mitigate | No `paths:`/`paths-ignore:` filter on the workflow. A workflow skipped by a path filter reports nothing, and GitHub treats a required check that never reports as permanently pending — every docs-only PR would become unmergeable with no way out. Asserted by the `grep -Ec '^\s*(paths\|paths-ignore):'` criterion returning 0. `timeout-minutes: 15` and `cancel-in-progress: true` bound runner-minute consumption from a runaway or spam-pushed run. |
| T-32-25 | Repudiation | undocumented merge gate | mitigate | Branch protection has no in-repo representation, so an undocumented setting silently disappears on repo transfer, fork, or restore. Task 3 records the exact ruleset configuration and the two `gh api` audit commands in `CONTRIBUTING.md`, making the control reconstructible and verifiable. |
| T-32-SC | Tampering | npm/pip/cargo installs | mitigate | **This phase installs zero new packages** — `32-RESEARCH.md` § "Package Legitimacy Audit" records an empty candidate table and no `slopcheck` run, because there is nothing to check. The only third-party code introduced is the two first-party GitHub Actions covered by T-32-21. No `[ASSUMED]`, `[SUS]`, or `[SLOP]` package exists in this phase, so no blocking legitimacy checkpoint is required. Separately noted and deliberately **not** acted on: `npm ci` reports 39 existing lockfile advisories (4 critical, 23 high); adding `npm audit --audit-level=high` to this workflow would make the required check red on day one and is filed as future work, not silently bolted on. |
