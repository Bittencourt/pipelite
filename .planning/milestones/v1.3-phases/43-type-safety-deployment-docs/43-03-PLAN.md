<objective>
Make uploaded files survive a rebuild. Three coordinated changes, ONE commit.

Purpose: POLISH-02 says an operator can back up and restore a self-hosted deployment. You cannot
recover data that was never persisted. Measured: `docker-compose.yml` declares a volume only on
`postgres`; the `app` service has no `volumes:` block at all; `FILE_STORAGE` defaults to `'local'`. So
local-storage uploads are written into the container filesystem and destroyed on every
`docker compose up --build`. Postgres survives; the files its JSONB custom-field values point at do not.
A database-only restore would produce rows referencing files that no longer exist.

**This is the phase's highest-risk change, and the risk is that a partial fix looks like a fix.**
Research measured all three failure modes:

| Applied | Result |
|---|---|
| volume only | The app keeps writing to `/tmp/uploads` — `UPLOAD_DIR` defaults to `/tmp/uploads` (`src/app/api/upload/route.ts:12`) and this compose file has **no `env_file:`**, so an unlisted variable never reaches the container. The volume stays empty **forever** and nothing errors. |
| volume + `UPLOAD_DIR`, no Dockerfile change | A fresh named volume mounted at a path absent from the image is created **root:root 0755**, and the container runs as uid 1001. Measured: `touch: Permission denied`. **Every upload returns 500.** Strictly worse than today. |
| `UPLOAD_DIR` + chown, no volume | Writes succeed to a container path and vanish on rebuild. Exactly today's defect with more moving parts. |

One of those fails silently and one fails loudly, so neither review nor a smoke test reliably catches
the wrong subset. The gate written in task 1 is the only thing that can: the defect is a three-file
disagreement that is invisible in any single diff.

Output: a compose volume, an env var, an image-layer `chown`, `.env.example` brought level with what
compose actually requires, and a gate that goes red if any one of them regresses.
</objective>

**The ownership trap, measured both directions:**
```
$ docker run --rm -u 1001:1001 -v probe_uploads_test:/app/uploads alpine:3 \
    sh -c 'id; ls -ld /app/uploads; touch /app/uploads/probe.txt || echo "WRITE FAILED"'
uid=1001 gid=1001 groups=1001
drwxr-xr-x    2 root     root          4096 /app/uploads
touch: /app/uploads/probe.txt: Permission denied
WRITE FAILED
```
With `RUN mkdir -p /app/uploads && chown nextjs:nodejs /app/uploads` in the image before
`USER nextjs`, the same probe reports `drwxr-xr-x 2 nextjs nodejs` and `WRITE OK`, and the file
survives into a second container against the same volume.

**Chown the USER, not the group.** `id` inside the running container reports
`uid=1001(nextjs) gid=65533(nogroup)`. The Dockerfile does `addgroup --system --gid 1001 nodejs` then
`adduser --system --uid 1001 nextjs` **without `-G nodejs`**, so `nextjs`'s primary group is `nogroup`
and it is NOT a member of `nodejs`. The write above succeeded through the OWNER bit.
- `chown nextjs:nodejs /app/uploads` — **works** (owner is `nextjs`).
- `chown root:nodejs /app/uploads && chmod g+w` — **does not work.** Do not write it that way.
- Do not "fix" a permission error with `chmod 777`. That is the wrong fix for this failure.

**`/tmp` is mode 1777**, which is the only reason nobody has hit EACCES yet. Moving off `/tmp` is what
makes ownership suddenly matter.

**No live data is at risk.** 169 `custom_field_definitions` rows exist — `text` 62, `multi_select` 56,
`single_select` 28, `number` 12, `date` 11 — and **zero of type `file`** (verified). The defect is
latent and the fix is preventive, so there is no data-migration obligation and plan 43-05's experiment
must CREATE its own upload rather than relying on existing data.

**`.env.example` cannot start this stack.** `docker-compose.yml` requires `POSTGRES_USER`,
`POSTGRES_PASSWORD` and `POSTGRES_DB`; `.env.example` (33 lines, read in full) contains none of the
three. An operator who copies it cannot bring up Docker at all — which means step 1 of the restore
runbook cannot be completed on a clean host. That puts it on POLISH-02's path, and it is four lines.
</measured_facts>

<the_change>
**1. `docker-compose.yml`** — one env entry, one volumes block on `app`, one top-level volume:

```yaml
services:
  app:
    environment:
      # ... existing entries, untouched ...
      - UPLOAD_DIR=/app/uploads
    volumes:
      - uploads_data:/app/uploads

volumes:
  postgres_data:
  uploads_data:
```

**Hardcode `/app/uploads`. Do NOT write `${UPLOAD_DIR:-/app/uploads}`.** An operator who then set
`UPLOAD_DIR=/srv/files` in `.env` would move the write path out from under the mount and silently lose
persistence again — the same class of bug being fixed. An operator who genuinely wants another path
edits both lines, which is honest and which the gate enforces by asserting the two are equal.

**2. `Dockerfile`** — runner stage, after the `addgroup`/`adduser` lines and **before `USER nextjs`**.
Not in the builder stage:

```dockerfile
RUN mkdir -p /app/uploads && chown nextjs:nodejs /app/uploads
```

**3. `.env.example`** — add `UPLOAD_DIR`, and add the three `POSTGRES_*` variables compose requires.
</the_change>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container filesystem → named volume | The line between data that survives a rebuild and data that does not. Today every uploaded byte is on the wrong side of it. |
| image build (uid ownership) → container runtime (uid 1001) | Two tiers that must agree about one directory. Docker decides the new volume's ownership from the image, before the app ever runs. |
| `.env` → container process env | This file has no `env_file:`, so a variable absent from the `environment:` list never arrives. That mechanic is why the volume alone changes nothing. |
| operator following `.env.example` → a bootable stack | Today it is not one. Three compose-required variables are missing. |
