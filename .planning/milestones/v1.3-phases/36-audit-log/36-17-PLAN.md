  <action>
    Implement `auditSource.hydrate(ids)` returning `AuditTimelineEntry[]`.

    One batched select on `audit_log` for the given ids, with `leftJoin`s for: `users` (the actor
    name and email), `workflow_runs` joined onward to `workflows` (the run's workflow id and name),
    and `api_keys` (the key name). Use `alias()` if any table is joined twice.

    Actor resolution follows the analog's guard shape: `actor` is populated only when
    `actorKind === 'user'` AND the joined user row is present; otherwise `null`, which the renderer
    turns into "Unknown user". `workflowRun` is populated only when `actorKind === 'workflow_run'`
    AND the workflow still exists — otherwise `null`, and the renderer draws the plain kind label
    with no link. Never a broken link. Same for `apiKeyName`.

    Then build `changes` by calling `buildAuditFieldChanges(entityType, action, row.changes,
    resolution)`. Populating the `AuditResolution` is this function's real work:
    - `customFieldNames` / `customFieldTypes` / `customFieldPositions`: ONE batched read of
      `custom_field_definitions` for the entity types present in this page, not one per entry.
    - `references`: collect every reference-column id appearing across the page's change maps
      (stage ids, owner/assignee user ids, organization ids, person ids, deal ids, activity type
      ids), then ONE batched read per referenced table. An id whose row is gone maps to `null`, which
      the renderer prints as "no longer available".

    Batch, do not loop. A page is 20 entries and a naive per-entry resolution would be dozens of
    round trips on a path that renders inside the detail page's own render.

    Do NOT resolve anything the renderer can do itself — dates, numbers and lists are formatted in
    the client via `useFormatter`, and `present.ts` is where the typing happens. This function's job
    is strictly the database-dependent half.
  </action>
