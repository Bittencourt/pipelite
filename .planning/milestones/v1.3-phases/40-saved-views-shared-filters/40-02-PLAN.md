  <name>Task 1: Declare savedViews and savedViewDefaults</name>
  <files>src/db/schema/saved-views.ts, src/db/schema/index.ts, src/db/schema/_relations.ts</files>
  <action>
    Create `src/db/schema/saved-views.ts` following `dedup-scans.ts` in shape and in comment density.

    TABLE 1 — `savedViews` (`saved_views`):
      - `id` text pk, `$defaultFn(() => crypto.randomUUID())`
      - `ownerId` text `not null` → `users.id`. NOT `onDelete: cascade`: a soft-deleted user's rows
        must survive, because a shared view owned by a soft-deleted user stays visible and stays
        functional (V-5) — it is a filter set, not a record.
      - `entityType` text `not null` `.$type<EntityType>()`, with `EntityType` **imported** from
        `./custom-fields`, never restated. A renamed member of that union must be a compile error
        here, exactly as `dedup-scans.ts` arranges for `MergeableEntityType`.
      - `name` text `not null`
      - `filters` jsonb `not null` `.default({})` `.$type<Record<string, string>>()`
      - `isShared` boolean `not null` `.default(false)`
      - `createdAt`, `updatedAt` timestamps, `defaultNow().notNull()`
      - There is deliberately **no `deletedAt`**: UI-SPEC D-2 and the locked decision say a delete
        removes the view for everyone immediately and the records are untouched. A soft-deleted saved
        view would be a filter set nobody can see and nobody can purge, and `/trash` has four tabs
        that do not include views.
      - There is deliberately **no `isDefault` column** — see task note below.

    Indexes on `savedViews`:
      - `uniqueIndex("saved_views_owner_type_name_uniq").on(ownerId, entityType, name)` — S-6's
        refusal as a DB invariant. Scoped to (owner, entityType) so two users may each have a view
        called "Mine" and one user may not. Write the comment saying the action catches `23505` and
        returns `name_taken` rather than pre-checking, and naming the BACKLOG scan-guard item as the
        precedent for why a read-then-write check is not enough.
      - `index("saved_views_owner_idx").on(entityType, ownerId)` — the "my views" half of the picker
        read.
      - `index("saved_views_shared_idx").on(entityType, isShared)` — the "shared with me" half.
        Not partial: `isShared` is toggled both ways from the manage dialog and both values are
        queried.

    TABLE 2 — `savedViewDefaults` (`saved_view_defaults`):
      - `userId` text `not null` → `users.id`, `onDelete: cascade`
      - `entityType` text `not null` `.$type<EntityType>()` (imported)
      - `viewId` text `not null` → `savedViews.id`, **`onDelete: cascade`**
      - `updatedAt` timestamp `defaultNow().notNull()`
      - `primaryKey({ columns: [userId, entityType] })` — one default per user per entity type, as a
        DB invariant. Import `primaryKey` from `drizzle-orm/pg-core`.
      - `index("saved_view_defaults_view_idx").on(viewId)` so the cascade and the "is this view
        somebody's default" read are both index-backed.

    WRITE THIS RATIONALE INTO THE FILE, because it is a deliberate departure from 40-CONTEXT.md and
    the next reader must not "simplify" it back:

    > 40-CONTEXT.md's grounded default says the default view is "a per-user, per-entityType flag on
    > the view row". That same file, and UI-SPEC G-7, also require that **a user may set someone
    > else's shared view as their own default** — G-7 calls that asymmetry "the one thing this row
    > must make legible". A boolean on the view row cannot express both: setting `isDefault` on a
    > view owned by Ana would make it Ana's default too. So the discriminator-table decision
    > (ONE views table for all four entity types, not four tables) is honoured exactly as written,
    > and the default is a two-column primary key in a separate 4-column table. This is the smaller
    > departure; the alternative is to silently drop G-7, and G-7 is a locked spec rule.

    Export `SavedView`, `NewSavedView`, `SavedViewDefault`, `NewSavedViewDefault` via `$inferSelect`
    / `$inferInsert`.

    Register: add `export * from "./saved-views"` to `src/db/schema/index.ts`, placed before the
    trailing `export * from "./_relations"` line (that line must stay last).

    In `src/db/schema/_relations.ts`, import `savedViews` and `savedViewDefaults` and add:
      - `savedViewsRelations = relations(savedViews, ({ one, many }) => ({ owner: one(users, {
        fields: [savedViews.ownerId], references: [users.id] }), defaults: many(savedViewDefaults) }))`
      - `savedViewDefaultsRelations` with `view: one(savedViews, …)` and `user: one(users, …)`
      - add `savedViews: many(savedViews)` to the existing `usersRelations` object

    The `owner` relation is not decoration: V-5's attribution chain is `user.name || user.email` plus
    a soft-delete check, and without the relation that is a second query per view. Confirm after
    editing that `db.query.savedViews.findMany({ with: { owner: true } })` typechecks.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server action → database | a `name` and a `filters` blob authored by any authenticated user land here |
| one user's row → another user's read | `ownerId` + `isShared` are the only things standing between a private view and a teammate |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-40-07 | Tampering | `saved_views.name` uniqueness | mitigate | `uniqueIndex(ownerId, entityType, name)` makes the S-6 refusal atomic; the action catches `23505` instead of pre-checking. A read-then-write check is the advisory guard BACKLOG.md already records as a defect |
| T-40-08 | Elevation of privilege | `saved_view_defaults` | accept | a user may point their own default at any view id, including a private one they cannot see. The default only produces a REDIRECT to filter params; the records behind it are still governed by per-record rules, and plan 40-05's resolver refuses to redirect to a view the user cannot read. Recorded rather than fixed with a trigger |
| T-40-09 | Denial of service | `filters` jsonb | mitigate | values are length-capped upstream by `MAX_FILTER_VALUE_LENGTH` (plan 40-01) and the whitelist bounds the key count at 7; no unbounded blob can be stored |
| T-40-10 | Repudiation | view deletion | accept | deleting a view writes no audit row this phase. 36-CONTEXT.md:61 anticipates Phase 40 as an audit consumer, but a saved filter set is not record data and the audit schema keys on entity ids. Recorded as a deliberate omission |
| T-40-SC | Tampering | npm/pip/cargo installs | mitigate | this plan installs nothing. `drizzle-kit` is already a devDependency; do not run `shadcn add` or `npm i` for any reason (UI-SPEC N-1) |
