<objective>
Put the bound in the one place a caller-supplied filter map reaches an uncapped-by-selection read, and
make its removal loud.

`guardExportInput` has exactly ONE production caller — `src/lib/views/export-action.ts:62` — and that
call site is the only place in the repository where a filter map reaches the export read. The four
Phase 38 bulk actions take `(ids: string[])` and nothing else, hard-capped at `BULK_MAX_IDS = 100`;
`src/app/admin/export/actions.ts:16` is role-gated and deliberately unbounded. So this plan touches one
call site — and then proves, repo-wide, that there is still only one.

**The order inside the action is the control.** Authenticate, then the cheap sync guard, then the
count, then the decision, then the fetch. A `{}` request or a crafted `entityType` still stops at
`guardExportInput` having read nothing, which is what its header (`:18-19`) exists to preserve — the
count must not become a tax on requests the guard already refuses.

**NO ADMIN BRANCH, and the shipped gate stays green and unmodified.**
`view-filters.test.ts:736-747` asserts over comment-stripped source that `export-action.ts` contains
neither `/["']admin["']/` nor `/\brole\b/`, with a message stating that an admin gate there *"would
silently un-widen a recorded widening, and it would do so invisibly, because this deployment's two
admin accounts would still pass every test."* Its author anticipated exactly this move. The resolution
needs no gate change at all: `src/app/admin/export/actions.ts` is already a separate role-gated
unbounded export, so admins keep the path they have while the view path is bounded for everyone. E-9
survives — export remains available to every authenticated user, now *bounded* rather than *refused*.
**Do not add a `role` or `admin` token to `export-action.ts`. Do not rewrite that gate. Do not relocate
the branch into a helper to keep it green** — that is gate-laundering, and 50-01 already closed the
escape by asserting the same absence in `export-selectivity.ts`.

**One consequence to record rather than discover later.** With selectivity refusing anything above
40% of the table, `EXPORT_ROW_CAP = 50_000` becomes unreachable from the view path on current volumes:
a set above 50,000 rows on the largest table (79,022 activities) is 63%+, so the selectivity refusal
lands first. The cap's one live branch today — `activities status=completed`, 74,857 rows, refused with
`too_many` — will be refused with `too_broad` instead. **The cap stays**: it is defence in depth and
fires again as soon as a table passes ~125,000 rows, `view-filters.test.ts:766-773` asserts it in both
directions, and threading a computed allowance through `maxRows` instead would redden `:749-764` and
lose the exact `matched` SC-3's message needs. Record the consequence; change nothing about it.
