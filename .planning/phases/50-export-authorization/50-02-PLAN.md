<objective>
Give the refusal a sentence a user can act on, in three languages, without half-satisfying a contract
that cannot be half-satisfied.

SC-3 asks that *"a refused user sees why, in terms they can act on; a blocked broad export is
distinguishable from a broken one."* Today the client has three outcomes and two of them are wrong for
this case: `views.export.tooMany` speaks about a cap the selectivity refusal does not use, and
`bulk.error.exportFailed` is the generic breakage. A fourth key is needed, and it must carry the two
numbers the server measured — 50-CONTEXT locks that: *"The refusal must carry the numbers (`matched`,
`total`) so SC-3 is satisfiable with an actionable message rather than a generic one."*

**Phase 40 already had to reword one of these strings once.** Its verifier found
`views.export.disabledReason` reading *"Choose at least one filter first. An unfiltered export isn't
allowed."* in the one case the narrowing exists for, and G-2 closed by rewording. The shipped text
today is *"Add a filter that narrows the results before exporting."* — **do not touch it.** It is the
client-side PRE-submit affordance, computed from `canExport`, which cannot know `matched`. The new key
is the POST-submit refusal. Two different moments, two different strings.

**The contract this lands in cannot be half-satisfied, and that is the good news.**
`locale-parity.test.ts:1326-1329` is a total `toEqual` over the sorted shipped `views.*` key set
against `REQUIRED_VIEWS_KEYS`, so a string added to the JSON without the array entry fails there, and
an array entry without the JSON fails the `missingIn` check at `:1172`. Both directions are already
covered. Six edits, one commit — and the plan drives them in an order that makes each half-state
visible as a red before the next edit closes it.

Purpose: SC-3's string, its parity, and a proof that it renders with the numbers in it.
Output: one key in three locales, six contract edits, and a behavioural copy proof.
</objective>

**The shipped `views.export` object, en-US** (`en-US.json:716-720`), for placement:

```json
"export": {
  "disabledReason": "Add a filter that narrows the results before exporting.",
  "tooMany": "This view matches more than {max} records. Narrow the filters and export again.",
  "refused": "That export was refused because no filter was applied."
}
```

**The copy to add.** `{matched}` and `{total}` in all three, because `placeholderDrift`
(`locale-parity.test.ts:1515`) requires the ICU placeholder set to be identical across locales, and
`untranslatedInBoth` (`:1397`) fails a key whose pt-BR and es-ES values are byte-identical to en-US.

- en-US: `"tooBroad": "This filter matches {matched} of {total} records — too many to export. Narrow it and try again."`
- pt-BR: `"tooBroad": "Este filtro corresponde a {matched} de {total} registros — muitos para exportar. Restrinja o filtro e tente de novo."`
- es-ES: `"tooBroad": "Este filtro coincide con {matched} de {total} registros — demasiados para exportar. Acótalo e inténtalo de nuevo."`

**The translator to render with**, already in the repository and already used in production
(`src/lib/email/i18n.ts:1`):

```ts
import { createTranslator } from "use-intl/core"
const t = createTranslator({ locale: "en-US", messages, namespace: "views" })
t("export.tooBroad", { matched: 44254, total: 46054 })
```

**The trap in that call, and it is why the proof asserts what it asserts.** `use-intl` formats a
numeric ICU argument PER LOCALE. `44254` renders as `44,254` in en-US and `44.254` in pt-BR and es-ES.
An assertion that the sentence `toContain("44254")` therefore FAILS against correct code. Compute the
expected substring with `new Intl.NumberFormat(locale).format(44254)` and assert that — and record the
observation, because this is exactly the shape of assertion that would have shipped red.
