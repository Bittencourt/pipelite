<objective>
Make the number the guard authorizes on, and the number the export produces, the same number by
construction.

This is the hazard that turns a selectivity rule into a gate that can be bypassed. `matched` must be
counted with the SAME predicate the export runs. Today the four fetchers build their `conditions: SQL[]`
arrays **privately**, inside their own bodies (`formatters.ts:349-380`, `:382-417`, `:419-486`,
`:488-568`). A count written from a *copy* of those conditions is correct exactly until one side is
edited, and then it authorizes on a number the export does not honour — silently, because both halves
still "work".

**So the builders come out, and both consumers call the same one.** The in-repo precedent already
solves this in production: `src/app/api/v1/organizations/route.ts:35-38` builds ONE `whereClause` and
hands it to both `count()` and `findMany`. This plan does the same thing one layer down.

**The extraction collides head-on with this phase's most load-bearing gate, and that collision is the
plan's first deliverable.** `view-filters.test.ts:191-233` extracts each `fetch*` function's body by
brace matching and asserts, for all **14** exportable entity/key pairs, that `filters?.<key>` appears
in that body — the T-40-30 invariant that every key `hasExportableFilter` counts provably NARROWS the
query. Move the conditions out of the fetchers and all 14 rows go red. That red is not damage to be
avoided; it is the observation that proves the gate was measuring something. The correct response is
to RE-ANCHOR it onto the builders — which makes it stronger, because one builder now feeds both the
read and the count, so the gate covers the count path too — and then to falsify the re-anchored form
by deleting a predicate and watching the same 14-row cell go red again.

**Two counts, per attempt, uncached — measured, not guessed.** `COUNT(*)` with the organizations
`search` predicate is 46.1 ms and the unfiltered live count is 13.0 ms, while a single combined
`count(*) FILTER (WHERE …)` aggregate is **93.5 ms** — slower, because the `FILTER` form evaluates the
ILIKE inside the aggregate on every row instead of short-circuiting in the scan filter. And a cached
`total` is a staleness bug on a security control.

Purpose: the count half of SEC-03's decision, and the structural guarantee that it cannot drift.
Output: four exported builders, one dispatcher, one counter, a re-anchored gate, and a live proof that
the count equals the file.
</objective>

**The shape to add to `formatters.ts`.** Four named function declarations plus one dispatcher — named
`function <name>(` declarations, not arrow consts, because `view-filters.test.ts`'s `functionBody`
helper matches on `function <name>(` and throws by name if a declaration is absent or duplicated.

```ts
export function organizationExportConditions(filters: ExportFilters | undefined): SQL[]
export function personExportConditions(filters: ExportFilters | undefined): SQL[]
export function dealExportConditions(filters: ExportFilters | undefined): SQL[]
export function activityExportConditions(filters: ExportFilters | undefined): SQL[]

/** Total over ViewEntityType, so a fifth entity type is a compile error rather than a silent gap. */
export function buildExportConditions(entityType: ExportEntityType, filters: ExportFilters | undefined): SQL[]
```

Each fetcher then reads `const conditions = <entity>ExportConditions(filters)` and pushes nothing of
its own.

**The shape of the new module** (`src/lib/export/export-count.ts` — a THIRD file, deliberately):

```ts
export interface ExportCounts { matched: number; total: number }
export async function countExportMatches(
  entityType: ExportEntityType,
  filters: ExportFilters | undefined
): Promise<ExportCounts>
```

**Why three files and not two.** `src/lib/export/export-selectivity.ts` (plan 50-01) is PURE and
imports no database — that is what makes its small-N cells possible, since `pipelite_dedup_test`
starts empty and every live table is at least 25,195 rows. `countExportMatches` must import `@/db`. Put
them in one file and 50-01's unit file cannot load without `DATABASE_URL`, and the floor becomes
unprovable. So: `export-selectivity.ts` decides, `export-count.ts` counts, `view-export-guard.ts` stays
untouched and sync.

**The production idiom for the two counts** (`src/app/api/v1/organizations/route.ts:35-38`):

```ts
const [{ total }] = await db.select({ total: count() }).from(organizations).where(whereClause)
```

`count()` from `drizzle-orm` 0.45.2 is already imported in eight-plus modules. No new dependency.

**`total`'s predicate is the fetchers' own base predicate and nothing else** — `isNull(<table>.deletedAt)`
(`formatters.ts:353, 386, 423, 492`). NOT a viewer-scoped count: there is no viewer scoping anywhere in
the export read path, which is the exposure, not something to encode into the denominator.

**The gate to re-anchor**, read at source (`view-filters.test.ts:87-233`):

- `FETCHER_BY_ENTITY: Record<ViewEntityType, string>` maps entity type → `fetchOrganizations` etc.
- `functionBody(source, name)` brace-matches, is string-aware (because `fetchDeals` contains a `sql`
  template whose `${` would otherwise be counted as a brace), and THROWS by name on 0 or 2+ matches.
- The anti-vacuity cell asserts each body is longer than 100 chars and `toContain("findMany")`.
- The discriminator cell asserts `deal` matches `filters?.stage` while `activity` does not, and
  `activity` matches `filters?.type` while `organization` does not.
- `EXPORTABLE_PAIRS` is asserted `toHaveLength(14)`.
- One `it.each` over those 14 pairs asserts `filters?.<key>` appears in that entity's body.
- A separate cell asserts `BODY_BY_ENTITY.deal` matches `filters?.pipeline` — narrows without
  authorizing.

After re-anchoring, `findMany` will no longer be in the extracted body. The replacement anchor must be
something only a real builder has: `isNull(` plus `conditions` are both present in every builder, and
the length floor still applies.

**The rendered-SQL half of the same file is unaffected** (`:265-400`): it drives `fetchFilteredData`
against the mocked `db` and renders whatever `findMany` received, so it measures the composed predicate
regardless of where it was built. It must stay green untouched, and that is itself a useful signal —
the extraction must not change one rendered byte.
