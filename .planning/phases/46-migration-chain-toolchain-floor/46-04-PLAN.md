<objective>
Build the behavioural half of DEPLOY-01: a repeatable check that creates a throwaway database, migrates
it from zero with `drizzle-kit migrate` and nothing else, compares the resulting **catalog** against the
expected schema, and drops the database in a `finally`.

Purpose: SC-1 and SC-3. Plan 46-01's static gate catches the class of defect that is visible in the SQL
text; only a real from-zero build proves the chain actually produces a working schema. And SC-3 is
explicit that the check must be observed FAILING on purpose before it is trusted — v1.3 shipped six
gates that could not fail, and NC-2 below is the one that matters most, because it must go red **while
`drizzle-kit migrate` itself still exits 0**.

**Do not grep for `migrations applied successfully!`.** `docs/admin/backup-restore.md:200-210` already
documents, with measured output, that drizzle prints the identical success line for 0 applied migrations
and for 20. A gate reading that line would be the seventh vacuous gate. Assert the catalog.

**Do not `diff` raw `pg_dump` output.** `pg_dump` from `postgres:16-alpine` emits
`\restrict <random-token>` lines whose token changes on every invocation, plus a `SET` preamble,
`OWNER TO` and a version banner. The host also has no `psql` and no `pg_dump` at all (verified). Nine to
ten catalog queries through the already-installed `postgres` driver are stronger, more readable, and run
unchanged on the host, in Docker and in CI.

Output: `scripts/migrate-from-zero.mjs` and the `db:check-migrations` npm script, plus NC-1 and NC-2
discharged with real recorded output. CI wiring is plan 46-05.
</objective>

**Connection resolution, in this precedence order.** `process.env.DATABASE_URL` first; otherwise parse a
single `DATABASE_URL=` assignment out of `.env` at `path.resolve(process.cwd(), ".env")` — the same one
file drizzle-kit's bundled dotenv reads (`bin.cjs:754`), so the script behaves identically to the
documented command. If neither yields a value, FATAL on stderr with the literal command that fixes it,
exit 1. Never accept a credential as an argv parameter, never print the connection string, and never
print a password: log the host, port and database name only.

**The three fences (S5).** Fence 1: the scratch name is generated as
`pipelite_migchk_${process.pid}_${Date.now()}` and MUST match `/^pipelite_migchk_[a-z0-9_]+$/` — FATAL
otherwise. This matters because a database identifier cannot be parameterised and is interpolated
directly into `CREATE DATABASE` / `DROP DATABASE`. Fence 2: the scratch name must not equal the
reference database name and must not equal the literal `pipelite` — FATAL otherwise. Fence 3: there is
no `DO $$` equivalent for `DROP DATABASE` (it cannot run inside a transaction), so the guard is
structural — every `CREATE DATABASE` / `DROP DATABASE` is issued on its own connection to the
`postgres` maintenance database, the pattern is re-checked immediately before each statement, and on the
scratch connection itself the script asserts `select current_database()` equals the scratch name before
running a single assertion. Issue a `DROP DATABASE IF EXISTS` on entry too, so a previously leaked
database cannot poison a run.

**Never issue a destructive statement against the reference database.** The reference is read with
`SELECT` only. Keep the reference database name in a constant named `REFERENCE_DB` and keep every
`drop`/`truncate`/`delete` token on a line that does not mention it — plan 46-05 adds this file to
`db-test-isolation.test.ts`'s line-oriented destructive-statement scan, which is exactly this rule
mechanised.

**Cleanup.** Wrap the whole body in `try { … } finally { … }`. The `finally` must contain BOTH the
`DROP DATABASE` and the `client.end()` calls, and must run even when the migrate step throws. This
combination has no in-repo analog — compose it from the fences above and `seed-admin.ts:61,94-96`.

**The from-zero build.** Create the scratch database, then spawn `drizzle-kit migrate` as a CHILD
PROCESS with `DATABASE_URL` set to the scratch URL in the child's env (dotenv's `override: false` means
this wins over `.env`). Derive the scratch URL by URL surgery in the `vitest.db.config.ts:75-79` style,
never by string concatenation. Capture the child's stdout AND stderr and echo them through verbatim —
`42P01` IS the diagnosis and swallowing stderr destroys the only useful output the failing case
produces. Record the exit code; do NOT branch the rest of the run on it alone.

**Assertion set A — snapshot equivalence. Unconditional, runs everywhere including CI.**
Read the LAST entry of `drizzle/meta/_journal.json`, load `drizzle/meta/<idx zero-padded to 4>_snapshot.json`,
and compare against the scratch database's catalog: the `public` table set equals the snapshot's table
names (strip the `public.` key prefix); the set of `table.column` pairs equals the snapshot's (293 at
plan time); and every index name the snapshot declares (41 at plan time) exists in
`pg_indexes where schemaname='public'` — a SUBSET assertion, because pg_indexes also reports
primary-key and unique-constraint indexes and reports 81 in total. Report set differences in BOTH
directions by name, never as a count. Every table-count query carries `table_schema = 'public'`.

**Assertion set B — reference equivalence. Runs when a reference database is reachable.**
Ten dimensions, exactly the queries in RESEARCH § Code Examples 3, each run against both databases,
sorted, and diffed: tables, columns (name/type/nullable/default/generated/char-length/numeric-precision/
generation-expression — **and NOT `ordinal_position`**, with the reason written inline so nobody
re-adds it), indexes, constraints, enums, functions, extensions, triggers, sequences, views. Report the
per-dimension verdict as a table in the `-> …` progress-echo style, and the actual differing rows on a
mismatch.

**Reference selection and skip rules for assertion set B — this must never become a silent pass, and
it must behave correctly in CI, where NO reference database exists.** Resolve the reference in this
exact order, and print the chosen branch:

1. `REFERENCE_DATABASE_URL` is set — that is the reference. Unreachable for any reason is FATAL.
2. Otherwise the candidate is the database named in `DATABASE_URL`.
3. Candidate does not exist — print `SKIPPED: reference equivalence — database <name> does not exist`,
   keep assertion set A authoritative, continue.
4. Candidate exists with **0** public tables — print
   `SKIPPED: reference equivalence — <name> has 0 public tables, so it is not a populated reference
   (this is the expected state in CI)`, continue. This is the branch plan 46-05's CI job takes: the
   workflow's Postgres service hands the script the `postgres` maintenance database.
5. Candidate exists with **between 1 and (snapshot table count − 1)** public tables — **FATAL**. A
   partially-populated reference is a misconfiguration, not an absence, and treating it as an absence
   is exactly how a skip turns into a silent pass.
6. Candidate exists with **at least the snapshot table count** — run the ten dimensions.
7. Auth failure, connection refused, wrong port — **always FATAL**, never a skip. Those are the shapes
   that would let a misconfiguration disguise itself as an absent reference.

`--require-reference` turns branches 3 and 4 into FATAL, so a caller that knows a reference exists can
demand it. The host run in this plan's acceptance criteria takes branch 6.
