<objective>
Put the from-zero migration check on the **required** CI job.

This is Route A, decided in CONTEXT and recommended by RESEARCH § Pitfall 7. Route B — a separate
`migrations.yml` workflow — was rejected because its new check-run name is not in the master ruleset, so
it could go red without blocking a merge until a maintainer manually adds it. **A non-blocking gate is a
vacuous gate**, which is the one thing this milestone exists to stop shipping. DEPLOY-01 is the
requirement the whole milestone is sequenced behind; a non-blocking check for it would be a weaker
guarantee than the one it replaces.

Route A has a same-commit trap. `src/lib/mutations/__tests__/db-test-isolation.test.ts:137-142` asserts
`ci.yml` contains neither `services:` nor `postgres`, and adding a Postgres service turns it red. That
assertion is a **blunt proxy** for a real invariant stated in the file's own header: the
`vitest.db.config.ts` project must never become reachable from the required `ci` check, because GitHub
treats a required check that never passes as permanently pending and that makes every pull request
unmergeable. The proxy must be replaced by assertions that express the invariant DIRECTLY, in the same
commit — never deleted, never weakened. The test's own comment invites exactly this: *"If a service
container were ever added the reasoning in this file would change, and it should change deliberately."*

Purpose: SC-3's "repeatable check" becomes a merge gate rather than a thing someone remembers to run.

Output: an amended `db-test-isolation.test.ts` asserting the real invariant per-step, with its
destructive-statement scan extended to cover `scripts/migrate-from-zero.mjs`; and a `ci.yml` carrying a
Postgres service and a `db:check-migrations` step. Amendment first and observed RED, then the workflow
change. Commits: `test(46-05): …` then `feat(46-05): …`.
