<objective>
Make a permanent delete permanent, without ever letting a storage failure roll one back.

`src/lib/trash/prune.ts:66-79` says it out loud today: *"NOT COVERED — UPLOADED FILE BLOBS ARE NOT
REMOVED. … purging the row destroys the REFERENCE and leaves the BYTES on disk (or in S3). … Do not
read the batch size below, or anything else in this module, as evidence that blobs are handled."* That
comment is honest and it must stop being true.

**`prune.ts` is NOT the transaction boundary, and this is the correction that decides the whole shape.**
It selects ids and delegates: `purgeRecordByType(entityType, id)` → `dispatch.ts:107` →
`purge{Entity}Mutation(id)`. Each of the four mutations **already pre-fetches the full unprojected
row**, so `customFields` is in scope at zero extra cost, and each has exactly one `db.transaction`
followed by a `return`. The insertion points are verified: `organizations.ts:646`, `people.ts:650`,
`deals.ts:754`, `activities.ts:504`. All four are symmetric — unlike SC-4, there is no per-entity
special case here.

**Post-commit, best-effort, never rethrowing.** SC-2 requires the purge to stay COMMITTED when storage
deletion fails; a throw would be the defect, not a diagnostic. Mirror `dedup.ts:627-651`, whose own
comment already explains why work like this lives outside the transaction.

**The mismatch goes in the LOG ONLY.** Widening `PurgeResult` would put **eleven exact
`toEqual({ success: true, detached: N })` assertions** in the blast radius — `activities.test.ts:878,898`;
`deals.test.ts:1011,1095,1127`; `organizations.test.ts:968,1010,1063`; `people.test.ts:936,996,1017`.
SC-2's criterion is a *log*, not a return value.

And **the proof must manufacture its own subject.** Measured: **zero `type='file'` definitions and zero
records carrying a stored file descriptor**, and `/app/uploads` is empty. A purge test that reaches for
existing data finds no blobs and passes on an empty set. CONTEXT.md flagged this; the ROADMAP does not.

Purpose: SEC-04's second half — the bytes, after the route.
Output: four post-commit blocks, a corrected comment, a corrected register entry, and a behavioural
proof including an injected failure.
