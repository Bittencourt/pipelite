<objective>
Close the three holes in the file route, and close the one that actually cannot be worked around.

`src/app/api/files/[entityId]/[fieldName]/[filename]/route.ts` is 139 lines and two handlers. Both do
`const session = await auth(); if (!session?.user) return 401` and then **nothing else** — no record
read, no ownership term, no containment. `GET` serves the bytes; `DELETE` unlinks them. **Any signed-in
user can download or destroy any file in the product**, given its URL, and the URL is recoverable from
the audit tombstone for **90 days** (`audit.retention_days = 90`, measured — the ROADMAP's earlier
"indefinitely" was false).

The user chose the widest of three options: **close all three holes, not just the one SEC-04 names.**
Ownership on `GET`; the identical guard on `DELETE`, because closing the read while leaving the
destructive verb open is not acceptable; and path containment, because
`path.resolve(UPLOAD_DIR, entityId, fieldName, filename)` interpolates three URL segments unvalidated.
Verified by execution: `path.resolve('/app/uploads','e1','f1','../../../../etc/passwd')` resolves to
`/etc/passwd`, and `path.resolve('/app/uploads','../../etc','f1','x')` to `/etc/f1/x` — **both
`filename` and `entityId` are escape vectors.**

Of the two containment checks, **the load-bearing one is the JSONB reference match**, not the prefix
test: require `record.customFields[fieldName]` to be an array containing a descriptor whose
`storedName` equals `filename`. That makes traversal *structurally* impossible — the filename must
already be a value the server wrote — and it makes the ownership check non-bypassable via a guessed
field name. Both go in, but if only one could be proven, it would be that one.

**SC-1 holds for `FILE_STORAGE=local` only.** Under `FILE_STORAGE=s3` the stored `publicUrl` is
`${S3_PUBLIC_URL}/${key}` (`upload/route.ts:89`), so reads never traverse this route and the guard
protects nothing in an S3 deployment. That is recorded as **SEC-49-A** and is out of scope. **No claim
of S3 coverage may appear in this plan's output.** `FILE_STORAGE` is unset in this deployment, so
`'local'` is the configuration under test. The guard is nonetheless placed BEFORE the storage branch,
so it applies to both branches — it simply has no traffic to protect in one of them.

Purpose: SEC-04's first half, which closes the exposure on its own and must land before any blob is
deleted.
Output: one new lib module, two guarded handlers, and a unit proof that invokes them directly.
