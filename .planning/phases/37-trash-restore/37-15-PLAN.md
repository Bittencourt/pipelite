Create `scripts/trash-checks.sql` following `scripts/audit-log-checks.sql` structurally.

Open with the header contract, stating: what each part proves; how to run it
(`docker compose exec -T postgres psql -U pipelite -d pipelite -f - < scripts/trash-checks.sql`); that
psql runs on the container's unix socket so no password is passed and none may ever be added to this file
or to the command line; and that the script is re-runnable and mutates nothing because every destructive
probe is wrapped in `BEGIN ... ROLLBACK` — with an explicit instruction not to unwrap them.

Six parts, each preceded by an `\echo` label:

  **Part 1 — the foreign-key inventory is unchanged.** Select every constraint in `pg_constraint` whose
  confrelid is one of the four CRM tables, projecting the constraint name, the child table and column,
  and `confdeltype`. The expected result is exactly the six rows listed in this plan's interfaces block,
  all with `confdeltype = 'a'`. If a seventh appears, or any becomes a cascade, the purge teardown is
  incomplete or has become redundant — either way this script is what says so. Include the expected
  count as an assertion, not just as a listing.

  **Part 2 — a bare DELETE still fails, per entity type.** Four `BEGIN ... ROLLBACK` blocks, each
  attempting a bare `DELETE` on a parent that has a child, and each expected to raise SQLSTATE 23503.
  Because psql aborts a transaction on error, run each probe in its own transaction and comment the
  expected error and constraint name above it. `activities` is the exception — it is a true leaf and its
  bare delete succeeds; include it so the asymmetry is documented rather than assumed. This part is the
  standing proof that the ordered teardown is necessary rather than defensive.

  **Part 3 — the full teardown succeeds, per entity type.** Four `BEGIN ... ROLLBACK` blocks, each
  replaying the mutation layer's ordering in SQL against a real trashed record (or, when none exists, a
  freshly inserted one created and rolled back inside the same transaction): delete the notes, delete the
  pure join rows, null the independent children's foreign keys, delete the row. Each block ends with the
  assertions that matter — zero rows remain in `notes` for that `(entity_type, entity_id)`, zero rows in
  `deal_assignees` and `deal_stage_history` for a purged deal, and every detached child's foreign key is
  now null while the child row itself still exists. Then `ROLLBACK`.

  **Part 4 — the audit log survived.** Inside one of the Part 3 transactions, assert that the record's
  pre-existing `audit_log` rows are still present after the parent row is gone. `audit_log.entity_id` has
  no foreign key by design, and this is the assertion that keeps it that way.

  **Part 5 — the seeded retention default is present as DATA.** `SELECT key, value FROM app_settings WHERE key = 'trash.retention_days'`,
  asserting exactly one row. If a future migration or a botched restore drops it, the pruner silently
  stops and this is what says so. Copy the framing of Part 3 of `audit-log-checks.sql`.

  **Part 6 — the pruner's expired-id query uses the index.** A rolled-back
  `EXPLAIN (ANALYZE, BUFFERS)` of `SELECT id FROM deals WHERE deleted_at < now() - make_interval(days => 30) LIMIT 200`,
  documenting the expected plan node (an index scan on `deals_deleted_at_idx`, not a sequential scan).
  RESEARCH measured `Index Scan Backward using deals_deleted_at_idx`, cost 2.785 ms, on the live
  25,207-row table. No index is added by this phase — all four `*_deleted_at_idx` btrees came from
  migration 0012 — and this part is what would catch that changing.

Every probe binds nothing and takes no parameter: the script is a fixed artifact, not a template. No
password appears anywhere in it.

| Boundary | Description |
|----------|-------------|
| mocked test database → real constraints | Every purge unit test mocks `db.delete`, which cannot raise a foreign-key violation |
| verification script → production data | A script that probes destructive behaviour against the real database |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-16 | Denial of Service | the purge teardown against real foreign keys | mitigate | `scripts/trash-checks.sql` Part 2 proves a bare delete still raises 23503 per entity type and Part 3 proves the full teardown succeeds. A mocked `db.delete` cannot establish either, which is why this script exists |
| T-37-07 | Repudiation | audit-log survival across a purge | mitigate | Part 4 asserts the record's prior `audit_log` rows are still present after the parent row is gone, inside the same rolled-back transaction |
| T-37-36 | Tampering | the verification script itself destroying data | mitigate | Every destructive probe is wrapped in `BEGIN ... ROLLBACK` with an explicit do-not-unwrap instruction, and the acceptance criteria require the four CRM tables' row counts to be identical before and after a run |
| T-37-37 | Information Disclosure | credentials in the verification path | mitigate | psql runs on the container's unix socket, so no password is passed on any command line and none may ever be added to the script. Asserted by grep |
| T-37-05 | Tampering | a dropped retention seed | mitigate | Part 5 asserts the `trash.retention_days` row exists as data; if a future migration or a botched restore removes it the pruner silently stops and this script is the standing detector |
| T-37-11 | Tampering | the Docker standalone build | mitigate | The phase gate re-runs the `[trash-prune] Starting` log grep after a rebuild, so a later change to the chunk layout is caught rather than silently disabling the policy |
| T-37-SC | Tampering | npm/pip/cargo installs | accept | This phase installs nothing (`37-RESEARCH.md § Package Legitimacy Audit`); the final gate run confirms `package.json` and the lockfile are unmodified |
