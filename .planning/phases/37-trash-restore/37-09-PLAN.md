<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| navigation entry → route | A menu item advertises a capability; the route itself is what must enforce authorization |
| confirmation copy → user decision | A dialog's claim about consequences is what a user consents on |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-24 | Elevation of Privilege | the `/trash` user-menu item | accept | The item is deliberately visible to every authenticated user, because trash is owner-scoped rather than admin-only. Visibility is not authorization: `/trash` scopes its own query by owner-or-admin (plan 37-07) and the purge control is gated separately (plans 37-10 and 37-13). A nav item is never the gate |
| T-37-25 | Elevation of Privilege | the `/admin/trash` sidebar and dashboard entries | mitigate | Both render only inside `/admin/*`, which `src/app/admin/layout.tsx` already redirects non-admins away from, and the retention server action re-checks the role itself (plan 37-08) |
| T-37-26 | Tampering | the six delete confirmations | mitigate | A confirmation that overstates the consequence is a consent defect: users who learn that "cannot be undone" is false stop reading the two dialogs where it is true. The correction is scoped to exactly six files and a grep assertion proves the two genuinely irreversible ones still say so |
| T-37-SC | Tampering | npm/pip/cargo installs | accept | This phase installs nothing (`37-RESEARCH.md § Package Legitimacy Audit`); zero new lucide symbols enter the product — `Trash2` is already in use |
