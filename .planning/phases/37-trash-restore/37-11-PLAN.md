  <action>
Create `src/lib/trash/prune.ts`, following `src/lib/audit/prune.ts` structurally rather than merely in
spirit.

Constants, each with a comment stating its reasoning:

  - `INITIAL_DELAY = 60_000` — same as the audit pruner; nothing here is time-critical and the server
    should finish booting first.
  - `TICK_INTERVAL = 24 * 60 * 60 * 1000` — daily. Retention is a window measured in days and the
    `trash.retention.windowHelp` copy already says "once a day".
  - `BATCH_SIZE = 200` — deliberately far smaller than the audit pruner's 5,000. A trash purge is a
    multi-statement teardown inside its own transaction per row, not one bulk `DELETE`, so the per-row
    cost is orders of magnitude higher. Comment that this is a tunable and that it should be measured
    once against a seeded batch.
  - `MAX_BATCHES_PER_TICK = 25` — a denial-of-service control, sized to the batch: at most 5,000 records
    per entity type per day, so at most one long-running window of write locks. Its cost is starvation
    if the delete rate exceeds it, and that is ACCEPTED precisely because the tick logs its total every
    time, so the shortfall is visible rather than silent.

`export function startTrashPruner(): void` logs
`[trash-prune] Starting with initial delay of 60s, ticking daily` and calls `scheduleTick(INITIAL_DELAY)`.
That exact log line is the deployment gate in Task 3, so it must be emitted unconditionally at start.

`function scheduleTick(delay: number): void` — MODULE-PRIVATE on purpose: an exported one would let a
caller start a second, overlapping chain. Inside a `setTimeout` callback:

  - `try` block: read `readTrashRetentionDays()`. When it is `null`, log
    `[trash-prune] retention unset or invalid — nothing purged` and do nothing else. FAIL CLOSED: `null`
    is what an unset, cleared, corrupted, out-of-range or pre-migration settings row produces. There is
    deliberately no code-level day fallback here — the 30-day default is a seeded `app_settings` row from
    migration 0015, and a code fallback would turn a tampered row back into an unbounded delete.
  - Otherwise, loop over `TRASH_PRUNE_ORDER` — activity, then deal, then person, then organization. The
    order is leaves-first and fixed so a parent is never purged while a sibling pass is still detaching
    from it; comment that, rather than iterating an object's keys and making the order incidental.
  - For each entity type, run up to `MAX_BATCHES_PER_TICK` batches. Each batch is one
    `db.execute` of `SELECT id FROM <table> WHERE deleted_at < now() - make_interval(days => ${days}) LIMIT ${BATCH_SIZE}`,
    served by the existing `*_deleted_at_idx`. The cutoff is computed SERVER-SIDE from a bound day count:
    a JS `Date` must never be bound into a raw drizzle `sql` fragment, because postgres.js throws
    `ERR_INVALID_ARG_TYPE` and the near-miss `${date}::timestamp` silently truncates microseconds
    (STATE.md Phase 35). Do NOT copy the `ctid` subselect from the audit pruner — it applies to a
    single-statement bulk delete and this is not one.
  - For each returned id, call `purgeRecordByType(entityType, id)` inside
    `runWithActor({ kind: "system", userId: null }, ...)`. Wrap each individual purge in its own
    try/catch so one bad record does not abort the batch, and log the failing id — identifiers only.
  - Break out of the batch loop when a batch comes back shorter than `BATCH_SIZE`: a short batch means
    nothing older is left.
  - Log `[trash-prune] purged N record(s) older than Xd` EVERY tick, even at zero.
  - `catch` logs `[trash-prune] Tick error:` with the error.
  - `scheduleTick(TICK_INTERVAL)` sits OUTSIDE the `try`, so a pruner that hits one bad read still runs
    tomorrow. A pruner that stops rescheduling is a silently disabled retention policy.

Never log a record's contents — identifiers and counts only.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `app_settings` row → automated deletion | Stored state that governs how much data a timer destroys, with no human in the loop |
| timer tick → database write locks | An unbounded tick is a self-inflicted denial of service |
| build pipeline → running container | A silently-dropped `instrumentation.js` disables the policy while the code says it is enabled |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-05 | Tampering | the tick's retention read | mitigate | `readTrashRetentionDays()` returning `null` means purge nothing, and the tick has no day fallback of its own. Tested by asserting the absence of BOTH the id query and the purge call |
| T-37-06 | Denial of Service | one long tick holding write locks | mitigate | `BATCH_SIZE = 200` and `MAX_BATCHES_PER_TICK = 25` bound the work per entity type per day. Starvation is accepted over lock contention BECAUSE the total is logged every tick, so the shortfall is visible |
| T-37-18 | Tampering | the cutoff arithmetic | mitigate | `now() - make_interval(days => ${days})` computed server-side from a bound integer; a JS `Date` is never bound into the raw fragment. Asserted on the rendered params |
| T-37-08 | Repudiation | the pruner's audit actor | mitigate | Every purge runs inside `runWithActor({ kind: "system", userId: null })` explicitly, so "no actor established" and "genuinely system" stay distinguishable rather than collapsing into the subscriber's fallback |
| T-37-29 | Denial of Service | a tick that stops rescheduling | mitigate | `scheduleTick(TICK_INTERVAL)` sits outside the `try`, and `scheduleTick` is module-private so no caller can start a second overlapping chain. Both asserted by test |

| T-37-30 | Information Disclosure | pruner logging | mitigate | Identifiers and counts only; a failing record is logged by id, never by content |
| T-37-SC | Tampering | npm/pip/cargo installs | accept | This phase installs nothing (`37-RESEARCH.md § Package Legitimacy Audit`) |
