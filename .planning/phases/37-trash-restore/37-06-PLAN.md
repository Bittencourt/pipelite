<objective>
Add the one place in the codebase that maps an `EntityType` to its restore and purge mutation, so the
server actions, the REST routes and the retention pruner all reach the same eight functions through
one exhaustive, compile-checked map instead of three hand-maintained switches.

Purpose: `restoreWithLinked` restores a record and its parents, which are of DIFFERENT entity types;
the pruner walks all four types in a fixed order; the REST routes accept the type as a path segment.
All three need dispatch, and three copies of a four-entry switch is how one of them silently drifts.
Output: `src/lib/trash/dispatch.ts` and its test.
</objective>

    - `restoreRecordByType("deal", "d1")` calls `restoreDealMutation("d1")` exactly once and returns its result unchanged — assert identity of the returned object, so no wrapper can silently reshape a failure into a success.
    - The same holds for `"person"`, `"organization"` and `"activity"` against their four functions.
    - `purgeRecordByType` dispatches to the four purge mutations the same way and forwards the `detached` count unchanged.
    - Dispatching one type never calls another type's mutation — assert the other seven spies were not called.
    - A `NOT_IN_TRASH` failure is forwarded verbatim, with its `error` string untouched, so the caller can still switch on the code.
    - A rejected mutation propagates the rejection rather than being swallowed — the dispatch adds no try/catch of its own, because each mutation already contains its own.
    - Both maps have exactly four keys and their key sets are equal — assert `Object.keys(...).sort()` equality against `["activity", "deal", "organization", "person"]`.

  <action>
Create `src/lib/trash/dispatch.ts`.

Declare the two result types as re-exported aliases so downstream callers do not have to import from
four mutation modules:

  - `export type RestoreResult = { success: true } | { success: false; error: string }`
  - `export type PurgeResult = { success: true; detached: number } | { success: false; error: string }`

Declare two module-private frozen maps typed as `Readonly<Record<EntityType, (id: string) => Promise<RestoreResult>>>`
and `Readonly<Record<EntityType, (id: string) => Promise<PurgeResult>>>`, populated with the eight
mutations. The `Record<EntityType, ...>` annotation is the whole point of this module: it is what makes
a fifth entity type a compile error in one place instead of a silent gap in three.

Export two thin functions:

  - `export function restoreRecordByType(entityType: EntityType, id: string): Promise<RestoreResult>`
  - `export function purgeRecordByType(entityType: EntityType, id: string): Promise<PurgeResult>`

Each looks up the map and calls it. Neither adds a try/catch, neither reshapes the result, and neither
performs an authorization check — authorization lives in the server action and the REST route, per the
Phase 24 decision recorded in STATE.md that mutations only check entity existence. Write that as a
comment so the next reader does not add a check here and create two places to audit.

Do NOT add a runtime `if (!fn) throw` fallback: `entityType` is typed as the closed `EntityType` union
and every caller narrows an untrusted string through `parseTrashTab` or `isTrashEntityType` before it
reaches here. A runtime fallback would make the compile-time exhaustiveness look optional.

Write `src/lib/trash/dispatch.test.ts` first (RED). Mock all four mutation modules with `vi.mock`,
exposing only the two functions each one contributes so an accidental import of a third surfaces as a
TypeError. Drive every one of the eight paths and assert both the forwarded result and the absence of
cross-calls.

Commit as `test(37-06): add failing tests for the trash restore/purge dispatch` then
`feat(37-06): add the trash restore/purge dispatch map`.
