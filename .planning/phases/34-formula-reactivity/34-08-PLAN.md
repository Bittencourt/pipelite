<objective>
Make the UI custom-field save path recalculate formulas, scoped precisely, without letting the browser write formula values.

Purpose: RESEARCH's consolidated answer to D-02 is blunt — covering "the mutation layer plus the v1 routes" misses write path #1, the single most-used one. `POST /api/custom-fields/save` calls `saveFieldValues(entityType, entityId, values)`, which does `db.update(table).set({ customFields: values })` with no read of the prior state, no diff, and no formula handling whatsoever (`src/lib/custom-fields.ts:123-143`). Two consequences: without a diff this path either recalculates unconditionally — directly violating SC-4 — or does not recalculate at all; and because `CustomFieldsSection` posts the whole `localValues` blob including the formula key, any authenticated user can set an arbitrary value on a server-derived field today.

The module has no test file at all. This plan creates one.

Output: `saveFieldValues` reads a pre-image, strips formula keys from client input, carries over stored formula values, diffs to a precise `changedFields`, persists, and recalculates.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/custom-fields/save` → whole-blob replacement | Any authenticated user posts an arbitrary object that becomes the entity's entire `custom_fields` value, with no per-key authorisation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-04 | Tampering | client-posted formula key | mitigate | `stripFormulaKeys` removes every formula-typed key from `values` before persistence, and the stored wrapper is carried over from the pre-image. Tested by posting `Margin: 999999` and asserting the persisted value is the stored wrapper. This closes the "an API caller can currently set any value on a formula field" hole RESEARCH named |
| T-34-20 | Tampering | whole-blob replacement wiping derived values | mitigate | The carry-over step in point 5 preserves every formula-typed key present in the pre-image. Without it, stripping would delete every stored formula value on every save — the D-06 failure mode inverted |
| T-34-21 | Elevation of Privilege | no per-entity ownership check on this route | accept | `src/app/api/custom-fields/save/route.ts` checks `auth()` only and performs no ownership check on `entityId` — a pre-existing condition since the custom-fields feature shipped, unchanged by this plan. This plan does not widen it: it strictly REDUCES what a caller can write, by removing formula keys from the accepted set. Record as a backlog item in plan 34-11 |
| T-34-03 | Denial of Service | recalc on every UI field edit | mitigate | The pre-image diff yields a precise `changedFields`, so an edit to a field no formula references produces zero evaluations. Deep comparison is required specifically so array-valued `multi_select` fields do not appear changed on every save |
| T-34-17 | Repudiation | recalc failure visibility | mitigate | Rejections are logged with a `[formula-recalc]` prefix; the save still returns success per D-05 |
| T-34-SC | Tampering | npm installs | accept | Zero new packages |
