<objective>
Wire the deal and activity write paths to `recalculateFormulas`, always before the event emit.

Purpose: this plan establishes the exact call pattern that plans 34-07, 34-09 and 34-10 replicate across the remaining write paths. The ordering is load-bearing and non-obvious: `events/subscribers/webhook.ts:19` forwards `payload.data` verbatim to `triggerWebhook`, and `triggers/matcher.ts:88` builds `envelope.data = { ...payload.data, ... }`. Both are snapshots of a JavaScript object captured at emit time, never a re-read. A test that only asserts on the database row cannot detect a wrong ordering — SC-1 would pass while SC-2 and SC-3 silently fail. So the tests here assert on the EMITTED PAYLOAD, not just on the persisted blob.

Output: `createDealMutation`, `updateDealMutation`, `updateDealStageMutation`, `reorderDealsMutation`, `createActivityMutation`, `updateActivityMutation`, `toggleActivityCompletionMutation` and `PUT /api/v1/activities/[id]` all recalculate before emitting.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API/UI caller → mutation `customFields` → stored JSONB | Client-supplied keys reach the database (enabled by plan 34-02) and could target a server-derived formula key |
| entity write → recalc write → `crmBus.emit` → webhook delivery / workflow run | The emitted payload now determines what external systems and workflow actions see |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-04 | Tampering | caller-supplied `customFields` on deals/activities | mitigate | `stripFormulaKeys` is applied before the insert/merge in every create and update path in this plan, and on the v1 activities `[id]` `custom_fields` merge. The server then overwrites formula keys with its own computed wrappers |
| T-34-03 | Denial of Service | `reorderDealsMutation` fan-out | mitigate | Reorder passes `changedFields: ["position"]`, which is absent from `ENTITY_NATIVE_ATTRIBUTES.deal`, so every call early-returns with zero evaluations. A shared `definitionsCache` bounds the definition query to one per reorder. The plan 34-04 budget still applies per call |
| T-34-17 | Repudiation | recalc failure visibility | mitigate | A rejected recalc is logged via `console.error` with a `[formula-recalc]` prefix rather than swallowed, and asserted by a test. The user's edit still succeeds per D-05 |
| T-34-18 | Elevation of Privilege | `PUT /api/v1/activities/[id]` missing ownership check | accept | Pre-existing IDOR recorded in the Phase 32 review; the route already permits any authenticated caller to update any activity. This plan neither fixes nor widens it — it adds no new field the caller controls beyond what plan 34-02 already enabled, and formula keys are stripped. Record as a backlog item in plan 34-11 |
| T-34-05 | Tampering | cascade from a deal save | accept | Saving a deal cascades to its activities regardless of activity ownership, per D-09. Bounded by the plan 34-04 budget and depth 1 |
| T-34-SC | Tampering | npm installs | accept | Zero new packages |
