Validated end to end during research. Do not drive a browser and do not add a Playwright spec — a
direct `curl` against `/api/upload` with the existing storage state is sufficient and much cheaper.

```bash
TOK=$(python3 -c "import json;d=json.load(open('$MAIN/e2e/.auth/admin.json'));print([c['value'] for c in d['cookies'] if c['name']=='__Secure-authjs.session-token'][0])")

  -H "Cookie: __Secure-authjs.session-token=$TOK" \
  -F "file=@/tmp/probe-upload.txt" -F "entityId=phase43probe" -F "fieldName=probefield"
```

Measured response (against the pre-fix container, hence the `/tmp/uploads` path):
```json
HTTP=200
{ "success": true,
  "file": { "id": "567f367d-…", "storedName": "567f367d-….txt",
            "path": "/tmp/uploads/phase43probe/probefield/567f367d-….txt",
            "publicUrl": "/api/files/phase43probe/probefield/567f367d-….txt",
            "size": 47, "mimeType": "text/plain" } }
```

Facts this establishes:
- `POST /api/upload` authorizes on `await auth()` alone (`route.ts:33-36`) — the session cookie is
  sufficient, there is **no CSRF token and no form-origin check**, which is why `curl` works.
- The required multipart fields are exactly `file`, `entityId`, `fieldName` (`route.ts:39-50`). Both ids
  are arbitrary strings and **no database row is needed** — which is what makes this probe small, and is
  necessary because there are **zero `file`-type custom field definitions** in this database.
- The cookie carries the `__Secure-` prefix because `.env` sets an https `NEXTAUTH_URL`. `curl` does not
  enforce cookie prefixes, so it works over plain HTTP on `localhost:3001`.
- **The storage state expires 2026-08-29T23:35.** If the probe returns 401, regenerate it —
  `cd "$MAIN" && npx playwright test e2e/auth.setup.ts` — rather than hand-crafting a token.

**Use the literal `phase43probe` as `entityId`.** It flows unsanitized into `path.resolve`
(pre-existing traversal debt, already logged in `.planning/STATE.md`). Do not widen it and do not
exercise it: no `..`, no absolute path, no encoded separator.
</the_probe>

<the_drill>

```bash

docker compose exec -T postgres createdb -U pipelite pipelite_restore_drill
docker compose exec -T postgres pg_restore -U pipelite -d pipelite_restore_drill \
  --no-owner --no-privileges < /tmp/pipelite-drill.dump

# Parity: a md5 over per-table row counts across BOTH schemas — 37 tables, one line of output
docker compose exec -T postgres sh -c '
Q="SELECT string_agg(format('"'"'SELECT %L AS t, count(*) FROM %I.%I'"'"', schemaname||'"'"'.'"'"'||tablename, schemaname, tablename), '"'"' UNION ALL '"'"') FROM pg_tables WHERE schemaname IN ('"'"'public'"'"','"'"'drizzle'"'"');"
SQL=$(psql -U pipelite -d pipelite -qAt -c "$Q")
psql -U pipelite -d pipelite               -qAt -c "$SQL" | sort | md5sum
psql -U pipelite -d pipelite_restore_drill -qAt -c "$SQL" | sort | md5sum'
# → 870a172d371b44a03f0941466e29cbcc for both (37 tables compared)

docker compose exec -T postgres dropdb -U pipelite pipelite_restore_drill
rm -f /tmp/pipelite-drill.dump
```

`unaccent 1.1`, `drizzle.__drizzle_migrations` 12 rows with `max(created_at) = 1787441440793` matching
live. The md5 is the right verification — it covers all 37 tables including the migration ledger, it is
one line, and it fails loudly. It does **not** verify column values.

**The research session's drill does not count.** Criterion 3 requires the restore to be exercised as
part of the work, and the phase's version must also cover the uploads volume, which did not exist when
