### Mandatory colour repair — C-1

`src/components/user-menu.tsx:87` uses `className="text-red-600 focus:text-red-600"` on the sign-out
item. It **must become `text-destructive focus:text-destructive`.**

This is in scope for a specific reason and not a drive-by: this phase makes dark mode reachable for
the first time, and `red-600` (`#dc2626`) on the dark popover surface (`oklch(0.205 0 0)`) is roughly
3.4:1 — below the 4.5:1 AA text threshold. `--destructive` carries a lightened dark-mode value
(`oklch(0.704 …)`) precisely so this works in both themes. The file is already being edited for the
theme toggle, so the cost is one line.

**Out of scope, stated so the checker does not flag it:** 234 hardcoded palette utilities across 45
other `.tsx` files. A repo-wide token sweep is a separate phase. The rule for *this* phase is narrow
and enforceable: **zero hardcoded palette colours in the nine files this phase touches.**

## Theme Contract

### T-1 — Provider (locked)

`ThemeProvider` from `next-themes@^0.4.6` in `src/app/layout.tsx`, with exactly:
`attribute="class"`, `defaultTheme="system"`, `enableSystem`, `disableTransitionOnChange`.

### T-2 — `suppressHydrationWarning` on `<html>` (locked)

Mandatory. next-themes writes the class before hydration.

### T-3 — Nesting

Mount inside the existing `NextIntlClientProvider` → `HotkeysProvider` chain without restructuring
it. The theme provider has no dependency on locale and locale has none on theme, so either order
works; nesting *inside* `NextIntlClientProvider` keeps the existing tree diff to one wrapper.

### T-4 — Toggle placement and shape **[DISCRETION RESOLVED: submenu vs flat items]**

**Flat, not a submenu.** In `UserMenu`, above the existing final `DropdownMenuSeparator`:

```
DropdownMenuSeparator
DropdownMenuLabel  → theme.label            (Label typography, font-normal)
DropdownMenuRadioGroup value={theme ?? "system"} onValueChange={setTheme}
  DropdownMenuRadioItem value="light"   → Sun     + theme.light
  DropdownMenuRadioItem value="dark"    → Moon    + theme.dark
  DropdownMenuRadioItem value="system"  → Monitor + theme.system
```

Rationale for flat over `DropdownMenuSub`: this phase's headline concern is a 320px viewport. A
224px-wide (`w-56`) menu spawning a nested panel inside a 305px client width has nowhere to open —
Radix will flip or clamp it, and nested menus are hostile to touch besides. Three flat rows cost
~96px of vertical space in a menu that has room, show the current selection as a radio dot with no
extra affordance, and each row is a full-width tap target.

Icons: `Sun`, `Moon`, `Monitor` from lucide, `mr-2 h-4 w-4` — matching the four existing items in
this menu exactly.

### T-5 — Three-way, because "system" is a real state (locked)

`defaultTheme="system"` makes "system" the initial value; a two-way toggle would strand the user
outside OS-following forever. The radio group's three values are the complete set — there is no
fourth state and no "auto" alias.

### T-6 — No hydration gate is needed, and this is verified, not assumed

The standard next-themes recipe wraps theme-dependent UI in a `mounted` flag set from an effect.
**Do not add one here.** Two reasons, both load-bearing:

1. `react-hooks/set-state-in-effect` is an **ERROR** in this repo (three Phase 38 plans hit it on
   code their own spec had specified). `useEffect(() => setMounted(true), [])` fails the lint gate.
   The existing suppression in `src/components/ui/relative-time.tsx` is a documented deferral, not a
   pattern to copy.
2. It is unnecessary. `MenuPortal` renders `Presence present={forceMount || context.open}` and
   shadcn's `DropdownMenuContent` passes **no** `forceMount` to the Portal
   (`node_modules/@radix-ui/react-menu/dist/index.mjs:109`), so a closed menu renders nothing at all.
   The radio items therefore never exist during SSR or hydration — they first mount on a user click,
   long after next-themes has read `localStorage`. There is no mismatch to guard.

Consequence: the inert `forceMount` on `user-menu.tsx:48` may be left exactly as-is. It is not load-
bearing either way, and removing it is not part of this contract.

### T-7 — Free fix to record

`src/components/ui/sonner.tsx` already calls `useTheme()` and today always reads the default because
no provider is mounted. Mounting one makes the toaster follow the theme with no edit to that file.
State this in the plan rather than "fixing" sonner.

### T-8 — Persistence

next-themes' default `localStorage` key (`theme`) with no override. SC-2 ("the choice survives a
reload") is satisfied by the library; no cookie, no server round-trip, no user-settings column.

### T-9 — Dark-mode readiness of the nine touched files

All nine already use tokens (`bg-background/95`, `bg-muted/30`, `bg-background`, `text-muted-
foreground`, `Alert variant="destructive"`, which carries its own `dark:` variants). The single
exception is C-1. Verify each changed surface in dark mode; do **not** open a repo-wide sweep.

## Bulk-Failure Copy Contract

The panel currently renders `bulk.failures.retryHint` unconditionally. The caller keeps failed ids in
`rowSelection` (`handleOutcome`) but the effective selection is intersected with the loaded rows
(`selectedIds = keys(rowSelection) ∩ loadedIds`), so for the `no longer exists` reason code the
sentence is false: 0 checked, bar unmounted, panel still instructing a retry.

**Fix by conditioning the copy on what survived the prune, never by re-selecting vanished ids** —
locked. Re-selecting would reintroduce ids the table cannot render, which is what the prune exists to
prevent.

### New prop

`BulkFailureReport` receives the count of failed ids **still present in the rendered data**. The
caller owns the computation, because the caller owns `data`:
`failures.filter(f => loadedIds.has(f.id)).length`. The component must not be handed the row array
and must not recompute the intersection — it renders a truth it is told.

### Three branches, one per truth condition

| Condition | Key | Renders |
|-----------|-----|---------|
| `stillSelected === failures.length` | `bulk.failures.retryHint` **(unchanged text)** | "These records are still selected. Fix the problem and try again." |
| `0 < stillSelected < failures.length` | `bulk.failures.retryHintPartial` with `{count: stillSelected}` | "2 of these records are still selected. The rest have left this list — refresh to see what's there now." |
| `stillSelected === 0` | `bulk.failures.prunedHint` | "These records have left this list. Refresh to see what's there now." |

**On the third branch, "fix the problem and try again" is actively wrong advice** and must not appear
in any form — the records are gone, so there is nothing to retry against.

**Note on the second branch.** CONTEXT names two keys (keep `retryHint`, add one sibling for the
pruned case). The partial branch is an *elaboration* of the locked rationale — "the panel states only
what is true" — not a departure from it: with 5 failures of which 2 survived, both of the two-key
options assert something false. Key naming is explicitly delegated to discretion.
**[DISCRETION RESOLVED: key naming]**

### Unchanged in this component

- No cap on the list. Forty failures render as forty rows (`max-h-48` scroll box). The panel's header
  comment explains why; **update that comment for the new branching, do not contradict it.**
- No timer, no auto-dismiss.
- The reason is a code translated via `t("reason.<code>")`, never a server sentence.
- Colour is never the sole carrier: each branch's sentence differs in words, not only in tone.
- `Alert variant="destructive"` keeps its border-and-foreground-only treatment (no fill).
- Position: above the table, below the search/filter row, outside the fixed bulk bar.

## Verification Surfaces

### V-1 — The 320px regression check runs in Playwright **[DISCRETION RESOLVED]**

CONTEXT flagged the choice and named the disqualifier: jsdom computes no layout, so
`scrollWidth <= clientWidth` there is vacuously true. The check therefore runs as a Playwright spec
inside the new minimal harness — the only instrument in the plan that measures real layout.

| Parameter | Value |
|-----------|-------|
| Viewport | 320 × 640 |
| Routes | `/organizations`, `/people`, `/deals`, `/activities`, `/trash`, `/admin/audit` |
| Locales | `en-US`, `pt-BR`, `es-ES` — set by writing the `locale` cookie (`src/i18n/request.ts` reads exactly that cookie, so no UI navigation is needed) |
| Assertion | `document.documentElement.scrollWidth <= document.documentElement.clientWidth` |
| Matrix | 18 assertions |
| Auth | all six routes are session-gated, and `/admin/audit` additionally requires `role: "admin"` — the harness needs a real authenticated admin session |
| Anti-vacuity anchor | the spec must fail if the page never loaded. Assert a known per-route element is visible before measuring; a blank 200 has `scrollWidth === clientWidth` and would pass silently. |

**es-ES is not optional.** It measures worse than pt-BR (526 vs 508) and the es-ES-worse-than-pt-BR
asymmetry is the exact failure mode the original Phase 36 UAT item was written to catch.

### V-2 — The deals-drag spec (locked)

One config plus one spec covering drag-with-selection **and** the G1 Escape regression. It must emit a
held pointer sequence satisfying dnd-kit's activation constraint (press, intermediate `pointermove`s,
release) — a move-and-up times out, which is why `browser_drag` could not close this.

Synthetic `KeyboardEvent`/`PointerEvent` dispatch remains **refused as evidence**: G1 proved synthetic
dispatch hides a real defect on this exact component, and the in-browser `computer` key action
delivers zero key events to the page in this environment.

### V-3 — Harness boundaries (locked)

One config, one spec file (plus V-1's viewport spec). Not a migration of the existing 2086-test suite,
and **not** a prerequisite for Phases 39–43. It must not become a required gate for unrelated work.

### V-4 — Dark mode is load-bearing for the whole project

While it is unreachable, every "check it in dark mode" UAT item anywhere in Pipelite is unverifiable
as a real user state. Sequence the theme provider early in the phase so later plans can actually use
dark mode as a verification surface.
