<objective>
Stop the bulk failure panel asserting a selection state that is not true.

Purpose: the panel renders "these records are still selected — fix the problem and try again"
unconditionally, but the caller prunes its effective selection to rendered ids. For the
`no longer exists` reason code the failed rows have left the table and the selection is empty:
0 checked, bulk bar unmounted, panel still instructing a retry. This is not an artefact of a forced
test — it is exactly what happens when another user deletes the records concurrently.

Output: a `stillSelected` number prop, three mutually exclusive copy branches, four callers passing
the computed count, and two extended/new source gates.
</objective>

<!-- The prop contract. Fixed here; all four callers implement it. -->

BulkFailureReportProps gains exactly one member:
  stillSelected: number      // count of `failures` whose id is still in the caller's rendered set

The three branches, mutually exclusive, one per truth condition:
  stillSelected === failures.length   -> t("failures.retryHint")                       (text UNCHANGED)
  0 < stillSelected < failures.length -> t("failures.retryHintPartial", { count: stillSelected })
  stillSelected === 0                 -> t("failures.prunedHint")
Both new keys are delivered by 45-01. "fix the problem and try again" must not appear in any form on
the third branch — the records are gone, so there is nothing to retry against.

The four callers, all verified by direct read — every one already has its set in scope at the
render site, so NO caller needs a new derivation:

  file                                        set           set at   <BulkFailureReport> at  form
  src/app/organizations/data-table.tsx        loadedIds     155      324                     {cond && (…)}
  src/app/people/data-table.tsx               loadedIds     185      282                     {cond ? (…) : null}
  src/app/activities/activities-client.tsx    loadedIds     110      292                     {cond && (…)}
  src/app/deals/kanban-board.tsx              renderedIds   136-144  515                     {cond && (…)}

Both `loadedIds` and `renderedIds` are `Set<string>`, so `.has(f.id)` reads identically at all four
sites. The kanban's set is built by looping open stages only (won/lost render summary tiles and no
cards, so nothing there is ever selectable) — that difference is intentional and must survive.

Why intersect against the loaded/rendered set and NOT against `rowSelection`: `handleOutcome`
re-asserts EVERY failed id into `rowSelection` unconditionally
(`organizations/data-table.tsx:232-247`), so `rowSelection[failedId]` is always true. The only thing
that can drop a failed row from the effective selection is it leaving `data`. `failed ∩ loadedIds`
is therefore exactly the "still selected" set.
