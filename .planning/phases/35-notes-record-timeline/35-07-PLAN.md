## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated caller → note mutation | Authentication is already established by the caller; this module decides authorization for edit and delete |
| API-key context → role | `ApiAuthContext` carries no role, so the role must be re-read from the database rather than trusted from the request |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-03 | Elevation of Privilege | IDOR — editing or deleting another user's note by guessing a note id | mitigate | `isAuthorOrAdmin` returns false for a non-author member; enforced server-side in BOTH the action (35-09) and the route (35-10). Note ids are v4 UUIDs, but unguessability is defence in depth, not the control |
| T-35-09 | Elevation of Privilege | authorization drift between the server action and the v1 route | mitigate | One exported predicate, unit-tested once, imported by both call sites. Plans 35-09 and 35-10 each carry a grep gate asserting they import `isAuthorOrAdmin` from this module rather than inlining a check |
| T-35-24 | Elevation of Privilege | privilege escalation via a role claimed in a request instead of read from storage | mitigate | `resolveActorRole` reads `users.role` from the database for the API-key surface; the server action reads it from the signed Auth.js session. No caller-supplied role is ever accepted |
| T-35-25 | Elevation of Privilege | failing open when the role lookup errors | mitigate | `resolveActorRole` returns `null` on any caught error, and `isAuthorOrAdmin(note, null)` is `false` |
| T-35-SC | Tampering | npm installs | accept | Zero packages installed |
