<objective>
Build the browser-facing surface for notes: four server actions that authenticate with the Auth.js
session, authorize with the shared predicate, delegate persistence to the mutation layer, and
revalidate the record's detail page.

Purpose (TDD): the session is the source of the author id and of the admin role, so "who is allowed
to do what" is testable as a matrix before any UI exists. This is also new ground for the repo — no
existing test mocks `@/auth` — so the scaffold is worth getting right once.
Output: `src/app/notes/actions.ts` + `src/app/notes/actions.test.ts`.

Why server actions and not `/api/v1`: `/api/v1/**` authenticates with a Bearer API key via
`withApiAuth` and does not read the session cookie. A browser has no API key. The UI must therefore
call server actions; the v1 routes built in plan 35-10 exist for external consumers and share the
same mutation layer.
</objective>

Create `src/app/notes/actions.ts` implementing the `<interfaces>` contract. `"use server"` must be
the first line.

Every action starts with `const session = await auth()` and
`if (!session?.user?.id) return { success: false, error: "Not authenticated" }`.

`addNote(entityType, entityId, content)`
- Builds the actor from the session and calls `createNoteMutation({ entityType, entityId, content, authorId: session.user.id })`.
  The action signature deliberately has NO authorId parameter — attribution comes from the signed
  session only (T-35-28).
- On success, hydrate the created row into a `NoteTimelineEntry` (author name/email from the
  session user is acceptable here, or re-read via the notes source's `hydrate`) and return it, so
  the client can prepend optimistically without a refetch.
- `revalidatePath(\`/${segmentFor(entityType)}/${entityId}\`)` on success only.

`editNote(noteId, content)`
- `const note = await findNoteById(noteId)`; if null return a generic not-found error.
- `const actor = { userId: session.user.id, role: session.user.role }`.
- `if (!isAuthorOrAdmin(note, actor)) return { success: false, error: <notPermitted> }`. Import the
  predicate — do NOT re-implement the check inline. The equivalent inline check exists at three
  sites in `src/app/organizations/actions.ts` and that drift is exactly what this phase avoids.
- Delegate to `updateNoteMutation`, then revalidate using the note's own `entityType`/`entityId`.

`deleteNote(noteId)`
- Same lookup + `isAuthorOrAdmin` gate, then `softDeleteNoteMutation`. Never a hard delete.

`loadMoreTimeline(entityType, entityId, cursor)`
- Session guard, then `assembleTimeline({ entityType, entityId, cursor })`. The cursor is passed
  through as the opaque encoded string; `assembleTimeline` decodes and validates it. Do not decode
  it here and do not trust it.

Shared helper `segmentFor(entityType)` mapping `deal → 'deals'`, `organization → 'organizations'`,
`person → 'people'`, `activity → 'activities'`. Keep it in this file.

Error handling: wrap each action body in try/catch, `console.error("<action> failed:", error)` and
return a generic `{ success: false, error }`. Never surface a raw Postgres error to the client
(T-35-10).

Note for the SUMMARY: no `note.created` crmBus event is emitted anywhere (D-15), so `revalidatePath`
is the only cache invalidation in this phase. Workflows cannot react to notes yet — by design.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → server action | Fully untrusted arguments over an authenticated session; the session cookie is the only trusted input |
| server action → mutation layer | Authorization must be decided here, because the mutation layer deliberately does not decide it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-03 | Elevation of Privilege | IDOR on `editNote` / `deleteNote` | mitigate | `findNoteById` then `isAuthorOrAdmin(note, actor)` before any mutation; asserted by the "may not edit another user's note" tests which also assert the mutation was never called |
| T-35-09 | Elevation of Privilege | authorization drift versus the v1 route | mitigate | Imports the shared predicate; grep gate forbids an inline `role === 'admin'` comparison in this file |
| T-35-28 | Spoofing | forged note attribution by passing an authorId | mitigate | `addNote` has no `authorId` parameter; the value comes from `session.user.id` only, asserted by the "takes authorId from the session" test |
| T-35-10 | Information Disclosure | raw Postgres error or existence oracle returned to the browser | mitigate | try/catch with `console.error` for detail and a generic `{ success:false, error }` string; a missing note and a soft-deleted note return the same generic refusal |
| T-35-02 | Tampering | cursor injection via `loadMoreTimeline` | mitigate | The cursor is passed through opaquely to `assembleTimeline`, which decodes and zod-validates it (plans 35-05/35-08). This action never decodes or trusts it |
| T-35-29 | Denial of Service | unbounded note content submitted from the browser | mitigate | Delegated to `createNoteMutation`'s `NOTE_CONTENT_MAX` zod cap (plan 35-04) |
| T-35-SC | Tampering | npm installs | accept | Zero packages installed |
</threat_model>
