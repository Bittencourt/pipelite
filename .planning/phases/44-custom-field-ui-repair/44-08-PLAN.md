<serialization_note>
Read this before writing any code — it changes the shape of the optimisation.

`page.tsx` passes the **same array reference** to `FieldsList` and to `AddFieldButton`. React Flight
maintains a written-objects map and emits a back-reference for an object it has already serialized,
so that array costs bytes once, not twice. Introducing a *separate* slim array for `availableFields`
would therefore ADD roughly 155 newly-serialized objects on top of the full rows `FieldsList` still
requires — a net payload increase, the opposite of the decision's intent.

`FieldsList` genuinely needs more than three keys: it renders `name`, `type`, `required` and
`showInList`, uses `id` for sorting and archiving, and hands the whole row to `FieldDialog` as
`field` for the edit dialog, which reads `config` for select options and formula expressions. So
`config` reaches the browser either way.

What is genuinely unread by any client code in this route: `createdAt`, `updatedAt`, `deletedAt`
(the server has already split active from archived), `position` (reordering posts ids only) and
`entityType` (passed separately as its own prop).

The optimisation that is both real and consistent with D-44-02 is therefore:
project **once** at the server into a row type containing only the keys the browser reads, share that
one array between both consumers, and narrow `FieldDialog`'s `availableFields` declaration to
`{id,name,type}` so the contract states what it actually consumes. A `Pick` with more keys is
structurally assignable to the slim one, so no cast is needed.
</serialization_note>
