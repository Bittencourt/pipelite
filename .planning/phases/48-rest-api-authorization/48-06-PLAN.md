<objective>
Prove SC-3 with a proof that can fail.

**The criterion was vacuous by construction.** Measured on the live database:
`select owner_id, count(*) from activities group by 1` returns **ONE row** — all **79,022** activities
belong to a single user, who is an admin. A correctly-scoped query and a completely unscoped query
return the identical number for the only user who has any data, so the original criterion was satisfied
**today, by the broken route**. The AMENDED SC-3 requires a discriminator (at least two owners each
holding at least one activity), a floor, a ceiling and a cross-check.

**And a mocked test cannot substitute.** A mocked `findMany` ignores its `where`; that is not a
hypothesis, it is the measured finding of SEC-48-B. So this runs in the db vitest project against real
PostgreSQL, through the real `withApiAuth`, with two real API keys — which is literally what CONTEXT
requires: *"two distinct users with real API credentials, and the negative case must be a genuine
cross-user request — not a mocked-out authorization result."*

**There is zero precedent in this repository for minting an API key in a test.** No file under `src/`
or `e2e/` references `apiKeys` or `api_keys`. This plan writes that fixture.

Purpose: SEC-01, ROADMAP SC-3 as amended.
Output: a reusable two-user API-key fixture, a seeded discriminating DB test, and negative controls D
(scope ablated) and E (single-owner dataset).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API key holder → `GET /api/v1/activities` | The collection query decides how much of the table crosses back to an authenticated but unauthorized principal. |
| the test process → the operator's live database | A misconfigured `DATABASE_URL` would point destructive fixture code at ~79,000 real activities. |
| minted plaintext key → `api_keys.key_hash` | The fixture must store a digest, not the key, or the test would encode a weaker storage model than production. |
