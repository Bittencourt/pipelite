<objective>
`GET /api/v1/stages` fetches a global page of stages, derives a JavaScript array of pipeline ids from it,
and interpolates that array into a raw SQL fragment. When the array is empty the statement becomes
`"pipelines"."id" IN ()` and PostgreSQL rejects it with `42601`.

**QG-03 is a LIVE HTTP 500, not latent.** ROADMAP SC-5's original text named a `stageList` non-empty
guard that does not exist — `:69` is `if (!pipelineId)`, the absence of a *filter parameter*.
`parsePagination` imposes no ceiling on `offset`, so `GET /api/v1/stages?offset=73` reaches it from the
public API with one query parameter. **The AMENDED SC-5 is the contract: 500 today, 200 with `data: []`
after, proven behaviourally and without ablation.**

The same route also paginates before it authorizes: measured, `?limit=5` returned `data: []` with
`meta.total: 1` for the stage's own owner. The correct predicate already exists in the file, twelve lines
below the defect, in the count query at `:84-93`.

Purpose: QG-03, plus the F3 correctness bug. The behavioural 500→200 proof is plan 48-07; this plan owns
the fix and its CI-visible structural assertions.
Output: one shared predicate builder, a joined list query paginated after the predicate, and a
base-project test that binds the route to the predicate.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `?offset=` query parameter → SQL statement text | An unbounded caller-controlled integer decides whether a JavaScript array is empty and therefore whether the emitted statement is syntactically valid. |
| `?pipeline_id=` query parameter → the list predicate | A caller-supplied filter reaches the same `where` as the ownership scope. |
| Global stage page → JavaScript post-filter | Rows the caller does not own cross the database boundary before being discarded in application code. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-48-04-01 | Denial of Service | `GET /api/v1/stages?offset=<count>` emitting `IN ()` and dying `42601` | mitigate | the array is deleted with the JavaScript post-filter; the predicate is a static join condition with bound parameters. Behavioural proof in plan 48-07 |
| T-48-04-02 | Information Disclosure | rows the caller does not own being read from the database before being filtered in application code | mitigate | `innerJoin` plus `ownedStagesPredicate` scope the read itself; no foreign row is fetched |
| T-48-04-03 | Denial of Service (self-denial) | a stage's own owner receiving `data: []` with `meta.total: 1` | mitigate | pagination moved after the predicate; asserted by the method-ordering record in the chainable stub |
| T-48-04-04 | Tampering | page and total drifting apart so `meta.total` stops bounding the page | mitigate | one `ownedStagesPredicate` call feeds both `where`s; asserted by an identical-render comparison and ablated in Task 3 |
| T-48-04-05 | Injection | a JavaScript array interpolated into a raw SQL fragment | mitigate | the raw fragment is deleted. Note the measured finding: for NON-empty arrays drizzle expanded the array into placeholders, so this was a robustness and availability defect, not a SQL-injection defect. Do not overstate it |
| T-48-04-06 | Spoofing | the predicate correct in the helper but unused by the route | mitigate | the route-binding assertion renders the route's captured `where` and compares it to the helper's own render |
| T-48-04-07 | Tampering | a future refactor reintroducing a raw `IN` over a JS array elsewhere | accept, with a named owner | out of this route's scope; the Q10 gate in plan 48-08 is a presence gate over authorization, not over SQL construction. Recorded rather than silently assumed covered |
