assertions timing out — **none of them the two this phase fixed**. Same mechanism 47-03 repaired
(module import cost paid inside a test), different population: dynamic imports in test **bodies**,

`suite-hook-hygiene.test.ts` is green and non-vacuous but its corpus is **lifecycle hooks only**, so

gate's corpus to cover it.

Without this, the phase goal — *"a red test run means a defect"* — is measurably false in exactly the
multi-worktree, high-oversubscription environment where the milestone's own executors run.
</objective>

<task id="2" tdd="true">
<name>Hoist the 112 hoistable dynamic imports to static module-scope imports</name>

<action>
In each of the 9 set-(A) files, replace `await import("...")` inside test bodies with a static
module-scope import, exactly as 47-03 did for `toggle.test.ts` and `recursion.test.ts`.

`vi.mock` is hoisted above imports, so a static import is safe **only because** the mock hoists above
it. Where a `vi.mock` factory closes over `vi.hoisted` consts, the two cannot move independently —
47-03 hit this in `recursion.test.ts`, where the `vi.mock` sat inside a `describe`; move both to module
scope together. vitest 4.1.11 warns that a nested `vi.mock` "will become an error in a future version",
so leaving one nested makes the fix depend on a guarantee scheduled for removal.

**Every file must keep its exact test count.** Verify per file, before and after, with
`--reporter=json` — not by eyeball. A hoist that changes behaviour is a defect, not a speedup.

If a file resists hoisting for a real reason discovered during the work — a genuine per-test module
instance requirement the scan did not detect — do NOT force it. Add it to the carve-out with the
reason, assert the live control on it, and say so in the SUMMARY. An honest carve-out beats a broken
hoist.
</action>
