<recorded_decisions>
**D-A4 / auth is SESSION-ONLY for both `replayWorkflowRun` and `startDryRun`, not admin.** RESEARCH
requires this choice be recorded, and CONTEXT's own amendment block already settles it: *"Auth on replay
is session-only, not `replayDelivery`'s admin gate. An admin gate would 403 exactly the non-admin users
the page renders the button to."* The evidence: the run detail page has no role check, and
`run-changed-records.tsx:117-120` documents that omission as deliberate — *"workflows are not
owner-scoped in this product"*. STATE.md § Decisions records *"Workflows not owner-scoped; all
authenticated users can CRUD any workflow"*, and `triggerManualRun` has no role gate at all. A user who
can already edit and manually trigger any workflow gains no new capability from replay. CONTEXT's
code-context note saying the pattern is mirrored "including its admin gate" describes `replayDelivery`;
it is not a security requirement for a different surface.

**`startDryRun` must NOT check `workflow.active`** (Pitfall 8). `triggerManualRun` rejects inactive
workflows, correctly, since every other trigger path does. Copying that check here makes it impossible
to test an unproven, not-yet-activated workflow — which is the primary use case, because the phase goal
is literally *"a failed or **unproven** workflow"*.

**`replayedFromRunId` stays DIAGNOSTIC, never a guard.** Do not add a chain-length check anywhere.
Walking the chain needs a recursive query per replay, the chain is human-driven so no bound is
principled, and CONTEXT is explicit that the column is diagnostic (rendered as the lineage line, one
direction only).

**No hand-rolled insert.** Both actions go through `createWorkflowRun`, which owns the
`MAX_RECURSION_DEPTH` short-circuit. A bespoke `db.insert(workflowRuns)` in the action bypasses the
recursion guard entirely.
</recorded_decisions>
