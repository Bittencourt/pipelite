<objective>
Set `ExecutionContext._dryRun` from the `workflow_runs.dryRun` COLUMN on every engine entry, and make a
delay node a no-op under dry run in both places delays are handled.

Purpose: this is the enforcement point for "no CRM mutation", and where it reads the flag from is the
whole security property. The engine restores `context` from a mutable `jsonb` blob a few lines above
the assignment site (`engine.ts:152-161`); if the flag came from there, a hand-edited context row could
turn a dry run into a real one mid-execution — the one thing the flag exists to prevent. And CONTEXT
amendment A2 is a self-inflicted-outage fix: a dry run that hits a delay parks as `waiting`, and the
processor's serial-enforcement clause then blocks *every real run of that workflow* until the delay
resolves, up to the 30-day cap.
Output: two lines in `engine.ts` plus one condition in each of the two delay branches, gated by
`engine.test.ts`.
</objective>

Open Question 1 left open, and it overrides RESEARCH's own framing of it as a judgment call. The
accepted cost, stated so nobody later files it as a bug: **a dry run does not exercise delay
resolution, so a misconfigured delay is not caught by dry-running.** The two alternatives were worse —

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `workflow_runs.context` jsonb → the engine | a mutable blob restored on every resume; it must never decide whether a run is dry |
| the engine's context → QuickJS (`transform`, `condition`) | user-authored JS runs against this object; anything visible there is attacker-influenced control flow |
| a dry run's `waiting` row → every real run of the same workflow | serial enforcement makes one parked test run a production outage |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-41-23 | Tampering | `context._dryRun` derivation | mitigate | assigned from `run.dryRun === true` BELOW the context restore, so the column is authoritative on every entry including a delay resume. Asserted in both directions: a persisted `_dryRun: true` with a `false` column yields `false` |
| T-41-24 | Elevation of privilege | `_dryRun` visibility inside QuickJS | mitigate | `transform.ts` injects only `{ trigger, nodes }`, asserted as an exact key set. If user JS could branch on `_dryRun`, a workflow could behave differently under test than in production and the whole exercise would be a lie |
| T-41-25 | Denial of service | a dry run parking as `waiting` | mitigate | A2: both delay branches no-op under dry run. Without this, one test run of a workflow with a 30-day delay blocks every real run of that workflow for 30 days via `execution-processor.ts:122-127` |
| T-41-26 | Tampering | `=== true` vs coercion | mitigate | strict comparison, so a pre-migration row reading `undefined` becomes `false` and not falsy-but-not-false. Asserted with `typeof === "boolean"`, because plan 41-08's alert path and the five handler gates all compare against `false` |
| T-41-27 | Repudiation | the skipped-delay output | mitigate | `simulated: true` on the output makes the skip visible in the existing `json-viewer.tsx` with no new UI and no new copy, so an operator reading a dry run's per-node output can see the delay was not exercised |
| T-41-SC | Tampering | npm/pip/cargo installs | mitigate | **this plan installs nothing.** If a task concludes a package is needed, STOP and report |
