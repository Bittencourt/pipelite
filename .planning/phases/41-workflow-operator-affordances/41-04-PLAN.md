| Component | Verdict | Mechanism | Source |
|---|---|---|---|
| Schedule processor claim | SAFE | `UPDATE workflows SET next_run_at = NULL WHERE active AND next_run_at <= now RETURNING *` — one statement; under READ COMMITTED the loser re-evaluates the predicate after the row lock, matches nothing, and creates no runs | `src/lib/triggers/schedule-processor.ts:64-73` |
| Execution processor **pending** claim | SAFE | `UPDATE workflow_runs SET status='running' WHERE id = (SELECT … WHERE status='pending' … FOR UPDATE SKIP LOCKED) RETURNING *` — the subselect's lock is held for the enclosing statement and the predicate is re-checked, so exactly one instance claims | `src/lib/execution/execution-processor.ts:115-133` |
| Stale-run reclaim | SAFE | idempotent single-statement `UPDATE … WHERE status='running' AND started_at < NOW() - interval`; a double-apply is a no-op | `src/lib/execution/execution-processor.ts:73-95` |
| Execution processor **waiting resume** | was UNSAFE, **fixed in this phase** | its `SELECT … FOR UPDATE SKIP LOCKED` ran via `db.execute` on a transaction-free postgres-js client, so the row locks dropped at statement end, and the follow-up step `UPDATE` carried no `WHERE status='waiting'` guard. Two replicas could both resume the same delayed run, duplicating every side effect after the delay | `src/lib/execution/execution-processor.ts:162-205`; fix in plan 41-12 |
| `webhook_response` node | **UNSAFE — no fix this milestone** | `pendingResponses` is a module-level `Map`. `waitForWebhookResponse` registers in the process that received the HTTP request; `sendWebhookResponse` resolves only in the process that runs the node. Across replicas the map misses, the handler returns `sent: false`, and the caller's request hangs until the 30 s timeout then falls back to `{ ok: true }` | `src/lib/execution/actions/webhook-response.ts:15, 26-61`; `src/app/api/webhooks/in/[workflowId]/[secret]/route.ts:97-144` |

`src/instrumentation.ts:27-42` starts **all four** processors in every instance, so a second replica
runs a second copy of each. That is why the question is real rather than theoretical.

**Two WFOPS-03 coverage gaps to record in the same section** (RESEARCH § Failure Alerting; the
recommendation is document, do not close):
1. **Recursion-limit failures never alert.** `createWorkflowRun` inserts those rows already
   `status: 'failed'` (`src/lib/triggers/create-run.ts:22-36`), so the processor never claims them and
   never re-reads them.
2. **Synchronous webhook-response runs never alert.** `route.ts:102-118` claims the run itself and
   calls `executeRun` inline; the processor never sees it. A failure there returns `{ ok: true }` to
   the caller. This one belongs here specifically because it is the SAME in-memory-coordination
   limitation seen from the alerting side.

**A third webhook-response consequence, same mechanism, worth one sentence** (RESEARCH Q3): replaying a
failed run of a webhook-response workflow produces `sent: false` for that node, because the original
HTTP caller is long gone. Correct and harmless, but it means such a workflow's replay is not equivalent
to its original run.

**Existing prose idiom to match.** `vercel.md` § Limitations and Workarounds uses `### Heading` then
`**Problem**: …` then `**Solution**: …` with a bulleted list or a fenced env block
(`vercel.md:219-249` — File Uploads, Execution Time Limits, Cold Starts). Match it. `docker.md`
§ Production Considerations carries `###` subsections at the same depth.
