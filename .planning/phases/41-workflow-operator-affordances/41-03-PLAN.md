<recorded_decisions>
**Do NOT pin a key count anywhere.** 41-UI-SPEC.md says 25 keys, 41-VALIDATION.md says 23, and
`locale-parity.test.ts:1011-1018` carries a standing warning that EVERY key count quoted in the Phase
40 planning documents was wrong, because a naive count over an array literal also counts the dot-paths
quoted inside its explanatory comments. **The array is normative; the documents are descriptive.**
Concretely: this plan does NOT add a `REQUIRED_WORKFLOWS_KEYS` length assertion and does NOT add a
`WORKFLOWS: <n>` row to the pinned-length test at `:1020-1027`. It replaces the value that test was
buying — catching a list that repeats one dot-path and drops another — with the count-free form
`expect(new Set(REQUIRED_WORKFLOWS_KEYS).size).toBe(REQUIRED_WORKFLOWS_KEYS.length)`, which is
self-referential and cannot be wrong.

**D-A5 / the failure template IS localised.** 41-RESEARCH C-4 leaves this open and requires the choice
be recorded. Decision: **Option A — localise, as `emails.workflowFailed.*`.** The two un-localised
templates (`workflow-email.ts`, `workflow-notification.ts`) carry *user-authored* content a workflow
supplied; the seven localised ones carry the app's own voice. A failure alert is the app's own voice,
its recipient is a real `users` row, and `users.locale` exists (`src/db/schema/users.ts:20`). So the
keys are added here, in this plan, alongside the UI keys. This is a documented ADDITION to UI-SPEC's
manifest, not a silent divergence. Per UI-SPEC L-41-2 these keys stay OUT of
`REQUIRED_WORKFLOWS_KEYS` — they are covered by the whole-file parity assertion, which keeps the
`workflows` contract total.
</recorded_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| message value → next-intl renderer | a literal `{` in a value is parsed as a placeholder delimiter and throws at render, taking the whole page down |
| message value → the operator's decision | `replay.confirmBody` is the only warning an operator gets before duplicating every already-succeeded email, HTTP call and CRM write of a failed run |
| translated value → the parity gate | a copy-pasted English string in pt-BR ships an untranslated UI to two of three locales |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-41-13 | Denial of service | any new message value | mitigate | the G-9 gate: strip recognised placeholders, then assert neither brace remains. A literal brace throws at render, so this is an availability control, not a style rule |
| T-41-14 | Repudiation | `workflows.replay.confirmBody` | mitigate | the string is transcribed verbatim from the approved UI-SPEC and translated in full, including the enumeration of emails / outgoing requests / record changes. An abbreviated translation would let a non-English operator replay without the amplification warning |
| T-41-15 | Information disclosure | `emails.workflowFailed.*` | mitigate | no key takes the run error as an interpolated value; there is no `{errorMessage}` placeholder. The error is escaped and rendered outside the translator by plan 41-08, so a run error containing markup or braces can neither break the render nor be re-parsed |
| T-41-16 | Tampering | `REQUIRED_WORKFLOWS_KEYS` | mitigate | the contract is TOTAL and count-free: a 24th `workflows.*` key that never entered the array fails the exact-contract `toEqual`, and the no-duplicates check is written against the array's own length so no prose number can be wrong |
| T-41-17 | Information disclosure | pt-BR / es-ES values | mitigate | `untranslatedInBoth` forces every value to differ from en-US in both locales, including the `dryRun.action` / `dryRun.badge` pair that is identical in English |
| T-41-SC | Tampering | npm/pip/cargo installs | mitigate | **this plan installs nothing.** No package, no `npx shadcn add`. If a task concludes one is needed, STOP and report |
