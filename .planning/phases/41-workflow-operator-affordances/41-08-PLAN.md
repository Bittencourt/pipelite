<objective>
Build the failure-alert module: a database-backed, atomically-claimed per-workflow throttle, the
preference check, the dry-run exclusion, and a localised email template whose one interpolated
user-controlled value is escaped.

Purpose: WFOPS-03 exists because runs "can currently fail silently forever". The naive version of this
feature is itself an outage: a scheduled workflow failing on every five-second execution tick emits
~17,000 emails a day and gets the sending domain blocked. And the naive throttle — a read-then-write
check, or an in-memory `Map` — breaks under two replicas, which is precisely the defect class WFOPS-04
documents in the same phase. So the throttle is a guarded `UPDATE … RETURNING`, in the database.
Output: `src/lib/execution/failure-alert.ts`, `src/lib/email/templates/workflow-failed.ts`, one barrel
line, and one colocated unit gate.
</objective>

<recorded_decisions>
**Throttle storage: `workflows.failureAlertSentAt`, NOT `digest_log`** (CONTEXT amendment A5). CONTEXT's
original text names `digest_log` as the precedent for "remember that we already sent this". It is a good
conceptual precedent and the wrong vessel: `digest_log` has columns `id, sentAt, userCount, weekStart`
and **no workflow key**, and its only reader is
`SELECT id FROM digest_log WHERE week_start = $thisMonday LIMIT 1` — if that returns a row the weekly
digest **silently does not send**. Writing failure alerts there would suppress the weekly digest for
every user. The column added by plan 41-01 is the storage.

**Window: 60 minutes.** CONTEXT grants this as discretion. 60 minutes is chosen against the two poll
intervals that bound the failure rate — the execution processor ticks every 5 s and the schedule
processor every 30 s. A workflow failing on every execution tick emits ~17,000 emails/day unthrottled
and 24 at this window: below any transactional relay's rate limit, and still frequent enough that a
sustained outage keeps reminding the operator rather than going quiet after one message. It also matches
the only other time constant in the email layer, the activity reminder's one-hour horizon. Exported as a
constant so a test imports it and a change is one line.

**A failed DRY run sends no alert.** The operator is watching the dialog that started it, and without
this exclusion anyone can generate mail by clicking Test run in a loop.

**D-A5 / the template is LOCALISED** as `emails.workflowFailed.*` (RESEARCH C-4, option A). The two
un-localised templates carry *user-authored* content a workflow supplied; this one is the app's own
voice to a known user whose `locale` is in hand (`src/db/schema/users.ts:20`). Plan 41-03 already added
the five keys to all three locale files.

**Test placement diverges from 41-VALIDATION.md, deliberately.** VALIDATION names
`src/lib/execution/__tests__/failure-alert.test.ts`. `src/lib/execution/` has a **colocated**
convention — `engine.test.ts`, `execution-processor.test.ts`, `recursion.test.ts`,
`condition-evaluator.test.ts`, `delay-resolver.test.ts`, `toggle.test.ts` are all colocated and there is
no `__tests__/` dir. Per CONTEXT's placement rule the file is
`src/lib/execution/failure-alert.test.ts`. The verifier must use that path.

**Escaping approach, named because RESEARCH found no in-repo analog.** All nine existing templates
interpolate translator output or app-controlled strings; `workflow-notification.ts:21` interpolates a
workflow's own `message` **unescaped**, so the nearest precedent is the defect. Decision: a small local
`escapeHtml` in `workflow-failed.ts` covering `& < > " '`, plus truncation of the run error to a named
`MAX_ERROR_CHARS` constant. Do NOT add an HTML-sanitiser dependency and do NOT export the escaper for
reuse — a second consumer is when it gets promoted, and this phase has one.
</recorded_decisions>
