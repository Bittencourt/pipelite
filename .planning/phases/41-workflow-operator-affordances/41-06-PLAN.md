<objective>
Gate the two heaviest side-effecting handlers under dry run: the three `mutations.*` calls in
`crm_action`, and `sendWebhookResponse` in `webhook_response`. In both, gate **immediately before the
side effect** and keep every line of resolution above it running for real.

Purpose: the CRM gate is the phase's headline requirement. It is also where the affirmative proof comes
from: skipping the mutation call means no `crmBus` event is emitted, so the workflow-trigger subscriber
never fires and no `audit_log` row is written — and `run-changed-records.tsx`, which reads `audit_log`
by run id, therefore renders its existing empty state. That empty panel is criterion 2's evidence.
Output: two gated handlers and two extended test files.
</objective>

<recorded_decisions>
**Gate immediately before the side effect, never above the resolution.** 41-RESEARCH Pitfall 2: an
early `if (context._dryRun) return { output: … }` is the shortest diff and it makes the dry run
decorative — every dry run then "passes", including ones whose real counterpart would fail on a
missing target record. The governing principle is **simulate the side effect, never the resolution.**

**Second-order property that must NOT be "improved" away.** Because the gate skips the *mutation call*,
no `crmBus` event is emitted, so `instrumentation.ts`'s workflow-trigger subscriber never fires and a
dry run cannot trigger downstream workflows. That falls out of skipping the mutation. It would be LOST
if anyone rewrote the gate to call the mutation inside a rolled-back transaction — which CONTEXT
already rejected on other grounds (a sent email does not roll back).
</recorded_decisions>

`src/lib/execution/actions/webhook-response.ts:106-126` — the handler, complete:
```ts
const statusCode = (config.statusCode as number) ?? 200
const rawBody = normalizeBody(config.body)
const interpolatedBody = interpolateDeep(rawBody, context)   // <-- KEEP
const sent = sendWebhookResponse(runId, statusCode, interpolatedBody)   // <-- GATE HERE

```
Dry-run output: `{ sent: false, statusCode, body: interpolatedBody, simulated: true }`.

**Why the webhook-response gate is added even though it is already incidentally safe** (RESEARCH Q3):
`pendingResponses` is only written by `waitForWebhookResponse`, called only from the inbound webhook
route. A dry run is created by a server action, so its `runId` was never registered, so
`sendWebhookResponse` returns `false` immediately on the map miss — it does not await, does not
construct a promise, does not throw. The safety is therefore *incidental* and asserted nowhere. The
gate costs three lines and converts an accident into a decision.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workflow node config → CRM mutations | field mappings are workflow-author-supplied and interpolated with trigger data, then written to CRM records |
| `context._dryRun` → the mutation call | the only thing standing between a test run and a real record write |
| a dry run's runId → `pendingResponses` | a shared module-level map serving live HTTP requests |

| T-41-28 | Tampering | `crm_action` mutations under dry run | mitigate | three gates, each immediately before its `mutations.*` call, asserted by call-count-zero for all three collectively so a fourth operation added later without a gate fails |
| T-41-29 | Repudiation | gating above the resolution | mitigate | asserted that `resolveTargetId` still runs and that a failed target resolution still throws under `_dryRun`, and that the create output carries interpolated rather than raw template values. Pitfall 2: an early return makes the dry run decorative, so every dry run passes including ones whose real counterpart fails |
| T-41-30 | Elevation of privilege | downstream workflow triggering from a dry run | mitigate | skipping the mutation means no `crmBus` event, so `instrumentation.ts`'s workflow-trigger subscriber never fires and a dry run cannot start a real workflow. Documented in the gate comment as a property that would be LOST by a rolled-back-transaction rewrite |
