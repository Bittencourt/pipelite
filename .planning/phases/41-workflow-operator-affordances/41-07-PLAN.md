<recorded_decisions>
**FIVE handlers simulate, not four (amendment A1).** This is not an addition to CONTEXT's decision, it
is a correction to its enumeration: the decision's own invariant is that a dry run has no side effects,
and `notification.ts` has one the decision-maker did not see.

**`validateUrl` is kept on purpose under dry run.** It performs a DNS resolution
(`src/lib/execution/actions/ssrf.ts:62`), which is pedantically an outbound packet. Keeping it is right:
it is a *validation*, not the "outgoing request" the locked copy is about, and dropping it would let a
dry run pass a URL a real run rejects — turning the dry-run path into an SSRF laundering step.
`ssrf.ts:63-65` treats DNS failure as "hostname is an IP literal" and does not throw, so an offline
environment does not break dry runs.

**Gate immediately before the side effect, never above the resolution** (Pitfall 2). For `email` and
`notification` this specifically means the `emails.length === 0` / "No valid users found" throws must
STILL FIRE under dry run.
</recorded_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workflow node config → the internet | an `http_request` node's URL is workflow-author-supplied and interpolated with trigger data |
| workflow node config → the production SMTP relay | `email` and `notification` resolve real addresses from the `users` table and send through a real relay |
| `context._dryRun` → the side effect | the only thing between a test run and a real outbound packet |

|-----------|----------|-----------|-------------|-----------------|

Without it, a dry run mails real users from the production sending domain, because `.env` points `SMTP_PORT=465` at a real relay and not at mailhog. This is the phase's highest-severity finding |
