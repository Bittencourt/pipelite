<recorded_decisions>
**A Dialog from the toolbar, NOT the side panel** (UI-SPEC, researcher decision on CONTEXT's explicit
discretion item). Three measured grounds: `side-panel.tsx:100` is `w-[400px]`, a hard fixed width that
already overflows a 320px viewport; the side panel is single-slot and owned by node selection, so a third
`panelMode` would couple "test the whole workflow" to "a node is selected" and opening the dry run would
deselect the node being configured; and the interaction shape is edit-then-confirm-then-wait, which is a
modal — the side panel has no confirm affordance.

**Disabled while dirty.** A dry run executes the **persisted** workflow (the engine loads by
`workflowId`), so with unsaved edits on screen the test would silently exercise the old definition and
report on something the operator is not looking at. `disabled={dirty}` plus `title` plus an
`aria-describedby` pointing at a visible hint — a `title` alone is invisible to touch and to screen
readers that do not announce it.

**The timeout path is reachable in NORMAL operation, not just on error** (RESEARCH Q2). The execution
processor polls every 5 s, so a dry run waits 0-5 s before it even starts; and serial enforcement means a
dry run queues behind any `running` or `waiting` run of the same workflow. A workflow with a `waiting`
run will never be claimed inside 30 s. That is honest behaviour and `dryRun.timeout` is its state — do
not treat the timeout as a failure and do not extend the budget to hide it.

**F-41-1 — no copy asserting non-mutation.** No *"No records were changed."*, no *"Nothing happened."*,
no reassuring banner, no green tick. The proof is `run-changed-records.tsx` rendering its EXISTING
`audit.run.empty` state on the run detail page. Also forbidden: any copy in this dialog promising that
the run *will* prove non-mutation. `dryRun.description` states what is *simulated* — a factual property
of the execution — not what the operator will conclude.
</recorded_decisions>

/** Deriving it during render rather than storing it is what keeps the effect's dependency honest: a
 * terminal status turns this to `null`, the effect re-runs, its cleanup clears the interval, and no
 * further request is made. That is the SECOND of the two stops — the first is inside the poll
 * callback — and the reason there are two is that the analog's equivalent effect stops nothing. */
const pollScanId = scan !== null && !isTerminal(scan.status) ? scan.scanId : null

useEffect(() => {
  if (pollScanId === null) return
  let mounted = true
  const poll = async () => {
    const result = await getScanProgress(pollScanId)
    if (!mounted) return
    if (!result.success) { clearInterval(interval); return }   // a refusal will be refused again
    …
    if (isTerminal(result.scan.status)) { clearInterval(interval); router.refresh() }
  }
  /* THE INTERVAL IS CREATED BEFORE THE FIRST FETCH … if the very first answer is already terminal,
     the clear has to have something to clear. */
  const interval = setInterval(poll, SCAN_POLL_INTERVAL_MS)
  void poll()
  return () => { mounted = false; clearInterval(interval) }
}, [pollScanId, router])

| the JSON textarea → the server action → the engine → QuickJS | operator-authored trigger data is interpolated by handlers and injected into the transform sandbox |

| the poll loop → the server | an unbounded poll is a self-inflicted request flood from every open editor tab |
