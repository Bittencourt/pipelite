<objective>
Turn the CI workflow into an actual merge gate, and prove behaviourally that a broken pull request cannot be merged.

Purpose: CI-04's second half — "and a failing check blocks merge" — and ROADMAP success criterion 4. Branch protection is a GitHub repository setting with no in-repo representation, so no commit can create it. It also cannot be configured until the workflow has run at least once: GitHub's required-check picker only surfaces check names it has recently observed. That ordering constraint is why this is a separate plan in its own wave.
Output: a green first CI run on `master`, an active branch ruleset requiring the `ci` check, and a closed throwaway PR that demonstrated the block.
</objective>

    ROADMAP success criterion 4 requires that a pull request with a type error, a lint error, or a failing test "shows a red required check and cannot be merged". A required status check alone achieves that **for pull requests**.     The cost is concrete and lands on you daily: **this repository's GSD workflow commits directly to `master` and pushes.** Requiring a pull request means every future phase's commits — including SUMMARY files and ROADMAP updates — must go through a branch and a PR, or must be pushed by an actor on the ruleset's bypass list. Rulesets apply to repository admins too unless you add them as a bypass actor.

    You are the sole developer and the repo owner. All three options keep the `ci` check required and red-blocks-merge on PRs; they differ only in how much they constrain your own direct pushes.
  </context>
  <options>
    <option id="option-a">
      <name>Strict — require PR, no bypass (research recommendation)</name>
      <pros>Closes the direct-push bypass completely. SC-4 holds against every path, including your own. Matches the Security Domain recommendation and what `CONTRIBUTING.md` now documents.</pros>
      <cons>Every future GSD phase must branch and open a PR to land on `master`; `git push origin master` will be rejected. Adds a branch-and-PR step to a solo loop that currently commits straight to master.</cons>

    <option id="option-b">
      <name>Require PR, with repository-admin bypass</name>
      <pros>SC-4 holds for the normal path and the gate is real for any future contributor or fork, while you retain the ability to push directly when the GSD loop needs it. Practical middle ground for a solo repo.</pros>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-26 | Elevation of Privilege | direct push to `master` | mitigate (option A/B) or accept (option C) | This is the decision in Task 2, surfaced to the developer rather than assumed.
