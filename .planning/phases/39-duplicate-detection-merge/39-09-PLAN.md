<objective>
Write the merge itself: one transaction that reparents every child, applies the chosen field values,
soft-deletes the loser, writes both audit sides and the per-child audit rows, and settles the pair
table — plus the four-file `AuditAction` compile cascade it depends on.

Purpose: DEDUP-03 and success criteria 4 and 5. This is the most destructive operation in the
application. 39-RESEARCH measured the heaviest organization in the database at **114 child rows
total**, so a single transaction is not a stretch — it is smaller than several statements the app
already runs, and "nothing is orphaned" is only checkable if the whole thing is atomic.

<key_facts>
- **`purgeOrganizationMutation` (`src/lib/mutations/organizations.ts:544-642`) is a line-for-line
  template.** Its six load-bearing properties, all of which the merge needs: (1) `const actor =
  getCurrentActor()` synchronously at entry, before any promise; (2) an existence read OUTSIDE the
  transaction returning a discriminated CODE, never prose; (3) polymorphic notes handled explicitly
  with the "nothing in the database enforces this" comment; (4) `.returning({ id })` on every child
  UPDATE; (5) `tx.insert(auditLog)` and never `db.insert`; (6) a `catch` returning a FIXED sentinel
  string while logging the real error.
- **`deleteOrganizationMutation` must NOT be reused for the loser** (`organizations.ts:409-446`).
  Two defects visible in five lines: its `UPDATE` runs on the module-level `db` with no transaction,
  and it emits `organization.deleted` on the bus unconditionally, before any later step could fail.
  The merge's soft delete is an inline `tx.update(...)`.
- **The audit bus cannot be used.** `src/lib/events/subscribers/audit.ts:70` writes audit rows with
  the module-level `db`, fire-and-forget with a `.catch()`, deliberately. A bus-emitted row survives a
  rollback, and the timeline would show a merge that never happened. Also `merged` is not one of the
  twelve `AUDITED_EVENTS` and no `organization.merged` event exists.
- **B4, the single most likely thing to ship broken.** `notes_migration_uniq` is
  `uniqueIndex ON (entity_type, entity_id) WHERE source = 'migration'` and its own comment calls it
  "a permanent database invariant, not a one-shot script guard" — it may not be dropped. Measured:
  **29,037 of 46,054 organizations (63%) carry a `source='migration'` note**, so a naive
  `UPDATE notes SET entity_id = survivor` raises 23505 and rolls back roughly 40% of organization
  merges (likely more, since duplicate pairs come from the same import). **Resolution, decided:
  demote the loser's migration note to `source='user'` when the survivor already has one, and record
  the reclassification in the merge's audit `changes`** — the only option that loses nothing.
- **Do NOT reassign `audit_log` rows.** `src/db/schema/audit-log.ts:38-46` states the posture: an
  audit row for a deleted record must survive that record, and "do not fix this by copying the notes
  defence over — its absence is the design". The loser keeps its history; the loser is in Trash and
  restorable.
- **Activities are NOT reassigned and this is not an omission.** `activities` has `deal_id` only —
  no organization and no person column (verified against `pg_constraint` and a full
  `information_schema.columns` scan). They follow their deal transitively. Write the COMMENT where a
  reader would expect an `UPDATE activities` and not find one; never write a no-op statement.
- **The exhaustive child inventory is exactly three foreign keys**: `deals.organization_id`,
  `people.organization_id`, `deals.person_id`. Plus the polymorphic `notes`. Nothing else in the
  32-table schema can hold an organization or person id.
- **B3, the compile cascade.** `AuditAction` is declared TWICE (`src/db/schema/audit-log.ts:23` and
  `src/lib/timeline/types.ts:105`) and consumed by two EXHAUSTIVE maps
  (`src/lib/audit/linked-records.ts:40` `ACTION_RANK`, and
  `src/app/workflows/[id]/runs/[runId]/components/run-changed-records.tsx:54`
  `ACTION_BADGE_VARIANT`). Phase 37 wrote this down and deliberately avoided paying it. Phase 39
  pays it, in one task. **Never relax either map to `Partial<Record<...>>`** — that is Pitfall 6's
  warning sign.
- **`ACTION_RANK` today is `{ updated: 0, created: 1, deleted: 2 }`** and its comment states the
  precedence "deleted > created > updated". **Planner decision: `merged` ranks between `created` and
  `deleted`** — a `merged` row is written on the SURVIVOR, which is alive, so it must not outrank a
  deletion, but it is a more significant fate than a creation. Renumber to
  `{ updated: 0, created: 1, merged: 2, deleted: 3 }` and update the comment to
  "deleted > merged > created > updated".
- **`ACTION_BADGE_VARIANT` today is `{ created: "outline", updated: "outline", deleted: "secondary" }`**
  and its comment says NEVER `destructive`. Add `merged: "secondary"` — a completed merge is a fact,
  like a completed deletion.
- **`auditActorColumns` — planner decision: write a THIRD local copy** in `src/lib/mutations/dedup.ts`,
  with a comment naming the two existing copies (`organizations.ts:176`, `people.ts:172`) and stating
  that a shared extraction was considered and rejected for this phase because it would edit two
  shipped mutation files inside a phase already paying a four-file compile cascade. Carry the
  analog's rule verbatim: NEVER borrow a user id from a payload — that field describes the record
  being written, not the identity that wrote it.
- **`recalculateFormulas` cannot run inside the transaction** — it and its cascade use the
  module-level `db`, never a `tx`. Run it AFTER commit, best-effort. And **do not rely on a
  survivor-rooted cascade**: `cascadeToChildren` short-circuits on `if (changed.size === 0) return 0`,
  so a merge where the survivor won every field recomputes nothing and the reparented children keep
  the loser's `Organization.*` values. Iterate the reparented children explicitly.
</key_facts>
