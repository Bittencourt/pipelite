<objective>
Build the scan: a name-group table, star pairs for the exact tier, a name-level trigram self-join for
the fuzzy tier, persisted into `duplicate_pairs` in a way that cannot resurrect a dismissal — plus
the paged reads the review page renders.

Purpose: DEDUP-01's second half, SC-2. The design here is the phase's single biggest measured win and
it is not the obvious one: running the trigram self-join over ROWS produces 27,156 pairs in 67
seconds; running the identical join over the 21,503 DISTINCT normalized names produces **419 pairs in
18.2 seconds**. Combined with star pairing for exact-name groups (24,551 pairs instead of 1,030,436),
the whole scan lands at roughly 20 seconds and about 25,000 pairs, versus roughly 26 minutes and 14.5
million pairs for the naive row-level join.
Output: `scan-engine.ts`, `queries.ts`, and `scripts/dedup-checks.sql` Part 8.
</objective>

<key_facts>
- **The dominant cost is clique expansion, not similarity computation.** Measured on the live
  database (46,054 organizations, 21,503 distinct normalized names):

  | Approach | Threshold | Wall clock | Pairs |
  |---|---|---|---|
  | Row self-join | 0.30 (pg default) | ~26 min (extrapolated) | ~14.5 M (extrapolated) |
  | Row self-join | 0.85 | 67.1 s | 27,156 |
  | **Distinct-name self-join** | **0.85** | **18.2 s** | **419** |

  The 65x collapse is not a precision change — it is the same pairs with clique cross-products
  removed. A 216-member group joined against an N-member group emits 216xN identical-looking pairs at
  the row level and ONE at the name level.
- **Star pairing for the exact tier.** Every non-canonical member of an exact-name group pairs with
  the group's canonical record: `n-1` pairs, not `n(n-1)/2`. Measured: 24,551 instead of 1,030,436, a
  42x reduction, and it is mathematically lossless because exact equality is transitive.
- **The GIN trigram index over the distinct-name table IS the blocking mechanism.** Do not build a
  token-blocking layer: first-token blocking (which 39-CONTEXT suggested) was measured at 7,698,277
  candidate pairs with a largest block of 2,307 (`CONDOMINIO`), and 98.6% of its comparisons sit in
  blocks larger than 50 rows. It does not tame this dataset. Say so in a comment rather than
  implementing something the index makes redundant; mention rarest-token blocking as the fallback for
  a different dataset.
- **`SET LOCAL`, never plain `SET`.** The `%` operator reads `pg_trgm.similarity_threshold` from the
  session GUC and this app uses postgres.js with connection pooling, so a plain `SET` leaks the
  threshold onto whatever query runs next on that connection. Use `SET LOCAL` inside the scan's
  transaction, and additionally carry an explicit `similarity(a,b) >= $threshold` predicate so the
  filter is expressed twice — the operator for index access, the function for correctness.
- **Pitfall 3's detector, and it belongs in the code as well as in the SQL script:** the pair count
  must never exceed the row count of the entity being scanned. Assert it before committing.
- **Dismissal survives a rescan** — a locked functional requirement, not a nicety. The mechanism is
  `duplicate_pairs_uniq` on `(entityType, recordAId, recordBId)` with canonically ordered ids, plus an
  upsert whose `DO UPDATE` is guarded so a row with `status = 'dismissed'` is left untouched.
- Review-list shape: UI-SPEC L-9 sets the page size to **25** and L-1 puts all state in the URL. The
  `/trash` analog (`src/lib/trash/queries.ts`) fetches `PAGE_SIZE + 1` and trims to derive `hasMore`,
  and returns `{ ok: false }` rather than an empty success so a degraded read is distinguishable from
  "nothing found". Copy both.
- The scan runs inside `runWithActor({ kind: "user", userId })` opened by the server action (plan
  39-11); this module does not open one.
</key_facts>
