<objective>
Build the merge screen: the survivor selector, the three field groups, the what-moves list, the
confirmation and the submit — the surface DEDUP-02 and success criterion 3 are about.

Purpose: this is the hard surface. 39-UI-SPEC calls the merge screen "the single biggest hazard in
this phase" for the 320px viewport, and M-1 resolves the layout discretion outright: **a stacked
per-field option list, never side-by-side columns.** The reasons are measured, not aesthetic — 241px
of usable width at 320px gives each column about 112px, and column headers scroll away, so a user
picking field 12 has lost the header that said which column is which. That defect is
viewport-independent: it hurts at 1920px too.

  `{ RadioGroup as RadioGroupPrimitive } from "radix-ui"` — the repo's unified convention (K-5), so no
  import normalisation is needed; its only dependency is `radix-ui`, already at `^1.4.3`, so no new

  `./node_modules/.bin/shadcn add radio-group` — **never `npx`**, which resolves to `npm run` on this
  host and fails with "Missing script".
- **M-1:** stacked field list. At `sm` (640px) and up, the TWO OPTIONS OF ONE FIELD may sit in a
  `grid gap-2 sm:grid-cols-2` — that is a two-up of one field's two options, not a two-column
  comparison of two records, and each option still carries its own record-name caption so nothing
  depends on a header. Below `sm` the grid collapses.
- **M-2:** section 1 is a `RadioGroup` with two option cards, legend `dedup.merge.survivorLegend` at
  Heading typography, helper `dedup.merge.survivorHelp` at Label typography muted. Each card shows the
  record name, `dedup.merge.createdOn` with a formatted relative instant, and the `dedup.merge.moves*`
  counts. **Default: the older record survives.** Changing the survivor recomputes every field default
  and discards manual field choices — `survivorHelp` states that BEFORE the click, and there is no
  confirmation dialog, because a dialog for a reversible in-form change is friction.
- **M-3:** three groups in this order — conflicts (both populated and different, default survivor,
  never collapsed), filled-only (survivor empty and loser populated, default **loser**, never
  collapsed), identical (equal or both empty, no control, collapsed). Group 3 is its own visible
  section for one reason: its default **adopts a value from the record being destroyed**, and a
  default that quietly imports data is the thing a user needs to be able to audit before pressing
  Merge.
- **M-4:** every field label resolves through `describeField` in `src/lib/audit/present.ts` (exported
  by plan 39-02). No new map, no new `audit.field.*` key. The user sees the same word for a column in
  the picker as in the timeline entry that records the merge — one is the receipt for the other.
- **M-5:** the whole option card is the label, so the tap target is the card. Unselected
  `rounded-md border px-3 py-2`; selected adds `border-primary` **plus** the radio dot, so the state
  has two carriers and colour is never the only one. **An empty side renders `audit.value.empty` in
  `text-muted-foreground italic`, never a blank** — a blank option looks unclickable and is
  indistinguishable from a render bug, and "choose emptiness" is a legitimate choice. Long values wrap
  (`break-words`); **no `truncate` and no `line-clamp` anywhere in the picker** — a truncated website
  makes the choice unmakeable.
- **M-6:** section 5 is a plain `<ul>` stating what will be reassigned with counts —
  `dedup.merge.movesDeals`, `movesNotes`, `movesPeople` (organizations only), `audit.value.files` —
  followed by `dedup.merge.activitiesFollowDeals` and `dedup.merge.filesStayInPlace`. This is how
  success criterion 4 becomes checkable by a human BEFORE the merge. Both trailing sentences are
  load-bearing statements of locked decisions.
- **M-7:** `AlertDialog`, controlled, with NO trigger component — Radix `SlotClone` renders `null` for
  an `asChild` element that crossed the RSC boundary, and the repo-wide gate for that is
  `src/app/admin/fields/[entityType]/__tests__/rsc-boundary.test.tsx`. Action is
  `variant="destructive"` (C-2): a merge's consequence is that a record leaves the list and lands in
  Trash, identical to the bulk delete, the single delete and the purge.
- **M-8:** merge failed → `toast.error(dedup.merge.failed)` and the form KEEPS every choice the user
  made. One record already gone → `Alert variant="destructive"` with `dedup.merge.gone`, the form
  disabled, and `dedup.merge.backToList`. This is reachable: another user can merge or delete the same
  pair while this screen is open. **The merge is a single transaction, so there is no partial-failure
  surface and no per-record failure list** — Phase 38's principle is satisfied by atomicity here.
- **M-9:** the submit row is `flex flex-wrap gap-2` at the END of the form, in a `Card`, with **no
  `sticky` and no `fixed`**. Phase 45's D-45-02 is an OPEN UAT item about a fixed bar occluding
  content; adding a second fixed bar while that is unresolved would compound a known live defect.
- **M-10:** a full page at `/duplicates/[pairId]`, not a Dialog and not a Sheet. A modal at 320px
  would put a 10-decision form inside a scroll container inside the page's scroll container, and a
  route gives the user a URL to return to when a merge fails.
- **R-3, the enforceable form of M-1:** no `grid-cols-2` without an `sm:` prefix, no unwrapped flex
  row of two record blocks, no table whose columns are "record A" and "record B". A source scan can
  check all three.
- The pre-existing duplicate `Segmento Organização` definition means the field list must dedupe by
  name — `buildMergeFieldGroups` (plan 39-02) already does, and that is where it belongs.
