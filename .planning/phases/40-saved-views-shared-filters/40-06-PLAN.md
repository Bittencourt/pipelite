The write side: five server actions that create, update, share, default and delete a view — each one
re-deriving its own inputs rather than trusting the client, and each one authorizing before writing.

no filters (B-5) and hides the edit controls on somebody else's view (G-7), but neither of those is a
control — they are presentation. Every rule the UI implies has to exist here too.

The repo's server-action return shape is `{ success: true, ... } | { success: false, error: string }`.
`src/lib/fetch-entities.ts` is the precedent for `"use server"` living under `src/lib` rather than
under `src/app` — use it, so no `src/app/views/` directory is created for a surface that has no route.

Auth: `const session = await auth()` from `@/auth`; `session.user.id` and
`(session.user as { role?: string }).role` are the two fields every existing action reads.

From plan 40-01: `pickFilterParams`, `hasSaveableFilter`, `countFilters`, `SAVEABLE_FILTER_KEYS`.
From plan 40-02: `savedViews`, `savedViewDefaults`, and
`uniqueIndex("saved_views_owner_type_name_uniq").on(ownerId, entityType, name)`.

Message keys these actions map onto (already in the catalog after plan 40-03) — the ACTION returns a
machine code, the CLIENT picks the key. Never return a translated string from a server action:
| code | key |
|---|---|
| `name_taken` | `views.save.nameTaken` |
| `name_required` | `views.save.nameRequired` |
| `no_filters` | `views.save.noFilters` |
| `forbidden` | `views.manage.readOnly` (or `views.save.targetNewOnly` in the save dialog) |
| `failed` | `views.save.failed` / `views.manage.failed` / `views.delete.failed` |

    space, rejects an empty result (`null`), and caps at `MAX_VIEW_NAME_LENGTH` (pick and export a
    number in the low hundreds) by rejecting rather than truncating — a silently truncated name is a
    name the user did not choose. Assert: `"  "` → null, `"a\t\nb"` → `"a b"`, a 1 MiB string → null,

    (b) `guardSaveInput({ entityType, filters, name })` → `{ ok: true, filters, name } | { ok: false,
    error: "name_required" | "no_filters" }`:
      - runs `pickFilterParams` over the SUBMITTED filter map and uses the RESULT, so a client that
        posts `{ pipeline: "p", nonsense: "x" }` gets `{ pipeline: "p" }` stored and nothing else
      - returns `no_filters` when `hasSaveableFilter` is false on the picked map. Assert with an empty
        map, with a map of only non-whitelisted keys, and with `{ search: "   " }` — all three must be
        refused. **`views.save.noFilters` exists precisely for this path (S-15) even though the
        dialog is unreachable in that state; the guard is the control and the hidden button is not.**
      - returns `name_required` for a name `normaliseViewName` rejects

    `readStrippedSource` + `callArguments` from
    `@/components/custom-fields/__tests__/source-scan`:
      - every exported `async function` in the file contains `await auth()` before any `db.` call.
        Extract each function body by brace matching and assert `body.indexOf("auth()") <
        body.indexOf("db.")` for each, with the function name in the failure message. Comments are
        stripped first, so a comment saying "authenticated first" cannot satisfy it.
      - `guardSaveInput` is CALLED inside both `createView` and `updateView` (assert on the extracted
        body, not on the file)
      - the file contains zero occurrences of the string `views.` — a server action must not return a
        translated key or string. Scope this to the stripped source.
  </behavior>
  <action>
    Create `src/lib/views/actions.ts` with `"use server"` at the top.

    `createView({ entityType, name, filters, isShared, makeDefault })`:
      1. `auth()`; refuse unauthenticated
      2. `guardSaveInput`; return its error code on failure
      3. `db.insert(savedViews).values({ ownerId: session.user.id, entityType, name, filters,
         isShared }).returning({ id })`
      4. **catch the unique-violation and map it, do not pre-check.** Postgres code `23505` with
         `constraint_name === "saved_views_owner_type_name_uniq"` → `{ success: false, error:
         "name_taken" }`. Write the comment: a `SELECT` then `INSERT` is advisory, and BACKLOG.md
         already records exactly that shape as a defect (the dedup scan-guard read-then-write). Use
         the `postgres`/Drizzle error's `code` field; do not string-match the message text.
      5. when `makeDefault`, upsert `savedViewDefaults` on `(userId, entityType)` in the SAME
         transaction, so a failed default cannot leave a view saved with the user believing it is
         their default
      6. `revalidatePath` for the entity's list route (`/organizations`, `/people`, `/deals`,
         `/activities`, from a frozen map keyed by `ViewEntityType` — never a string transform, or
         `person` becomes `/persons`)
      7. return `{ success: true, id, name }`

    `updateView({ id, name, filters, isShared, makeDefault })`:
      1. `auth()`
      2. read the row; `notFound`-equivalent → `{ success: false, error: "failed" }`
      3. **authorize:** `row.ownerId === session.user.id || role === "admin"`, else
         `{ success: false, error: "forbidden" }`. This is the server half of B-5's fourth row and
         S-4: a user who cannot overwrite someone else's shared view must be refused here too, not
         only offered a different dialog.
      4. `guardSaveInput`; same `23505` mapping on rename
      5. same transactional default upsert, same `revalidatePath`

    Both actions accept `filters` as a plain `Record<string, string>` and never as a query string —
    the client builds it from `useSearchParams` and the action re-picks it. State that the submitted
    map is data, not a claim.

      - `it("setViewShared refuses a view the caller neither owns nor admins")` — the authorization
        predicate helper `canMutateView(row, viewer)` returns false for a non-owner non-admin
      - `it("setViewDefault does NOT require ownership, because a default is per-user")` — the
        default path deliberately does not call `canMutateView`. A user may point their own default at
        any view they can SEE. Assert this directly, with a comment naming G-7 and CONTEXT's "A user
        MAY set someone else's shared view as their own default, otherwise sharing has little payoff".
      - `it("setViewDefault refuses a view the caller cannot see")` — the visibility check IS
        required: the row must be owned by the caller or `isShared`. Without it, a member could point
        their default at an admin's private view and learn its filters from their own address bar
        after the redirect. That is the information-disclosure hole the ownership check does not cover.
      - `it("deleteView removes the row and every default that pointed at it")` — asserted as a
        structural claim that no manual `savedViewDefaults` delete is needed because the FK cascades,
        plus a comment naming the locked decision: a teammate who had defaulted to it falls back to
        unfiltered, with no error.

    ANTI-VACUITY on `canMutateView`: assert it returns TRUE for an owner and TRUE for an admin on
    someone else's view, as well as false for the stranger. A predicate hardcoded to `false` would
    pass every refusal test.
  </behavior>
  <action>
    Add to `src/lib/views/actions.ts`:

    `canMutateView(row, viewer)` — exported pure helper: `row.ownerId === viewer.id || viewer.role ===
    "admin"`. One definition, used by `updateView`, `setViewShared` and `deleteView`.

    `canSeeView(row, viewer)` — exported pure helper: `row.ownerId === viewer.id || row.isShared`.
    **No admin branch** — Decision 3, same as the read layer. Used by `setViewDefault`.

    `setViewShared({ id, isShared })` — auth, read, `canMutateView` else `forbidden`, update, revalidate.
    When a view is being made PRIVATE, delete every `savedViewDefaults` row pointing at it that
    belongs to someone else, in the same transaction: an unshared view that is still another user's
    default would redirect that user into a view they can no longer see, and the resolver would then
    return `null` on every visit — a silent, permanent no-op. Deleting the stale default is the same
    "fall back to unfiltered, no error" behaviour the locked decision already chose for deletion.
    Note this in the file: it is a consequence CONTEXT did not state.

    `setViewDefault({ entityType, viewId })` — auth, read, `canSeeView` else `forbidden`, then upsert
    `savedViewDefaults` on the `(userId, entityType)` primary key. `viewId === null` clears it
    (`views.manage.clearDefault`). Revalidate.

    `deleteView({ id })` — auth, read, `canMutateView` else `forbidden`, delete the `savedViews` row
    and let the FK cascade take the defaults. Return `{ success: true, name }` so the client can
    render `views.delete.success` with `{name}` after the row is gone. Revalidate.

    Every action returns `{ success: false, error: "failed" }` from a catch and `console.error`s; none
    of them throws into a page with no `error.tsx` above it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser POST → server action | a server action is a public endpoint; every argument is attacker-authored, including `id` and the whole `filters` map |
| one user's view row → another user's mutation | `canMutateView` is the only thing between a member and an admin's shared view |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-40-22 | Elevation of privilege | every exported action | mitigate | `await auth()` before any `db.` call, asserted structurally per function with the function name in the failure message. The UI hiding a control is presentation and is never the authorization |
| T-40-23 | Elevation of privilege | `updateView`, `setViewShared`, `deleteView` | mitigate | `canMutateView(row, viewer)`, read from the row rather than from the request. A submitted `ownerId` is ignored entirely |
| T-40-24 | Information disclosure | `setViewDefault` | mitigate | `canSeeView` blocks defaulting to a view the caller cannot see. Without it, the redirect would print another user's private filter values into the caller's address bar |
| T-40-25 | Tampering | `filters` argument | mitigate | `pickFilterParams` re-derives the stored map server-side; a submitted key outside the whitelist is dropped rather than stored, so no future read can be surprised by it |
| T-40-26 | Elevation of privilege | `guardSaveInput` | mitigate | `hasSaveableFilter` refuses an empty filter set at the ACTION, so `views.save.noFilters` is a real control rather than a message for an unreachable state (S-15) |
| T-40-27 | Tampering | name uniqueness | mitigate | `23505` on `saved_views_owner_type_name_uniq` is caught and mapped; there is no read-then-write pre-check, which BACKLOG.md records as an advisory-guard defect |
| T-40-28 | Denial of service | `name`, `filters` | mitigate | `MAX_VIEW_NAME_LENGTH` rejects (not truncates) an oversized name; `MAX_FILTER_VALUE_LENGTH` in plan 40-01 bounds every stored value |
| T-40-SC | Tampering | npm installs | mitigate | this plan installs nothing |
</threat_model>
