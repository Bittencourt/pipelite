## Spacing Scale

Every value is a multiple of 4 and already appears in the codebase.

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px | `gap-1` between a `Modified` badge's border and the truncated name it follows |
| sm | 8px | `gap-2` on the views bar row; `space-y-2` inside a save-dialog field group; `py-2` override on a two-line view menu item |
| md | 16px | `space-y-4` between save-dialog field groups; `p-4` on a manage-dialog row; `gap-4` inherited from `DialogContent` |
| lg | 24px | `space-y-6` on the page shells this phase mounts into — inherited, unchanged |
| xl | 32px | `container` `padding-inline: 2rem` — inherited and **unchangeable**; costs 64 of the 305px client width (M-1) |
| 2xl | 48px | not used by this phase |
| 3xl | 64px | `py-8` × 2 on the page shells — inherited, unchanged |

**Fixed dimensions declared by this phase:**

| Dimension | Value | Why |
|-----------|-------|-----|
| Picker trigger max width | **`max-w-[200px]`** | Measured (M-10). Wider and the trigger alone consumes the whole 241px row before the `Modified` badge; narrower and an ordinary view name shows four characters. `max-w-*` is a constraint, not a scale value. |
| Overlay height clamp | **`max-h-[calc(100dvh-2rem)]`** | The 32px is the xl scale value, applied as 16px of breathing room top and bottom. `dvh` rather than `vh` because a mobile URL bar changes `vh` and F-39-07 is a mobile defect. Applied to all three overlays (§ Rule O-1). |
| Manage-dialog list max height | **`max-h-[50vh]`** with `overflow-y-auto` | The list is the only unbounded region in that dialog; clamping the list rather than only the dialog keeps the dialog's own footer on screen at every list length. |

**Exceptions.** The core scale is exactly the seven standard values (4 / 8 / 16 / 24 / 32 / 48 / 64).
Three exceptions, all inherited, none introduced here:

1. **`px-2 py-1.5` (8px / 6px)** — shadcn's `DropdownMenuItem` default inset. This phase **overrides
   the vertical half to `py-2`** on its two-line view items, which moves it *into* the scale; the
   horizontal `px-2` stays as shipped so a view item and the `Manage views` item below it share one
   left edge.
2. **`px-3` (12px)** — the shadcn control inset baked into `buttonVariants` and `Input`. Already the
   ambient convention; recorded, not promoted.
3. **`h-9` / `h-8` (36px / 32px)** — `buttonVariants` sizes. Not multiples of 4 in the 8-point sense
   but the app's only button heights; changing them is out of scope everywhere.

## Typography

**Three sizes, two weights.** This phase adds no `<h1>`, so it declares no display size and inherits
no `font-bold` exception — a narrower typographic footprint than Phase 39's.

| Role | Size | Weight | Line Height | Class | Where |
|------|------|--------|-------------|-------|-------|
| Label | 12px | 400 | 1.33 | `text-xs` | the second line of a view menu item (the state words); `views.needsFilter`; `views.degraded`; the `Modified` badge text; `views.manage.filterCount`; every helper line under a save-dialog control |
| Body | 14px | 400 | 1.43 (`leading-normal`) | `text-sm` | the view name in the picker trigger and in every menu item; every button and menu-item label; `DialogDescription`; every `Input` and `Label` |
| Heading | 18px | 600 | 1.2 (`leading-tight`) | `text-lg font-semibold leading-tight` | `DialogTitle` and `AlertDialogTitle` |

**Rule T-1 — every `DialogTitle` and `AlertDialogTitle` in this phase overrides `leading-none` to
`leading-tight`.** The primitive ships `text-lg leading-none font-semibold` (`dialog.tsx:149`), and
39-UI-SPEC forbids `leading-none` on anything that can wrap. `views.save.titleUpdate` in es-ES is
"Guardar los cambios de esta vista" — 33 characters, which wraps inside a 288px dialog at 320px, and
`leading-none` makes the two lines touch. The override is per-call-site (`className="leading-tight"`),
**not** a primitive edit: `dialog.tsx` is shared by roughly sixteen dialogs and retuning it is a
different change.

**Forbidden in this phase:**

- Any font size outside {12, 14, 18}. No `text-2xl`, no `text-3xl`, no stat tiles.
- Truncation anywhere except **two** places: the view name in the picker trigger, and the view name
  on line 1 of a menu item. Both are user-authored strings whose full value is one click away in the
  manage dialog. **The state-words line is never truncated** — it is the only carrier of
  Shared/Private/Default (§ Rule C-40-2), and truncating it would delete the words that replace
  colour.
- `leading-none` on anything that can wrap (T-1).

**Accent reserved for — the complete list for this phase:**

1. The `:focus-visible` outline on buttons, menu items and links (global, already in `globals.css`).
2. **The save dialog's submit button — the only primary-filled control this phase adds, anywhere.**
   All four host pages already spend their one primary-filled button on "Add Organization" /
   "Add Person" / "Add Deal" / "Add Activity", so the views bar gets zero. A dialog is its own
   surface and may spend one.
3. The `Loader2` spinner (`text-primary animate-spin`) during a save and during an export.

**Explicitly NOT accent:** the picker trigger (`variant="outline"`), the bar's save/update control
(`variant="outline"`), `Manage views` and `Export these results` (menu items, inherit
`focus:bg-accent` only), the manage dialog's per-row controls (`variant="ghost"`), and the delete
`AlertDialogCancel` (`variant="outline"`, inherited default).

**Explicitly NO `text-primary` text.** No view name is a link. No owner attribution is a link. This
phase does not depend on F-39-06 being fixed, and the checker should verify the absence rather than
infer it.

**Rule C-40-1 — `Modified` is a WORD in a `Badge variant="secondary"`, never a dot, asterisk,
colour or italic.** The dirty state is the single most consequential thing the bar communicates: a
user who cannot tell that their filters have drifted from the view they think they are looking at
will either overwrite a shared view by accident or believe they saved something they did not. Phase
39's C-3 settled this shape for confidence tiers and the same reasoning applies verbatim. The badge
carries a border, which is what keeps it legible immediately after a `truncate`d name.

**Rule C-40-2 — `Shared`, `Private` and `Default` are WORDS on a muted second line, never icons
alone and never colour.** They render as `text-xs text-muted-foreground`, joined by ` · `, in this
order: visibility, then default, then owner. Examples:
`Shared · Default · by Ana Souza` / `Private` / `Shared · by Ana Souza`.
A lock glyph for private and a share glyph for shared would be two more things to learn and would
carry no meaning to a screen reader without a label anyway.

**Rule C-40-3 — the delete confirmation IS `variant="destructive"`.** Deleting a shared view removes
it from every teammate who selected it and silently drops anyone who defaulted to it back to
unfiltered (a locked decision). That is the same class of consequence as a bulk delete, and this repo
already uses a destructive `AlertDialogAction` for that class. The words carry it too
(`views.delete.action` = "Delete view", body naming the name and the fallout).

**Rule C-40-4 — `views.degraded` is muted body text, NOT an `Alert`, and never `destructive`.**
A view whose `owner` or `pipeline` id no longer exists still rendered a list. Nothing failed, nothing
is unsafe, and a red panel over a working list teaches the user that red means nothing. This is
39-UI-SPEC C-1 continuity: the weight is carried by the sentence. There is no `--warning` token and
this phase does not add one.

## The 320px Reachability Mandate

**This supersedes K-3 as the phase's headline gate. It does not replace it — it is the half K-3 was
missing.**

F-39-07 is the precedent and the warning. Phase 39's viewport matrix asserted only
`scrollWidth <= clientWidth` and returned 305/305 across three locales, GREEN, while a 940px create
dialog at 320x640 put "Create anyway" out of pointer reach — a functional dead-end on mobile that a
passing gate certified. Height and reachability were never covered.

So, for **every** surface and overlay this phase defines:

> **The primary action must be reachable and clickable at 320x640.**

### Rule O-1 — every overlay declares fits-or-scrolls, at its own call site

| Overlay | Primitive | Clamp |
|---|---|---|
| The view picker menu | `DropdownMenuContent` | **already safe by construction** (M-7): `max-h-(--radix-dropdown-menu-content-available-height)` + `overflow-y-auto`. Pass no class that removes either. |
| The save dialog | `DialogContent` | **`className="max-h-[calc(100dvh-2rem)] overflow-y-auto"` is MANDATORY.** The primitive declares neither (M-8) and the headroom is ~54px. |
| The manage dialog | `DialogContent` | same clamp, **plus** `max-h-[50vh] overflow-y-auto` on the inner list so the dialog footer never leaves the screen at any list length. |
| The delete confirmation | `AlertDialogContent` | same clamp as the save dialog. |

**Rule O-2 — nothing in this phase may live in a `Popover` or a `DropdownMenuSubContent`.**
Measured (M-5, M-7): `PopoverContent` is `w-72`, `max-height: none`, `overflow-y: visible`, and the
existing `/activities` filter popover already renders 388px into a 347px slot with 41px clipped off
the top of the viewport. `DropdownMenuSubContent` is `overflow-hidden` with no clamp and opens
sideways into a 241px budget. `DropdownMenuContent` and `DialogContent`-with-clamp are the only two
overlay hosts this phase may use. **This is also why the CONTEXT-nominated host is rejected** — see
§ Surface Placement.

**Rule O-3 — the escape hatch is asserted, not assumed.** Every overlay must dismiss on `Escape`
and on an outside click, and the reachability spec asserts it. F-39-07 was survivable only because
Escape still worked; that is a property to prove, not to hope for.

**Rule O-4 — the save dialog's submit button must not be reachable by `Enter` from the name input in
a way that triggers F-39-08.** `data-table-keyboard.tsx` registers `useHotkeys("enter", …, {
preventDefault: true })` with **no ref**, and its `isFormFocused` guard exempts
INPUT/TEXTAREA/SELECT/contenteditable but **not BUTTON**. On `/organizations` and `/people` — the two
surfaces where that hook is mounted — pressing Enter with the dialog's submit focused navigates the
list behind the dialog and discards the draft. The dialog therefore:
- wraps its fields in a real `<form onSubmit={…}>` so Enter **inside the name input** submits the
  form (the input is exempted by `isFormFocused`, so this path is safe today), and
- the spec asserts that Enter with the submit button focused does **not** navigate.

Fixing F-39-08 itself is out of scope — it is app-wide and touches six surfaces. Working *within* it
is not.

### Rule R-40-1 — the reachability predicate, spelled out

A later plan must prove this, in a real browser, for each surface and overlay. Written as
reachability rather than overflow, and as a `trial` click rather than a visibility check, because a
visible-but-occluded button passes `toBeVisible()` and fails a real user:

```
// 1. anchor — a blank 200 has scrollWidth === clientWidth and passes any overflow assertion
await expect(page.getByRole("button", { name: PICKER_LABEL })).toBeVisible()

// 2. reach — trial:true runs every actionability check including hit-target
//    testing, and fires no event. This is the assertion F-39-07 needed and lacked.
await expect(primary).toBeInViewport()
await primary.click({ trial: true })

// 3. fits-or-scrolls — either the content fits its box, or its box scrolls
const ok = await overlay.evaluate((el) => {
  const cs = getComputedStyle(el)
  return el.scrollHeight <= el.clientHeight
      || cs.overflowY === "auto" || cs.overflowY === "scroll"
})
expect(ok).toBe(true)

// 4. within-viewport — the box itself is on screen, top and bottom
const box = await overlay.boundingBox()
expect(box.y).toBeGreaterThanOrEqual(0)
expect(box.y + box.height).toBeLessThanOrEqual(viewportHeight)
```

Step 4 is what M-5 fails today. Step 2 is what F-39-07 needed. **Neither is expressible as a
`scrollWidth` comparison, which is why `e2e/viewport-320.spec.ts` cannot absorb this and a new spec
file is required.**

| Rule | Requirement |
|------|-------------|
| R-40-2a | **`SavedViewsBar` is `flex flex-wrap items-center gap-2` and occupies its own row.** It wraps to two rows at 320px in all three locales (M-10) and that is accepted, not fought — there is no trigger width at which a 200px trigger and a 139px "Guardar cambios" share a 241px row. |

## Component Contract — `SavedViewsBar`

### Rule B-1 — the bar has exactly two slots

```
[ ▾ {view name} (Modified) ]    [ {save resolver} ]
```

Slot 1 is the picker (`DropdownMenu`). Slot 2 is a **resolver**, not a fixed button: one control, one
label at a time, following the "one resolver per label" convention Phase 39 settled.

### Rule B-2 — every piece of state is computed on the SERVER and passed as a prop

The bar derives nothing. Its props interface is exactly:

```ts
export interface SavedViewsBarProps {
  entityType: ViewEntityType
  views: SavedViewSummary[]        // already scoped to what this user may see
  selectedViewId: string | null     // resolved server-side by comparing URL params to stored filters
  isModified: boolean               // server-computed
  droppedFilterKeys: string[]       // server-computed: which stored keys were invalid on read
  canSave: boolean                  // hasSaveableFilter(entityType, params)
  canExport: boolean                // hasExportableFilter(entityType, params)  — see E-2
  canUpdateSelected: boolean        // owner-or-admin on the selected view
}
```

Three reasons this is a rule and not a preference:

1. **No loading state, no flash.** All four host pages are server components that already
   `await searchParams`; the views come down with the first paint. A client-fetched picker would
   flash "All records" over the user's actual default view on every navigation. **There is therefore
   no loading state anywhere in this phase**, and that absence is a decision (§ State Matrix).
2. **`isModified` and `droppedFilterKeys` are not the same thing and cannot both be derived from the
   URL.** Both manifest as "the URL differs from the stored blob". Only the server knows *why*: a key
   the user changed (modified) versus a key the read-side validator dropped because its target no
   longer exists (degraded). A client comparing the two would label every degraded view "Modified"
   and invite the user to save the damage.
3. **It is gateable.** A parsed-interface assertion (§ V-40-5) can prove the props are exactly these
   eight and that the component body contains no comparison of `searchParams` against a `filters`
   blob. That is a structural gate, not a token grep (K-9).

### Rule B-3 — the bar is a client component wrapped in `<Suspense>`

It calls `useSearchParams` (to write, and to preserve unrelated params), `usePathname` and
`useRouter`. `ActivityFilters` and `DealFilters` both already wrap for exactly this reason; the
fallback is the picker trigger in its disabled shape with the label `views.allRecords`, matching
`activity-filters.tsx`'s `<Suspense fallback={<Button variant="outline" size="sm">…}` precedent.

### Rule B-4 — the bar is not sticky, not fixed, and adds no spacer

See R-40-2f and K-8.

### Rule B-5 — slot 2's five resolutions

| Condition | Slot 2 renders | Notes |
|---|---|---|
| `!canSave` | **`views.needsFilter`** as `text-xs text-muted-foreground` — "Filter this list to save it as a view." | **Not a disabled button.** 39-UI-SPEC P-7 forbids a bare greyed control with no explanation; a sentence in the control's place *is* the explanation and costs the same 36px row. On an unfiltered list the bar has nothing else to say, so this is the bar's empty state rather than noise. |
| `canSave && selectedViewId === null` | `Button variant="outline"` reading **`views.saveNew`** ("Save view") | opens the save dialog with an empty name and no target choice |
| `canSave && selectedViewId && isModified && canUpdateSelected` | `Button variant="outline"` reading **`views.saveChanges`** ("Save changes") | opens the save dialog with the target `RadioGroup` (§ Rule S-3) |
| `canSave && selectedViewId && isModified && !canUpdateSelected` | `Button variant="outline"` reading **`views.saveNew`** | the user cannot overwrite someone else's shared view; the dialog explains why via `views.save.targetNewOnly` |
| `canSave && selectedViewId && !isModified` | **nothing** | there is nothing to save. `views.saveNew` stays reachable as a menu item inside the picker, so the capability is not lost — only the redundant button is. |
| export in flight (overrides all of the above) | `Loader2` + **`views.exporting`** ("Preparing your file…"), muted, non-interactive | § Rule E-4 |

### Rule B-6 — the search `<Input>` must re-sync when a view changes it **[CONSEQUENCE OF A LOCKED DECISION]**

**Measured (M-9): it does not today.** `defaultValue={search}` is ignored after mount, and app-router
navigation re-renders without remounting. Applying a saved view that stores `search=acme` will filter
the list correctly and leave the search box showing whatever was in it before; selecting
`views.allRecords` will clear the filter and leave "acme" visible.

That is **success criterion 1 failing visibly** — "reopens it later with filters restored" is not met
if the control that shows the filter shows the wrong thing. Three call sites must re-sync:

| File | Control |
|---|---|
| `src/app/organizations/data-table.tsx` | `<Input placeholder="Search organizations..." defaultValue={search}>` |
| `src/app/people/data-table.tsx` | `<Input placeholder="Search people..." defaultValue={search}>` |
| `src/app/activities/activity-filters.tsx` | `<Input placeholder="Search activities..." defaultValue={search}>` |

The fix is `key={search}` on the `Input` (remount on param change), **not** conversion to a
controlled input: these inputs are debounced writers, and a controlled value fed from the URL fights
its own 300ms debounce on every keystroke. `key` remounts only when the URL actually changes, which
is exactly the event that must reset the box.

`/deals` needs no change — it has no search input.

## The `?view=none` Escape Param **[CONSEQUENCE OF A LOCKED DECISION]**

CONTEXT locks two things that interact badly and does not say how:

- the default view is applied by **redirecting**, and **only when the incoming URL carries no
  params**;
- there is an **explicit "All records" pseudo-view as the escape hatch**.

Together, a bare URL is unreachable. Selecting "All records" would navigate to `/organizations`,
which carries no params, so the server redirects straight back into the default view. Worse, the
existing controls already navigate to bare paths:

| # | File | Call | Result today |
|---|---|---|---|
| 1 | `src/app/organizations/data-table.tsx` | `router.push("/organizations")` (empty-search branch) | bare → hijacked |
| 2 | `src/app/people/data-table.tsx` | `router.push("/people")` | bare → hijacked |
| 3 | `src/app/activities/activity-filters.tsx` | `clearAll()` → `router.push(pathname)` | bare → hijacked |
| 4 | `src/app/activities/activity-filters.tsx` | `setFilter(key, "")` on the last remaining chip | can produce bare → hijacked |
| 5 | `src/app/activities/activities-client.tsx` | `router.push("/activities")` (the no-results "Clear filters" button) | bare → hijacked |
| 6 | `src/app/deals/deal-filters.tsx` | `clearAll()` keeps `pipeline` but produces a bare query when no pipeline param was set | can produce bare → hijacked |

`kanban-board.tsx`'s clear (`router.replace(?pipeline=…)`) is already safe; it is listed in the
inventory as unchanged so the plan does not "fix" it.

**Rule U-1 — one helper, six call sites.** `src/lib/views/url-params.ts` exports:

```ts
export const VIEW_ESCAPE_KEY = "view"
export const VIEW_ESCAPE_VALUE = "none"

/** Serialise params, appending view=none iff no whitelisted filter key survives. */
export function withViewEscape(entityType: ViewEntityType, params: URLSearchParams): string
```

Every client writer on the four surfaces routes its query string through it. The helper is
idempotent, never throws, and imports nothing but its own sibling types — the
`src/app/duplicates/url-params.ts` shape verbatim, including the no-DB-import rule (all six callers
are `"use client"`, so anything this module imports enters the browser bundle).

**Rule U-2 — the redirect guard is "no params at all", and `view=none` is a param.** So the escape
URL is never hijacked, and the redirect cannot loop: its target always carries at least one
whitelisted filter key.

**Rule U-3 — `view` is never stored in a view's `filters` blob, and neither is `page`.** The
whitelist is per entity type and is the single definition of what a view may contain:

| entityType | Stored filter keys |
|---|---|
| `organization` | `search` |
| `person` | `search` |
| `deal` | `pipeline`, `stage`, `owner`, `assignee`, `dateFrom`, `dateTo` |
| `activity` | `type`, `owner`, `assignee`, `status`, `dateFrom`, `dateTo`, `search` |

Excluded on every surface: `page`, `view`. A membership test against frozen literal arrays, so
`__proto__` and `constructor` are ordinary non-members — the `parseDuplicateTab` precedent.

**Rule U-4 — a redirect, not a rewrite, and the address bar keeps telling the truth.** CONTEXT is
explicit and this rule exists only to restate the UI consequence: after the redirect the URL carries
the view's params, so the picker resolves the selection from the URL like any other visit, and there
is no second code path for "arrived by default".

## Surface 1–4 — The View Picker Contract

`DropdownMenu`. Height-safe by construction (M-7). One trigger, one menu, no submenus (O-2).

| Rule | Requirement |
|------|-------------|
| V-1 | **Trigger:** `Button variant="outline"` with `min-w-0 max-w-[200px]`, a `ChevronDown` icon at `shrink-0`, an accessible name of `views.picker.label` ("Saved views"), and a visible label of the selected view's name (`truncate`) or `views.allRecords` when none is selected. When `isModified`, a `Badge variant="secondary" shrink-0` reading `views.modified` follows the name. |
| V-2 | **Selection is a `DropdownMenuRadioGroup` of `DropdownMenuRadioItem`s**, not plain items. `role="menuitemradio"` + `aria-checked` exposes the selection to assistive tech instead of drawing it; the `Check` indicator the block ships is a shape, not a colour, and is additive. |
| V-3 | **Menu anatomy, top to bottom.** (1) `views.allRecords` as the first radio item, always present, always first. (2) `DropdownMenuSeparator`. (3) `DropdownMenuLabel` = `views.groupMine`, then the user's own views alphabetically. (4) `DropdownMenuSeparator` + `DropdownMenuLabel` = `views.groupShared`, then shared views owned by others, alphabetically. (5) `DropdownMenuSeparator`. A shared view whose owner was soft-deleted stays visible and stays functional — it is a filter set, not a record — and only its attribution changes. |
| V-6 | **The "Shared with me" group contains only `isShared` views owned by someone else. It never contains a private view, for any viewer, including an admin.** This is Decision 3 taken literally, and it has a consequence worth stating: a soft-deleted user's private views become unreachable by anyone, forever. Accepted — they are saved filter sets with no record content — but not silent. |
| V-7 | **No cap and no paging on the menu.** It renders every view the viewer may see; the primitive clamps the height and scrolls (M-7). A cap plus an "and N more" affordance would be a second list implementation for a case that does not occur, and the manage dialog already lists everything. |
| V-8 | **`views.emptyMenu`** ("No saved views yet") renders as a non-interactive `DropdownMenuLabel` between the separators when the viewer has zero visible views. `views.allRecords`, `views.saveNew` and `views.manageAction` stay present — the menu is never a dead end. |
| V-9 | **Selecting a view navigates.** `router.push` to the pathname plus the view's stored filter keys, through `withViewEscape` (U-1). Every param *not* in the whitelist is dropped, including `page` — a view lands you on page 1. Selecting `views.allRecords` navigates to `?view=none`. |
| V-10 | **The menu closes on selection** for every item except `views.exportAction` (§ Rule E-4). |

### Rule V-11 — `views.degraded`, the degraded-read notice

Rendered as one `text-xs text-muted-foreground` line **beneath** the bar (never inside the menu, never
as an `Alert`) whenever `droppedFilterKeys.length > 0`:

> "Part of this view no longer exists and was ignored."

It covers all three degradations in one sentence, deliberately: a deleted `owner`, a deleted `stage`,
and a deleted `pipeline` falling back to the default board (Decision 4). Naming *which* key was
dropped would need a per-key label resolver — a second field-label map, which 39-UI-SPEC M-4
explicitly refused — and the repair action is the same in all three cases: re-filter and save.

When the notice shows and `canUpdateSelected`, slot 2 resolves to `views.saveChanges` so the repair
is one click. When the notice shows and the user cannot edit, the notice stands alone; the view is
still usable.

**The list still renders. There is no 500, no `notFound()`, and no "pipeline not found" page** — the
read side is authoritative and non-throwing (CONTEXT), and there is no `error.tsx` above these routes
to catch anything (M-14).

## Export Contract

Criterion 4: "User exports the records matching a saved view." Decision 2 extends `ExportFilters`
with the missing params and adds a **hard no-empty-filters guard**.

| Rule | Requirement |
|------|-------------|
| E-1 | **The affordance is `views.exportAction` in the picker menu** ("Export these results (CSV)"), not a toolbar button. All four toolbars are at or past their width budget (M-2, M-3, M-4) and the menu is the one height-safe container on these pages. |
| E-2 | **`canExport` is NOT `canSave`. [CONSEQUENCE OF A LOCKED DECISION]** Two predicates, both in `src/lib/views/url-params.ts`: `hasSaveableFilter` counts every whitelisted key **including `pipeline`**, because Decision 4 requires a deals view to carry its pipeline. `hasExportableFilter` **excludes `pipeline`**, because a pipeline is a board selector, not a filter — the app's own UI already separates them ("Pipeline:" versus "Filters") — and 25,195 live deals scoped only by pipeline is the unbounded export 38-CONTEXT:110-116 exists to prevent. **Decision 2 preserves 38's intent by the guard; this is the line where the guard actually falls.** CONTEXT does not draw it, and without it the guard is satisfiable by a control that filters nothing. |
| E-3 | **When `!canExport` the item is rendered `disabled` with its reason as a second muted line**, `views.export.disabledReason`: "Choose at least one filter first. An unfiltered export isn't allowed." A menu is a vertical list with room for a second line, so this is the one place in the phase where a disabled control is correct — the reason is adjacent, not hidden in a tooltip. |
| E-4 | **In-flight state lives in the BAR, not in the menu.** On select, `onSelect` is **not** prevented: the menu closes, and slot 2 resolves to `Loader2` + `views.exporting` ("Preparing your file…"), muted and non-interactive (B-5). A menu held open for the duration of a 50k-row `SELECT` is dismissible by any outside click, which would strand the user with no feedback; the bar is in the page and nothing can dismiss it. State is set inside a `startTransition` callback, never in an effect body (K-7). |
| E-5 | **No progress bar.** `fetchFilteredData` is one query, not a job — there is no progress to report. And `ProgressBar` has no `role="progressbar"` / `aria-valuenow` (F-39-04), so a fake bar would add an a11y defect in service of a lie. The `Loader2` plus the word is the honest affordance. |
| E-6 | **Download through `bulk-action-bar.tsx:73-83`'s idiom, including the `revokeObjectURL`.** Copy in shape; do not write a fourth downloader. The filename comes from the server so the name and the row count cannot disagree, and it is never translated. There is no `/api/export` route (M-14) and this phase does not add one. |
| E-7 | **Success reuses `bulk.exported`** — `{count, plural, one {# record exported.} other {# records exported.}}`. Zero new keys for the happy path. `REQUIRED_BULK_KEYS` stays at 47; reuse adds nothing to a namespace it does not own. |
| E-8 | **Generic failure reuses `bulk.error.exportFailed`.** Two new keys cover only what `bulk` cannot say: `views.export.tooMany` ("This view matches more than {max} records. Narrow the filters and export again.") for the ~50k cap, and `views.export.refused` ("That export was refused because no filter was applied.") for the server guard's own path. `bulk.error.tooMany` is deliberately not reused — its copy is about a *selection* of ids and would read as nonsense here. |
| E-9 | **Export is available to every authenticated user, not admin-gated.** That is Decision 2's direct consequence: the guard replaces the gate. Recorded explicitly because it is a visible widening of a Phase 38 restriction and a reviewer will and should ask. |
| E-10 | **CSV only.** No format picker, no JSON, no Pipedrive shape. Locked. |

**Rule N-1 — do NOT run `shadcn add`, for any block, for any reason.** It silently bumps `radix-ui`
and rewrites roughly 1184 lines of `package-lock.json`, and this phase needs no primitive it does not
already have (verified by directory listing this session). If a later plan concludes a primitive is
genuinely missing, it must **say so and vendor the file by hand** with the unified `radix-ui` import
(K-5) rather than reach for the CLI.

**Rule N-2 — no dependency is added.** Not `cmdk` (the picker is a `DropdownMenu`, not a
`Command`), not a date library, not a diff library. `views.manage.filterCount` is a count, not a
rendered diff, precisely so no diff library is tempting.

## What Cannot Be Met As Written

Stated plainly rather than designed around.

1. **Success criterion 4 has a scope hole on `/deals`, and it is the right hole.** "User exports the
   records matching a saved view" is met on `/organizations`, `/people`, `/activities`, and on
   `/deals` for any view carrying at least one of `stage`/`owner`/`assignee`/`dateFrom`/`dateTo`. It
   is **not** met for a deals view carrying only `pipeline` — that export is refused by design
   (E-2), because 25,195 live deals scoped only by board selector is the unbounded export
   38-CONTEXT:110-116 forbids, and Decision 2 preserves that intent by the guard. The user sees a
   disabled menu item with `views.export.disabledReason` next to it, never a silent no-op.

2. **Success criterion 1 is thin on `/organizations` and `/people`, exactly as Decision 1 accepts.**
   A view there stores one string. The bar, the dialogs and the guard all work; the *value* is small
   until the deferred filters phase lands. This spec does not paper over it: `views.needsFilter` is
   what an org user sees until they type in the search box, and that is the truthful state.

3. **A soft-deleted user's private views become permanently unreachable.** Decision 3 is taken
   literally, so no admin can see or delete them (V-6). Six such users exist (M-11). Accepted — they
   hold no record data — but it is a row that outlives every actor who can act on it.
