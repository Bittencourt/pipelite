<task type="auto">
  <name>Task 2: V-40-1 — the reachability suite</name>
  <files>e2e/saved-views-320.spec.ts</files>
  <action>
    Four surfaces × three locales. For each combination, in this order:

    (a) ANCHOR FIRST. `await expect(page.getByRole("heading", { level: 1, name: <from catalog> }))
    .toBeVisible()`. A blank 200 satisfies every geometric assertion silently — this is the 45-02
    anti-vacuity rule and it is not a redundant smoke check.

    (b) THE PICKER MENU. Open it. Then, on the `DropdownMenuContent` locator:
    ```
    const box = await overlay.boundingBox()
    expect(box.y).toBeGreaterThanOrEqual(0)
    expect(box.y + box.height).toBeLessThanOrEqual(640)
    const ok = await overlay.evaluate((el) => {
      const cs = getComputedStyle(el)
      return el.scrollHeight <= el.clientHeight || cs.overflowY === "auto" || cs.overflowY === "scroll"
    })
    expect(ok).toBe(true)
    ```
    Then `scrollIntoViewIfNeeded()` + `click({ trial: true })` on the **LAST** menu item
    (`views.manageAction`). The last item is the one a clipped menu loses.
    **Step "box.y >= 0" is what the `/activities` filter popover fails today** (M-5: 388px at
    `top: -41`). Neither this nor the trial click is expressible as a `scrollWidth` comparison, which
    is why `e2e/viewport-320.spec.ts` cannot absorb this and a new file is required (R-1).

    (c) THE SAVE DIALOG. Reach it from the picker's `views.saveNew` (navigate to a filtered URL first,
    so `canSave` is true — on `/organizations` and `/people` that means `?search=acme`). Then:
    ```
    await expect(submit).toBeInViewport()
    await submit.click({ trial: true })
    ```
    plus fits-or-scrolls and box-within-viewport on the `DialogContent`. **`trial: true` runs every
    actionability check including hit-target testing and fires no event — it is the assertion that
    would have caught the unreachable "Create anyway", and `toBeVisible()` is not**, because a
    visible-but-occluded button passes `toBeVisible()` and fails a real user. Also assert the footer is
    stacked with the submit visually FIRST (S-12): compare the submit's `boundingBox().y` against
    Cancel's and expect it to be smaller.

    (d) THE MANAGE DIALOG, on the entity type seeded with ≥8 views. Same four checks on the
    `DialogContent`, plus the same four on the inner list container, plus `click({ trial: true })` on
    the LAST row's delete button after `scrollIntoViewIfNeeded()`.

    (e) THE DELETE `AlertDialog`. Open it from that last row. Same four checks, plus
    `click({ trial: true })` on the destructive action. **Do not click it for real** — `trial: true`
    fires no event, which is exactly why it is safe to assert on a destructive control.

    (f) O-3 — ESCAPE DISMISSES EACH. For all four overlays: press `Escape`, assert the overlay is
    detached. F-39-07 was survivable only because Escape still worked; that is a property to prove,
    not to hope for.

    Locale handling: the three locales lengthen labels (M-10: "Guardar cambios" is 139px vs 115px), so
    every locale must run every step. Do not assert pixel widths — assert reachability. The one width
    fact to record rather than assert is whether the bar wrapped to one row or two, per locale, so the
    summary carries the measurement.

    On `/people`, `/organizations` and `/activities`, wait on a settled anchor before each interaction:
    the hydration mismatch in BACKLOG can swallow a dialog-trigger click and these three routes are the
    flakiest in the suite.
