  <name>Task 1: validateStoredFilters — the non-throwing read-side validator</name>
  <files>src/lib/views/validate.ts, src/lib/views/__tests__/validate.test.ts</files>
  <behavior>
    `validateStoredFilters(entityType, filters, catalog)` returns
    `{ filters: ViewFilters, droppedKeys: string[] }`.

    `catalog` is a plain, already-fetched value object — NOT a database handle. That is what makes
    this function pure and unit-testable with no db mock:
    ```ts
    interface ViewFilterCatalog {
      userIds: ReadonlySet<string>       // active users only (deletedAt IS NULL)
      pipelineIds: ReadonlySet<string>   // deletedAt IS NULL
      stageIdsByPipeline: ReadonlyMap<string, ReadonlySet<string>>
      activityTypeIds: ReadonlySet<string>
    }
    ```

    Rules, each with its own test:
      - the input is first run through `pickFilterParams`, so a stale key from an older whitelist and
        a `page`/`view` key are gone before any existence check
      - `owner`, `assignee` → dropped when not in `userIds`. Both of the six soft-deleted users are a
        live case here.
      - `pipeline` (deal only) → dropped when not in `pipelineIds`
      - `stage` (deal only) → dropped when not in `stageIdsByPipeline` for the SURVIVING pipeline. If
        `pipeline` was itself dropped, `stage` is validated against the union of all stages; a stage
        that exists but belongs to a different pipeline than the one in the view is dropped, because
        the board would render zero columns matching it.
      - `type` (activity only) → dropped when not in `activityTypeIds`
      - `status` (activity only) → dropped unless it is one of the frozen literals
        `["pending","completed","overdue"]` (that is exactly what `activity-filters.tsx` writes)
      - `dateFrom`, `dateTo` → dropped unless `/^\d{4}-\d{2}-\d{2}$/` AND
        `Number.isFinite(Date.parse(v))`. A `new Date("garbage")` reaching a `gte()` is an
        `Invalid Date` in SQL, which is a 500 on a page with no `error.tsx` above it (M-14).
      - `search` → never dropped; any surviving string is valid
      - `droppedKeys` is sorted and de-duplicated, so `views.degraded` fires deterministically
      - NEVER THROWS: assert over a table containing `null`, `undefined`, a null-prototype object, an
        array value, a nested object value, and a 1 MiB string. Every row returns
        `{ filters: {}, droppedKeys: [...] }` or better.

    ANTI-VACUITY: one test passes a filter set where EVERY key is valid and asserts
    `droppedKeys.length === 0` and `filters` deep-equals the input. A validator that dropped
    everything would satisfy every "is dropped" test above; only this one distinguishes it.

    DISCRIMINATION, named: this suite must FAIL if `owner` stops being checked against `userIds`, if
    `status` accepts an arbitrary string, or if `dateFrom` accepts `"1"`. Write one test per named
    defect with that defect in its title, so a green run is a claim about three specific regressions
    and not a mood.
  </behavior>
  <action>
    Create `src/lib/views/validate.ts`. It imports `pickFilterParams` and the whitelist from
    `url-params.ts` and imports **no database module** — the catalog is passed in. Write a header
    saying the read side is AUTHORITATIVE AND NON-THROWING (40-CONTEXT), that there is no `error.tsx`
    anywhere under `src/app` (M-14) so a throw here is a blank page, and that the
    `readOrgIdentityInputFields` degrade-to-`[]` posture in `organizations/page.tsx:123` is the

    Write the sentence: **this function validates SHAPE and EXISTENCE, never effectiveness.** A
    `status=overdue` or `dateFrom` on `/activities` currently narrows nothing (the list-side gap plan
    40-13 closes); dropping it here would silently delete a filter the user set and the chip row
    displays. That is a different bug from the one being avoided.

  <action>
    Create `src/lib/views/queries.ts` — server-only, imports `@/db`.

    `listVisibleViews(entityType, viewer: { id: string; role?: string }): Promise<SavedViewSummary[]>`

    ONE query with the visibility predicate IN SQL, never a post-fetch `.filter()`:
    ```
    where: and(
      eq(savedViews.entityType, entityType),
      or(eq(savedViews.ownerId, viewer.id), eq(savedViews.isShared, true))
    )
    with: { owner: { columns: { id: true, name: true, email: true, deletedAt: true } } }
    orderBy: [asc(savedViews.name)]
    ```
    **There is no `role === "admin"` branch, and its absence is the decision.** Write that in a
    comment naming Decision 3 and naming the idiom being departed from
    (`src/app/deals/actions.ts:83`, locked for Trash in 37-CONTEXT.md:31): "private" that an admin can
    read is not private. An admin sees exactly what a member sees here. Also record the accepted
    consequence (A6/V-6): a soft-deleted user's private views become unreachable by anyone, forever;
    six such users exist.

    Then, in the SAME round trip (`Promise.all`), read this viewer's default row:
    `db.query.savedViewDefaults.findFirst({ where: and(eq(userId, viewer.id), eq(entityType, …)) })`.

    Map each row to `SavedViewSummary`:
      - `filters` — **left as stored**. Validation belongs to `resolve.ts`, which needs the catalog.
      - `isOwnedByViewer` = `ownerId === viewer.id`
      - `isDefaultForViewer` = `defaultRow?.viewId === row.id`
      - `canEdit` = `isOwnedByViewer || viewer.role === "admin"`. This one DOES keep the admin branch:
        CONTEXT says "only the owner (or an admin) may edit or delete a view", and it is about
        mutation, not visibility. An admin can only edit a view they can already see, so it does not
        reopen Decision 3.
      - `ownerLabel` = `owner.deletedAt ? null : (owner.name || owner.email)`. **Two of three active
        users have `name = NULL`**, so the `||` is the common path here, not the fallback. `null`
        selects `views.ownerUnavailable`; a bare uuid must never reach the UI (V-5).
      - `ownerIsInactive` = `owner.deletedAt !== null`
      - `filterCount` = `countFilters(entityType, row.filters)` — computed from the whitelist so the
        number `views.manage.filterCount` renders and the number the parser accepts cannot diverge
        (G-3)

    `readDefaultViewForUser(entityType, userId)` returns the joined default view row or `null`. It
    must also apply the visibility predicate: a user whose default points at a view that has since
    been made private by its owner gets `null`, and the locked "falls back to unfiltered, with no
    error" behaviour follows.

    Wrap both in try/catch returning `[]` / `null` and `console.error`. A failed view read degrades
    to the unfiltered list; it must never be the reason `/organizations` goes blank.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser URL → resolver | every `searchParams` value is attacker-authored |
| another user's row → this viewer | the SQL `or(ownerId = me, isShared)` predicate is the entire privacy control for criterion 2 |
| stored blob → SQL | a `filters` value written under an older whitelist, or against a since-deleted id |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-40-17 | Information disclosure | `listVisibleViews` | mitigate | visibility is a SQL predicate (`ownerId = viewer OR isShared`), never a post-fetch filter, and carries **no** admin branch. A post-fetch filter would ship every private view's name to the client in the RSC payload even if it were not rendered |
| T-40-18 | Information disclosure | `readDefaultViewForUser` | mitigate | the same predicate is applied, so a default pointing at a view that has since been made private resolves to `null` and the list renders unfiltered — the locked no-error fallback |
| T-40-19 | Tampering | `validateStoredFilters` | mitigate | a malformed `dateFrom` never reaches `new Date()` inside a `gte()`; the regex + `Date.parse` gate is what stops an `Invalid Date` becoming a 500 on a route with no `error.tsx` (M-14) |
| T-40-20 | Denial of service | `redirectTargetFor` | mitigate | returns `null` for an empty validated set, so the "no params at all" redirect guard cannot produce an infinite redirect loop |
| T-40-21 | Information disclosure | `ownerLabel` | mitigate | resolves to `user.name \|\| user.email` or `null`; a raw uuid is never returned, so a view's owner id cannot be harvested from the picker |
| T-40-SC | Tampering | npm installs | mitigate | this plan installs nothing |
</threat_model>
