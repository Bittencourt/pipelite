Make `ExportFilters` able to express a saved view, teach the four fetchers the new keys, and add ONE
server action that exports what a view matches — guarded so it can never degrade into "export
everything".

(38-CONTEXT.md:110-116: no filters-taking export reachable without an admin gate) by replacing the
gate with a guard. **The guard is the load-bearing part, and this is the plan where it either holds or
does not.** Amendment A2 and UI-SPEC E-2 draw the line: `hasSaveableFilter` counts `pipeline`,
`hasExportableFilter` does not.
Output: extended export types and fetchers, `exportViewResults`, and the invariant test that keeps the
guard honest.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-40-29 | Elevation of privilege | `exportViewResults` | mitigate | `guardExportInput` re-derives the filter map with `pickFilterParams` and requires `hasExportableFilter` on the RESULT. An action receiving `{}` is refused, which is what preserves 38-CONTEXT.md:110-116's intent after Decision 2 removed its admin gate |
| T-40-30 | Elevation of privilege | `hasExportableFilter` vs the fetchers | mitigate | the task-1 invariant gate proves every authorizing key is also a SQL predicate. Without it, `status=overdue` (which the LIST does not apply today) would authorize a 79,022-row export while narrowing nothing |
