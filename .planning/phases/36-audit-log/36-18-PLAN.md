  <action>
    Create `src/lib/audit/prune.ts`.

    Constants at module scope, each with an inline comment carrying its justification:
    `INITIAL_DELAY = 60_000` (let the server finish booting), `TICK_INTERVAL = 24 * 60 * 60 * 1000`
    (daily), `BATCH_SIZE = 5_000` (measured: 17.8 ms per batch at 1M rows),
    `MAX_BATCHES_PER_TICK = 20` (⇒ ≤100k rows/day, ≤~0.4 s of DELETE per tick).

    `startAuditPruner()` logs once and calls `scheduleTick(INITIAL_DELAY)`.

    `scheduleTick(delay)` is module-private. Inside the timer callback:
    - `try`: `const days = await readRetentionDays()`. If `null`, log
      `[audit-prune] retention unset or invalid — no rows deleted` and delete NOTHING. Keeping data
      is always the safe direction for an audit log, and this is a privacy trade-off as well as a
      safety one: the retention window is the only expiry mechanism for the former values stored in
      `changes`.
    - Otherwise loop up to `MAX_BATCHES_PER_TICK`, calling a private `deleteBatch(days, BATCH_SIZE)`,
      accumulating the count, and breaking early when a batch returns fewer than `BATCH_SIZE`.
    - Log the total and the window every tick, even when zero. This log line is the only signal that
      the pruner is falling behind the write rate.
    - `catch`: `console.error("[audit-prune] Tick error:", error)`.
    - AFTER the `try`/`catch`, outside it: `scheduleTick(TICK_INTERVAL)` under the comment
      `// Always schedule the next tick`.

    `deleteBatch(days, limit)` executes:
    `DELETE FROM audit_log WHERE ctid IN (SELECT ctid FROM audit_log WHERE created_at < now() - make_interval(days =&gt; ${days}) LIMIT ${limit})`
    and returns the affected row count from the result.

    Bind the day count as a parameter and let Postgres compute the cutoff with
    `now() - make_interval(days =&gt; $1)`. **Never compute the cutoff as a JS `Date` and never bind
    one into the fragment** — postgres.js throws `ERR_INVALID_ARG_TYPE`, and the near-miss form
    `${date}::timestamp` lets Postgres resolve the parameter to OID 1114 and the driver re-serialize
    through a `Date`, truncating microseconds.

    Do NOT use `LIMIT` inside `DELETE` (invalid in Postgres) and do NOT use the `id IN (SELECT id …)`
    form. Write the measured comparison into the comment above `deleteBatch` — 17.8 ms vs 311 ms vs
    395.7 ms — because the `id IN` form is what a careful engineer reaches for first and it is the
    second-worst option even with the index.

    Run green. Commit: `feat(36-18): add capped ctid audit retention pruner`.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-09 | Denial of Service | pruner starvation — the daily tick never catches up | mitigate | `MAX_BATCHES_PER_TICK = 20` ⇒ 100k rows/day. If steady-state writes exceed that the table grows forever AND the log says so, because rows-deleted is logged every tick. The visibility is the control. |
| T-36-39 | Denial of Service | a long write lock blocking the application | mitigate | Capped `ctid` batches take a `RowExclusiveLock` only, which does not block concurrent readers or other row writers. An unbounded `DELETE` is the exact long-lock 36-CONTEXT forbids. Measured 17.8 ms per 5,000-row batch. |
| T-36-19 | Repudiation | a silently disabled retention policy | mitigate | The tail `scheduleTick` sits outside the `try`, asserted by a test that advances timers past a throwing tick and checks `vi.getTimerCount()`. |
| T-36-18 | Tampering | an unreadable setting causing an unbounded delete | mitigate | `readRetentionDays` returning `null` results in zero database calls in that tick, asserted by the absence of a `db.execute` call rather than by a zero count. |
| T-36-37 | Tampering | a JS `Date` truncating the cutoff | mitigate | The cutoff is computed server-side with `now() - make_interval(days => $1)`; `grep -c "new Date"` in the module is asserted at `0`. |
| T-36-23 | Repudiation | a dead pruner in the Docker standalone build | mitigate | Registered inside the `NEXT_RUNTIME` guard; the `[audit-prune]` startup log line is checked in the browser verification in 36-20. |
