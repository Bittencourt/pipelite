<objective>
Make the `import` actor kind real, and record what an import did — as ONE summary row per import run,
written by the importer.

Purpose: ROADMAP SC-3 requires import-made changes to be distinguishable by actor kind. Both
importers bulk-insert through a private `batchInsert` helper with no `crmBus` event, so a pure
subscriber cannot see them and the `import` kind would otherwise never appear.

**Two consequences this plan creates deliberately, both locked by 36-CONTEXT § Post-Research
Addendum and both of which the phase SUMMARY must state plainly rather than gloss:**

1. **SC-3 is satisfied at SESSION granularity, not per-record.** An import is distinguishable from a
   user change, but an individual imported record cannot be traced back to the import that made it.
   Per-record events were rejected on measured cost: a 25,206-deal import would become 25,206
   workflow-trigger evaluations and up to that many webhook deliveries.
2. **SC-5 holds for the four CRM mutation modules but NOT for the importers**, which write their
   summary row directly. The subscriber remains the sole capture path for every `crmBus`-emitting
   write; the importers emit nothing and are therefore outside that claim.

Output: five `runWithActor` wraps and two summary-row writers.
</objective>

  <action>
    In each of the four entry points, after the existing session guard:

    1. Mint `const importRunId = crypto.randomUUID()` — the identity of this import run.
    2. Wrap the entire remaining body in
       `runWithActor({ kind: "import", userId: session.user.id, importSessionId: null }, async () =&gt; { ... })`.
       `importSessionId` is `null` on this path because the CSV importer creates no
       `import_sessions` row and the audit column carries a real foreign key — writing a
       non-existent id would fail the constraint. Comment that.
    3. On the SUCCESS return path only, write one audit row before returning:
       `entityType: "import_session"`, `entityId: importRunId`, `action: "created"`,
       `changes: { &lt;entity&gt;: { from: null, to: count }, warnings: { from: null, to: warnings.length }, autoCreated: { from: null, to: &lt;n&gt; } }`,
       `actorKind: "import"`, `actorUserId: session.user.id`, `workflowRunId: null`,
       `importSessionId: null`.
       Use the counts each action already computes — do not add a query to derive them.
    4. `await` this insert (unlike the subscriber's fire-and-forget) and wrap it in its own
       `try`/`catch` that logs with an `[audit-import]` prefix and swallows. An audit-row failure must
       not turn a successful import into a reported failure; the import already happened and the user
       needs to be told the truth about it.

    The error return paths write no row. An import that failed before writing anything has nothing to
    record, and the four actions already surface their own error to the user.

    The ALS wrap is deliberately wider than the summary row needs: any code path inside these actions
    that DOES emit a `crmBus` event (auto-created organizations and people, if they route through a
    mutation) will now be attributed `import` rather than `system`. Verify during execution whether
    the auto-create paths call the mutation layer or `batchInsert`, and record the answer in the
    SUMMARY — it determines whether auto-created records get per-record audit rows.

    Do NOT add `crmBus.emit` to `batchInsert` or to any per-record path. That is the rejected option:
    it drives `workflow-trigger.ts`, which subscribes to all thirteen events, turning a 25,206-deal
    import into 25,206 trigger evaluations.
  </action>
