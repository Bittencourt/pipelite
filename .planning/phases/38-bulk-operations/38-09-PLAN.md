<objective>
Create the inline per-record failure report: an `Alert variant="destructive"` that names every record
that failed and why.

Purpose: SC-3 is "any per-record failure is named rather than silently swallowed". That is why
deletion and reassignment are per-record and sequential rather than one transaction — an aborting
transaction structurally cannot name a per-record failure. The report is one of the two places a
partial failure surfaces (the other is the toast summary, owned by plan 38-10), and it is the one that
carries the individual records. A cap of the "and 3 more" kind IS the swallowing SC-3 forbids, so
height is bounded by a scroll box instead.
Output: one `'use client'` component and a comment-stripped source gate.
</objective>

Emit exactly this prop contract — plans 38-15..38-18 mount this component directly:

  import type { BulkFailure, BulkOperationKind } from "@/lib/bulk/types"

  export interface BulkFailureReportProps {
    kind: BulkOperationKind            // "delete" | "reassign"
    failures: BulkFailure[]            // [{ id, reason }]
    /** id -> display name, captured AT SUBMIT TIME by the caller. */
    labelById: Record<string, string>
    onDismiss: () => void
  }
  export function BulkFailureReport(props: BulkFailureReportProps): React.ReactElement | null

Return `null` when `failures` is empty, so a caller can mount it unconditionally.

Types come from `src/lib/bulk/types.ts` (plan 38-06):
  BulkFailureReason = "notFound" | "notPermitted" | "alreadyDeleted" | "unknown"
  BulkFailure = { id: string; reason: BulkFailureReason }
  BulkOperationKind = "delete" | "reassign"

Copy keys, all landed by plan 38-01:
  bulk.failures.deleteTitle   ({count} ICU plural)
  bulk.failures.reassignTitle ({count} ICU plural)
  bulk.failures.retryHint
  bulk.failures.dismiss
  bulk.reason.notFound / .notPermitted / .alreadyDeleted / .unknown

Primitive facts that constrain the markup (src/components/ui/alert.tsx, read directly):
  - `Alert` hardcodes `role="alert"` at :27 — no bespoke live region is needed or permitted.
  - The `destructive` variant is `border-destructive/50 text-destructive dark:border-destructive
    [&>svg]:text-destructive` at :12-13 — NO background fill, which is what makes a destructive
    REGION admissible here rather than only a destructive control.
  - `AlertTitle` is `mb-1 font-medium leading-none tracking-tight` at :40, i.e. weight 500. The Label
    role asks for 600. 38-UI-SPEC's preferred resolution is adding `font-semibold` in the CONSUMER's
    className. Do NOT patch `alert.tsx`.
  - The base class already includes `[&>svg]:absolute [&>svg]:left-4 [&>svg]:top-3 [&>svg~*]:pl-7`
    and `relative` at :7, so the icon is positioned by the primitive and an `absolute right-2 top-2`
    dismiss button needs no extra positioning context.

The only in-repo `Alert variant="destructive"` + `AlertCircle` composition is
src/app/admin/import/pipedrive-api/steps/api-key-step.tsx:79-83.

`labelById` is captured at SUBMIT time, not render time, and that is deliberate (38-RESEARCH
Pattern 3): a record that failed with `notFound` may already be gone from the NEXT server render, but
the caller still holds the array it submitted from. The server returns `{ id, reason }` only — no
display name crosses the boundary, which is cheaper and keeps the reason a closed union with no raw
server prose.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server action → failure report | The only data crossing is `{ id, reason }`; a raw server message would be untranslatable and could leak internals |
| failure list → user's record of what went wrong | A capped list is indistinguishable from a swallowed failure |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-38-07 | Information Disclosure | the reason rendered per failure | mitigate | The lookup is `t("reason." + failure.reason)` over the closed four-member `BulkFailureReason` union with no fallback branch, and `BulkFailure` has no `error`/`message` field to render. The gate additionally proves every union member has a copy key, so a fifth reason cannot ship as an untranslated raw key |
| T-38-27 | Repudiation (silently swallowed failure) | the failures list | mitigate | Every failure is rendered, in submit order, with no `.slice(` and no "and N more" element — asserted by a source gate whose negative direction is demonstrated. Height is bounded by `max-h-48 overflow-y-auto` so 40 failures do not grow the page while all 40 remain in the DOM and in the accessibility tree |
| T-38-28 | Repudiation (report disappears before it is read) | dismissal behaviour | mitigate | No `setTimeout` / `setInterval` anywhere in the file, asserted by the gate. Dismissal is the explicit button, a replacing bulk result, or the caller clearing the selection |
| T-38-29 | Tampering (colour as the sole carrier) | `Alert variant="destructive"` | mitigate | The variant supplies no background fill, the reason is real text rather than a colour or an icon, and the title states a count.
