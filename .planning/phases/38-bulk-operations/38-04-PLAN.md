<objective>
Add `ids?: string[]` to `ExportFilters` and honour it in all four private fetchers in
`formatters.ts`, then prove the narrowing against the live Docker Postgres.

Purpose: BULK-04 is "only the selected records, not the whole table". `fetchFilteredData` currently
exposes no id filter at all — `ExportFilters` is `{ stage, owner, dateFrom, dateTo }`. Without this
change the scoped export action has no way to narrow and would have to either duplicate the whole
fetch/flatten/serialise pipeline or silently export everything.
A live-database probe is mandatory here, not optional: Phase 37 shipped a malformed drizzle `sql`
fragment that a wholly-mocked suite passed cleanly (`${ids}` expanded to `= ANY(($1,$2,$3))`), and
`src/lib/export/formatters.test.ts` stubs `db` as `{ query: {} }` precisely because nothing it tests
touches the database — so it structurally cannot catch a malformed `inArray`.
Output: the widened filter type, four narrowed fetchers, extended unit coverage, and an
environment-gated live test.
</objective>

  export type ExportEntityType = "organization" | "person" | "deal" | "activity"
  export type ExportFormat = "csv" | "json" | "pipedrive-csv" | "pipedrive-json"

`ExportOptions` and `ExportResult` need NO change. Only `ExportFilters` gains `ids?: string[]`.

Four insertion points in src/lib/export/formatters.ts:
  fetchOrganizations  ~:249-267   `const conditions = [isNull(organizations.deletedAt)]`      (inferred array)
  fetchPeople         ~:269-287   inferred array
  fetchDeals          ~:290-307   `const conditions: ReturnType<typeof eq>[] = [...]`         (ANNOTATED)
  fetchActivities     ~:322-336   `const conditions: ReturnType<typeof eq>[] = [...]`         (ANNOTATED)

`inArray` returns `SQL<unknown>`, so the two ANNOTATED arrays are the typecheck risk
(38-RESEARCH assumption A1). Verify with `npm run typecheck`; if the annotation rejects `SQL<unknown>`,
widen the annotation to `SQL<unknown>[]` (import `SQL` as a type from `drizzle-orm`) rather than
adding a cast or an `@ts-expect-error`.

Drizzle 0.45.1 behaviour, verified in node_modules/drizzle-orm/sql/expressions/conditions.js:76 —
`inArray(col, [])` returns `sql\`false\``, i.e. zero rows, never a full table scan. Still guard at
the action boundary (plan 38-11..38-14), but the query itself cannot degrade.

Live database connection for the probe: `postgresql://pipelite:pipelite@localhost:5433/pipelite`.
Note `.env.local` says port 5432 but the Docker mapping is host 5433 -> container 5432, so the probe
must pass DATABASE_URL explicitly. Vitest does NOT put DATABASE_URL into process.env (verified: any
`src/lib/mutations/*` import throws "DATABASE_URL environment variable is not set"), which is what
makes an env-gated skip safe.
