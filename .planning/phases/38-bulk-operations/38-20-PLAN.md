Live data facts, measured 2026-08-17:

  The other 6 users are all `approved` but all soft-deleted
  All 46,054 organizations are owned by that one user

  `deal_assignees` has 0 rows
  1 active webhook; 3 workflows, 0 active
  `trash.retention_days` is set (Phase 37 recorded the live value as 30)

THE CANONICAL PARTIAL-FAILURE SCENARIO, which the second user unlocks: reassign 3 organizations to user B,
then select those 3 plus 9 still owned by the admin and bulk delete. Organizations have NO admin bypass, so
exactly 3 fail with `notPermitted` and 9 succeed — a real 9/12 partial failure rather than a simulated one.
On DEALS the same sequence would fully succeed, because deals DOES have the admin bypass. That asymmetry is
itself worth showing, and showing both is how the authorization matrix is proven end to end.

Audit timing hazard: the audit insert is deliberately NOT awaited — `subscribers/audit.ts:70-88` fires
`db.insert(auditLog)...catch(...)` and returns, because `crmBus.emit` is synchronous and cannot await. The
server action returns and `revalidatePath` runs while up to 100 inserts are still in flight. So for SC-5,
RE-READ the record's history (or re-poll `audit_log`) rather than asserting on the first render after the
toast, and allow a short settle in any DB probe. An assertion that passes on a slow machine and fails on a
fast one is this hazard.

320px method: `resize_window` CANNOT change `window.innerWidth` in this environment (Phase 37, measured).
Use a 320px SAME-ORIGIN IFRAME — media queries evaluate against the iframe, so Tailwind breakpoints
genuinely apply. This turned an unverifiable gap into a found-and-fixed defect in Phase 37.
The global app `<header>` ALREADY overflows at 320px on EVERY route (`scrollWidth 416` vs `clientWidth 301`,
identical on /organizations, /people, /deals and /trash) — tracked as 37-UAT G5, pre-existing and app-wide.
Measure the BAR's own `scrollWidth`/`clientWidth`, not the document's, and do NOT attribute the header's
overflow to this phase's bar.

Pre-existing hazard to note but NOT fix: `d`/`e`/`n` fire while a bulk dialog is open, because
`useDataTableKeyboard`'s hotkeys are document-level `react-hotkeys-hook` bindings guarded only by
`isFormFocused()`, which checks for INPUT/TEXTAREA/SELECT/contenteditable — and a focused Radix dialog
button is none of those. This is already true of the existing single-record delete dialog. 38-RESEARCH
assumption A4 flags that it is UNVERIFIED whether Radix blocks document-level listeners; verify it in the
browser and record the answer either way. Do not fix it here.
