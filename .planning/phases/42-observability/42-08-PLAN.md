<migration_contract>
Signature: `log.<level>(scope, msg, ctx?)` — exactly three arguments, the error ALWAYS under `ctx.err`.
Import: `import { log } from "@/lib/log"`.
Level map: `console.error`→`log.error`, `console.warn`→`log.warn`, `console.log`→`log.info`,
`console.info`→`log.info`.

**Scope rule.** A `[bracket]` prefix in the existing string ⇒ use that name verbatim as `scope`; the 22
existing bracket names are referenced by name in file headers and runbooks and must survive. No bracket
⇒ derive from the module path with `src/` and the extension stripped and `/` kept
(`src/lib/mutations/deals.ts` → `mutations/deals`). **ONE FILE MAY MIX BOTH.** Never blanket-apply a
per-file scope.

**Message rule.** The trailing `:` moves out of the message. Interpolated values move OUT of the string
into named `ctx` keys. **Never add a value that was not already in the string.** This is the single
easiest place in the phase to widen what is logged: `console.error(msg, err)` today prints a truncated
`util.inspect` view, and a JSON logger serializing the whole `ctx` can newly expose row contents. Two
in-source precedents already require counts-only logging.

**Control flow rule.** Byte-for-byte equivalent. A swallow-and-log catch keeps swallowing; its body
keeps exactly the statements it had; a `.catch(...)` stays attached. Read any header comment above a
catch before touching it. Never turn a swallow into a rethrow.

**Style rule.** Match the surrounding file's quote style; this repo is mixed. Do not reformat anything
you are not migrating.
</migration_contract>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user form input / API request body → mutation function → log line | These are the CRM's write paths. Every value in scope at a catch site is potentially a customer record field, an email address or an owner id. |
| application → container stdout | Migrated lines cross into Docker's json-file driver and any log aggregator an operator later adds |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-04 | Information disclosure | the 26 migrated call sites | mitigate | Each site logs exactly what its original string logged: a fixed message plus the caught error. No deal, person or note payload, no email address, no owner id and no field value is added to `ctx`. Enforced by the `git diff` criterion (changes on migrated lines only) and by the requirement to quote any site whose `ctx` gains a key. |
| T-42-05 | Tampering / Repudiation | user-controlled text reaching a log line | mitigate | Inherited from plan 01: `JSON.stringify` escapes newlines, so a newline in a note body or a person's name cannot forge a second log line. This is a genuine improvement over the current `console.error(msg, value)` form. |
| T-42-27 | Tampering | control flow of the CRM's write paths | mitigate | Byte-for-byte equivalent control flow is a hard constraint. Every one of these 26 sites sits in a catch that returns `{ success: false, error }`; a rethrow introduced here would surface as a 500 on a user action. The existing `src/lib/mutations` suites are the regression detector and must pass unchanged apart from the two named assertions. |
| T-42-28 | Repudiation | loss of the `[audit]` and `[formula-recalc]` scope names | mitigate | Three of these 26 sites carry scope names that file headers and runbooks refer to by name, and two test files assert on them. Preserving them verbatim as the `scope` field keeps every existing operational query answerable. Enforced by the acceptance criterion asserting the exact scope set per file. |
</threat_model>
