<migration_contract>
Signature: `log.<level>(scope, msg, ctx?)` — exactly three arguments, the error ALWAYS under `ctx.err`.
Import: `import { log } from "@/lib/log"`.
Level map: `console.error`→`log.error`, `console.warn`→`log.warn`, `console.log`→`log.info`,
`console.info`→`log.info`.

**Scope rule for route files** — a deliberate refinement of RESEARCH's single worked example, stated so
a reviewer does not read it as drift. RESEARCH says "derive from the module path with `src/` and the
extension stripped and `/` kept", and gives `src/app/api/v1/deals/[id]/route.ts` → `api/v1/deals`.
Collapsing the item route and the collection route into one scope loses a distinction the error paths
need, so this phase keeps the dynamic segment. The exact rule, applied identically in plans 10, 11, 14
and 15:

- strip the leading `src/`
- strip the leading `app/`
- strip the trailing `/route.ts` (or `/page.tsx`, or the `.ts`/`.tsx` extension for a non-route module)
- keep every remaining segment verbatim, dynamic segments included

Worked examples: `src/app/api/v1/deals/route.ts` → `api/v1/deals`;
`src/app/api/v1/deals/[id]/route.ts` → `api/v1/deals/[id]`;
`src/app/api/v1/trash/[type]/[id]/restore/route.ts` → `api/v1/trash/[type]/[id]/restore`.

A `[bracket]` prefix already present in the string always wins over the path derivation.

**Message rule.** The trailing `:` leaves the message. Where the message repeats the route path that the
scope now carries, drop the path and keep the HTTP verb: `"GET /api/v1/audit failed:"` becomes the
message `"GET failed"` under scope `api/v1/audit`. Interpolated values move into named `ctx` keys.
**Never add a value that was not already in the string.**

**Control flow rule.** Byte-for-byte equivalent. Every one of these sites sits in a catch that returns
an error response; the status code, the response body and the catch structure must not change.
</migration_contract>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-04 | Information disclosure | the 29 migrated sites, and the three object/result-argument sites above all | mitigate | Each site logs exactly what its original string logged. `trash/route.ts:266`'s existing object keys are carried as-is with nothing added; `notes/[noteId]/route.ts:109,145` carry only the field the original surfaced, never the whole result object. Both are required to be quoted before/after in the summary, so a widening is visible in review rather than buried in a 29-site diff. |
| T-42-29 | Information disclosure | the `Error` now serialized with a full stack | accept | Plan 01's serializer emits `err.stack`, which `console.error(msg, err)` also printed. The stack contains file paths and function names but no request data. Container stdout is not a client-visible surface, and the stack is the single most valuable field for diagnosing a v1 failure. |
| T-42-05 | Tampering / Repudiation | user-controlled text reaching a log line | mitigate | Inherited from plan 01: `JSON.stringify` escapes newlines, so a note body or organization name containing a newline cannot forge a second log line. |
| T-42-30 | Tampering | the public REST contract | mitigate | Byte-for-byte equivalent control flow. All nine `[formula-recalc]` sites exist so a recalculation failure resolves rather than rejects (D-05); converting any of them to a rethrow would turn a soft degradation into a 500 on a customer's API call. The two formula-recalc suites' `invocationCallOrder` and emitted-payload assertions are the regression detector and must pass untouched. |
| T-42-28 | Repudiation | loss of the `[formula-recalc]` scope name | mitigate | Nine sites plus three in-source doc comments plus six test assertions refer to this scope by name. It is preserved verbatim as the `scope` field, and all three surfaces are updated in the same plan so none is left describing a string that no longer exists. |
