<objective>
Wire the four `crmBus` event subscribers into the heartbeat registry and migrate their three
`console.*` calls.

Purpose: a dead subscriber is invisible to a processor-only health check, and it has already caused a
real defect — the 2026-08-16 incident where every audit row was written with `actor_kind = system`
because `src/lib/audit/actor-context.ts` was instantiated in two different module graphs. CONTEXT
requires all four subscribers in `/api/health` for exactly that reason.

There is a specific trap here. All four subscribers already guard re-registration with a module-level
`let registered = false` (`webhook.ts:12`, `workflow-trigger.ts:12`, `stage-history.ts:6`,
`audit.ts:34`). Those flags are per-instance and unreadable from the route's module graph. The health
route must NEVER consult them — the heartbeat registry on `globalThis` is the only bridge that works.

Two of this plan's three migration sites are also two of the phase's three argument-shape test
assertions, and both sit inside `.catch` handlers whose presence is mandatory: `audit.ts:70-75` and
`stage-history.ts:19-21` both explain that dropping the `.catch` turns a lost row into an unhandled
rejection.

Output: four subscribers registering and ticking, three migrated call sites, two updated assertions.
</objective>

<subscriber_liveness_semantics>
A subscriber is event-driven and may legitimately never fire — a quiet CRM emits nothing. So:

| Signal | What it proves | What it CANNOT prove |
|---|---|---|
| registration | `registerXSubscriber()` executed IN THIS PROCESS. This is the whole 2026-08-08 failure class, and the reason the four subscribers today emit no boot log at all: there is currently literally no way to tell whether they ran. | That the handler will ever be invoked. |
| `lastTickAt` | The handler ran at least once, so this subscriber is attached to the SAME `crmBus` instance the emitters use. | Liveness. Absence is not failure. |

So `alive` comes from registration, and `lastTickAt` is reported as a diagnostic only. The diagnostic
is sharp: registered but `lastTickAt` still null after known CRM writes is the fingerprint of a
module-graph split — exactly the 2026-08-16 `actor_kind = system` defect.
</subscriber_liveness_semantics>

<migration_contract>
Signature: `log.<level>(scope, msg, ctx?)` — three arguments, the error ALWAYS under `ctx.err`.
Import: `import { log } from "@/lib/log"`.
Level map: `console.error`→`log.error`, `console.warn`→`log.warn`, `console.log`→`log.info`,
`console.info`→`log.info`.
Scope rule: bracket prefix present ⇒ use it verbatim; absent ⇒ derive from the module path.
Message rule: trailing `:` out of the message; interpolated values into `ctx` keys; never add a value
that was not already in the string.
Control flow rule: byte-for-byte equivalent. A mandatory `.catch(...)` stays attached and stays
swallowing.
</migration_contract>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `crmBus` event payloads → subscriber handlers → log line | Payloads carry CRM record data (deal, person, organization and activity fields). Anything a handler logs crosses into container stdout. |
| subscriber module graph → heartbeat registry | The write side of the `globalThis` bridge `/api/health` reads |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-04 | Information disclosure | the three migrated `.catch` log calls | mitigate | Each currently logs a bracket prefix and an `Error` and nothing else. The migrated form logs a fixed message and the same error under `ctx.err`. The event payload — which carries CRM field values — is NOT added to `ctx`. This is the single easiest place in the phase to accidentally widen what is logged, and the contract forbids it. Enforced by reviewing each site against its original argument list. |
| T-42-25 | Tampering | the mandatory `.catch` attachments | mitigate | Both `audit.ts:65-75` and `stage-history.ts:19-21` explain that dropping the `.catch` converts a lost row into an unhandled rejection. The migration changes the callback body and nothing else; the existing `not.toThrow()` and unhandled-rejection assertions are the regression detector and must keep passing verbatim. |
| T-42-10 | Repudiation | `alive` derived from a per-instance flag | mitigate | The route must never read a subscriber's `let registered` flag: those flags are module-scoped and therefore per-Turbopack-instance, so the route would read a different copy and always see `false`. Registration goes through `registerSubscriber` on the `globalThis` registry instead, and a comment at each flag records why. |
| T-42-26 | Repudiation | a quiet CRM misread as a dead subscriber | mitigate | `alive` derives from registration, never from `lastTickAt`. A CRM that emits no events for a week must not turn its subscribers red, or the endpoint gets ignored — which is worse than not having it. Asserted by the "still alive far in the future with lastTickAt null" test. |
| T-42-24 | Denial of service | `recordTick` at handler entry | mitigate | `recordTick` is a no-op for an unknown name and never throws (plan 02). A throw at handler entry would break event handling for every audited event — a far worse outcome than a missing heartbeat. |
</threat_model>
