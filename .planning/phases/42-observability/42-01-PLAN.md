    - A `cause` chain serialises: `new Error("outer",{cause:new Error("inner")})` yields `err.cause.message === "inner"`.
    - A cause chain deeper than the depth cap terminates without throwing and without infinite recursion.
    - A non-Error value in `ctx` (a string, a number, a plain object) passes through unchanged.

    Console delegation — amendment A3, keeps test fallout at 3 assertions instead of 89

    Throw-safety — a logger must never throw

    - A `BigInt` in `ctx` does not throw.
    - A ctx payload far larger than the line cap emits a truncated line carrying `level`, `scope`, `msg`, `ts` and a truncation marker, still under the cap, still valid JSON.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-controlled value → log line | Any `ctx` value may originate from a request body, a CRM field or an external API response, and is serialized into a line that downstream tooling parses as JSON |
| application → container stdout | Log lines cross into Docker's json-file driver and, later, into any log aggregator an operator adds |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-05 | Tampering / Repudiation | `emit()` in `src/lib/log.ts` | mitigate | `JSON.stringify` escapes `\n`, so a newline in a user-controlled value cannot forge a second log line. Asserted directly by the log-injection test in task 1, not assumed. |
| T-42-08 | Tampering | `emit()` line length | mitigate | 8000-character cap, under Docker's 16 KB json-file split threshold, with the truncated form still valid JSON carrying level/scope/msg/ts. Asserted by the oversized-payload test. |
| T-42-11 | Denial of service | `emit()` throw path | mitigate | The whole serialization sits in a try/catch with a minimal-line fallback. A logger that throws inside a catch block converts a handled error into an unhandled one. Asserted by the circular-reference and BigInt tests. |
| T-42-04 | Information disclosure | the `ctx` argument | accept (in this plan) | The logger serializes whatever it is handed; it cannot know what is sensitive. The control lives at the call sites and is enforced by the migration contract in plans 06-16 ("never add a value that was not already in the string"). Recorded here so the split of responsibility is explicit rather than assumed. |
| T-42-12 | Information disclosure | `process.env` read | mitigate | The module reads exactly one variable by name (`LOG_LEVEL`). It never enumerates `process.env`, so no secret can be swept into a line by the logger itself. |
</threat_model>
