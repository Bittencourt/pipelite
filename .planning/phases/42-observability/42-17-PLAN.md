Purpose: OBS-02's seam and A7's first site.

`onRequestError` is the only hook Next.js offers that sees render, route, action and proxy errors
uniformly (`RequestErrorContext.routeType` is `'render' | 'route' | 'action' | 'proxy'`, verified in the
installed `next@16.1.6` types). It replaces per-call-site wrapping entirely.

The binding constraint is amendment A6. This file is compiled TWICE — once for Node and once for the
edge runtime — and its edge copy is currently `async function t(){}`, an empty function, verified in
`.next/server/edge/chunks/_52aa5b93._.js`. It is empty *only* because every dependency sits behind
`await import()` inside the `process.env.NEXT_RUNTIME === "nodejs"` guard. That rules out Sentry's own
documented one-liner `export const onRequestError = Sentry.captureRequestError`, which needs a top-level
import and would drag the SDK into the edge bundle — violating the server-only decision from the
opposite direction, and possibly failing the build, since edge has no `node:` builtins.

`docker compose logs app | grep -F '[trash-prune] Starting'`. That string ceases to exist after plan 06,
and the six processors now have a real detector.

Output: a wired, still-empty-on-edge `instrumentation.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any unhandled server error → `onRequestError` → Sentry | Every render, route, action and proxy error in the application funnels through this one export. The error object, the request path, the method and the headers all arrive here. |
| Node build ↔ edge build of the same file | This module is compiled twice; what it imports at the top level determines what enters the edge bundle |
| container boot → worker startup | `register()` is the single point where a startup failure either gets captured or is lost |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-20 | Denial of service | edge-runtime double compile | mitigate | Exactly one top-level import and it is `import type`. Every value import stays inside the `NEXT_RUNTIME` guard, which is what keeps the edge copy compiling to `async function t(){}`. A top-level SDK import would pull `node:` dependencies into a runtime that has none, growing the edge bundle at best and failing the build at worst. Enforced by an exact-count grep on top-level imports. |
| T-42-18 | Information disclosure | the `request` argument passed to `reportRequestError` | mitigate | This file passes Next's `request` object straight through to `reportRequestError` and adds nothing. Plan 04 owns the field selection: only `path`, `method`, `routePath` and `routeType` are logged, and the headers map — which may carry a bearer token or a session cookie — is never placed in a `ctx` object. Keeping this file a thin delegator is what keeps that decision in one reviewable place. |
| T-42-06 | Information disclosure | Sentry egress | mitigate | Initialisation happens through plan 04's `initSentry`, which applies both `dataCollection` and `beforeSend` scrubbing. This file does not configure Sentry and must not; adding an `init` call here would create a second, unscrubbed configuration path. |
| T-42-19 | Information disclosure | scope of what reaches the tracker | mitigate by design | `onRequestError` fires only for genuinely unhandled errors. The repo's swallow-and-log catches and its `{ success: false }` server actions never reach it, so the CRM's entire handled-error volume stays off the wire. Stated in the file's doc comment so nobody later "fixes" the apparent gap by wiring `log.error` into `captureException`. |
| T-42-09 | Denial of service (of the background jobs) | the A7 gate comment | mitigate | The comment is the only place a future reader learns how to verify that `register()` actually ran. Leaving it pointing at a string that no longer exists would produce a guaranteed false negative — a verifier greps, finds nothing, and concludes the processors are dead. It now names `/api/health` (runtime) and plan 03's Dockerfile postcondition (build time). |
| T-42-54 | Denial of service | a throw during Sentry init | accept | `initSentry()` runs before the twelve worker imports, so a throw there would prevent every processor from starting. Accepted because `initSentry` returns early when `SENTRY_DSN` is unset (the default), and because the alternative — initialising after the workers — would lose exactly the startup errors the hook exists to capture. `/api/health` would report the outcome as 503 with ten dead workers, which is the correct signal. |
</threat_model>
